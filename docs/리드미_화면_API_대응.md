# 리드미 화면과 API 대응

2026-11-13에 쓰고, 프런트가 시안의 화면을 모두 옮긴 뒤 2026-11-15에 머리말과 4절을 고쳤다. 같은 날 서버 작업 브랜치 11개가 `dev`에 들어간 뒤 1~3절의 서버 쪽을 맞췄다. 그 뒤 다섯 가지(내 공고 넣기, 올리기의 키워드·묶음, 읽어 오기의 키워드, 읽어 오기의 파일, 그룹 공고 목록의 원문 주소)가 더 들어가 1절과 4절을 다시 맞췄다. 화면구조도의 화면 27개 가운데 25개의 시안이 나왔다. 이 문서는 화면마다 무엇이 보이고 무엇을 누르는지, 그것이 어느 API에 기대는지, 설계에 아직 없는 것이 무엇인지를 모은 것이다. 서버를 만드는 쪽이 시안을 열지 않고도 화면이 요구하는 것을 알 수 있게 적었다.

- 시안(캔버스 "리드미 시안 3종". 5~9차 쪽이 2026-11-13에 더한 21개): https://claude.ai/artifact/M17BpvArDHoogfCnz87cfw
- 화면구조도: https://claude.ai/artifact/4HhMKRTdrUmF6yqrV33zvV
- 설계: `docs/리드미_설계_로그인.md`(아래에서 "로그인 문서"), `docs/리드미_설계_경험카드.md`("경험카드 문서"), `docs/리드미_설계_그룹.md`("그룹 문서"), `docs/리드미_설계_공고.md`("공고 문서")
- 백엔드 구조(만든 API, 공통 규칙): `docs/리드미_백엔드_구조.md`("구조 문서")
- 정한 것과 남은 결정: `docs/리드미_리서치_재사용_정리.md`("정리 문서")

이 문서에서 새로 정한 것은 없다. 3절은 없는 것과 선택지만 적었고, 시안이 가정이나 제안으로 그린 값은 5절에 모았다.

시안은 캔버스에만 있다. 저장소에는 그룹 공고 목록·상세의 원본만 있다(`docs/design`). 5~9차 시안도 프런트로 옮기며 그려진 모습대로 만들었다(2026-11-14). 옮긴 화면과 창은 `frontend/scripts/regress.mjs`의 장면으로 찍어 볼 수 있다.

## 2. 화면별로 보이는 것과 쓰는 API

"보이는 것"은 시안에 그려진 값과 버튼이다. 예시 값(이름, 회사, 숫자)은 지어낸 것이다.

### 2.1 로그인 전

| 화면 | 보이는 것과 누르는 것 | API |
|---|---|---|
| 랜딩 | 기능 설명 세 가지, 공개 범위 세 가지의 설명. 로그인, 회원가입, 시작하기 | 없음 |
| 로그인 | 이메일, 비밀번호, 구글로 계속하기. 비밀번호 재설정과 회원가입으로 가는 링크 | `POST /api/auth/login`, `GET /oauth2/authorization/google` |
| 회원가입 | 표시 이름("그룹 멤버에게 보이는 이름"), 이메일, 비밀번호, 구글로 계속하기. 이미 가입된 이메일이면 이메일 칸 아래에 알리고 로그인과 재설정 링크를 준다 | `POST /api/auth/signup`. 이미 있는 이메일은 409 |
| 이메일 인증 | 상태 셋. 보냄: 받는 주소, 링크를 24시간 동안 쓸 수 있다는 안내, 메일 다시 보내기. 끝남: 로그인하기. 쓸 수 없음(지났거나 이미 씀): 이메일을 넣고 확인 메일 다시 받기 | `POST /api/auth/verify-email`, `POST /api/auth/verify-email/resend` |
| 비밀번호 재설정 | 상태 다섯. 요청: 이메일. 보냄: "가입된 이메일이라면 … 재설정 메일이 갑니다", 링크를 1시간 동안 쓸 수 있다는 안내. 새 비밀번호: 칸 하나, "바꾸면 다른 기기의 로그인이 모두 풀립니다". 끝남: 로그인하기. 쓸 수 없음: 재설정 메일 다시 받기 | `POST /api/auth/password-reset/request`, `POST /api/auth/password-reset/confirm` |
| 그룹 초대 수락 | 상태 셋. 로그인한 사람: 그룹 표시 글자와 이름, 초대 링크를 만든 사람의 이름, 멤버 수, 처음 공개 범위가 "지원 여부까지"라는 안내, 그룹 들어가기, 나중에. 손님: 같은 내용에 로그인하고 들어가기, 회원가입, "로그인하거나 가입을 마치면 이 화면으로 돌아옵니다". 쓸 수 없음: 링크를 7일 동안 쓸 수 있다는 안내, 내 그룹으로 | `GET /api/group-invites/{token}`(로그인 없이), `POST /api/group-invites/{token}/accept`. 지난 링크는 410 `INVITE_EXPIRED` |

### 2.2 경험카드

| 화면 | 보이는 것과 누르는 것 | API |
|---|---|---|
| 카드 목록 | 카드마다 제목, 기간, 어디서, 맡은 일, 태그, 요약, 문항 유형, 확인 여부. 태그별 카드 수. 거르기는 화면이 한다 | `GET /api/cards`, `GET /api/cards/tags` |
| 카드 상세·편집 | 보기: "확인 필요" 표시, 기간, 제목, 어디서·맡은 일, 요약, STAR 네 칸(자료에 없는 숫자는 "확인 필요: 30%"로 표시), 근거 숫자, 확인할 것(오류·경고, 칸, 글), 추출 메모, 태그, 문항 유형, 공개 범위("나만 보기" 하나), 뽑아 온 자료의 파일 이름. 삭제, 수정, 확인하기. 고치기: 모든 칸, 요약 글자 수(32 / 60자), 근거 숫자 더하기, 태그 더하기(다른 표기를 치면 대표 표기 "Kubernetes"와 "k8s의 대표 표기"라는 설명을 보여 준다), 문항 유형 6종 | `GET`·`PUT`·`DELETE /api/cards/{id}`, `POST /api/cards`, `POST /api/cards/{id}/verify`, `GET /api/keywords?q=` |
| 자료로 카드 만들기 | 상태 넷. 올리기: 파일(PDF, DOCX, HWPX, PPTX, TXT, MD · 20MB까지) 또는 글 붙여넣기. 읽음: 파일 이름, 글자 수(12,480자), 조각 수(3개), AI 호출 수(3회), 카드 뽑기 시작. 뽑는 중: "조각 2 / 3", "지금까지 카드 4장", "이 화면을 닫아도 계속됩니다". 끝남: 새 카드 5장, 건너뜀 1개(같은 경험인 기존 카드의 제목). 아래에 올린 자료 목록과 지우기 | `POST`·`GET`·`DELETE /api/card-sources`, `POST /api/card-sources/{id}/extract`, `GET /api/card-extractions/{jobId}` |

## 4. 프런트에 이미 있는 화면이 기대는 것

그룹 공고 목록과 상세는 공고 문서 8절에 있다. 시안이 있는 화면은 모두 프런트에 있다. `npm run dev`에서는 각 층의 `api.ts`가 모두 가짜 서버(`frontend/src/mocks/`)를 부른다. `npm run dev:server`와 빌드에서는 서버에 API가 있는 것이 모두 `shared/lib/api.ts`의 `request`로 서버를 부르고(2026-11-15, 1절), 메일 확인함, 메일 자동화 설정, 홈의 "메일에서 온 변경"과 카드 뽑기만 서버를 부르지 않는다. 개발 프록시는 두지 않았고, 서버 주소는 `VITE_API_ORIGIN`(없으면 `http://localhost:8080`)이다. 화면이 기대는 응답 모양은 그 층의 `types.ts`, 부르는 함수는 `api.ts`에 있다.

| 층(`frontend/src/…`) | 화면 | 가짜 서버(`mocks/…`) |
|---|---|---|
| `features/auth` | 첫 화면, 로그인, 가입과 메일 보냄, 이메일 인증, 비밀번호 재설정(요청, 보냄, 새 비밀번호), 초대 받기 | `db.ts` |
| `features/cards` | 경험카드 목록, 상세, 고치기, 자료로 카드 만들기, 확인 | `cards-db.ts`(예시 카드는 `example-cards.ts`) |
| `features/group-posts` | 그룹 공고 목록, 상세, 공고 올리기, 칸 확인 | `db.ts`(예시 그룹과 공고는 `example-data.ts`) |
| `features/groups` | 내 그룹, 멤버 | `db.ts` |
| `features/my-posts` | 홈, 내 공고, 내 공고 상세, 지원 현황, 달력 | `my-db.ts`(내 공고 행은 `user-postings.ts`), 홈의 메일 변경 수는 `mail-db.ts` |
| `features/mail` | 메일 확인함 | `mail-db.ts` |
| `features/settings` | 내 정보, 메일 자동화, 탈퇴 | `account-db.ts` |
| `domain/session`, `domain/group` | 화면 틀이 읽는 보는 사람(`GET /api/me`)과, 그룹 화면의 그룹 | `db.ts` |

- 가짜 서버는 새로 불러오면 처음 상태가 된다. 주소에 `?mock=guest`(로그인 안 함), `?mock=no-groups`(그룹 없음), `?mock=no-google`(구글 연결 안 함)을 붙이면 그 상태로 시작한다.
- 설계가 없어 프런트가 응답 모양을 정한 곳에는 코드에 `// shortcut:` 표시와 3절 번호가 있다.
- 경험카드: 2026-11-13에 본 것은 경험카드 문서 6절에 있다.
- 로그인(`frontend/src/features/auth`): 이메일 로그인은 `POST /api/auth/login`을 부르고, 구글은 서버의 `/oauth2/authorization/google`로 페이지를 옮긴다(2026-11-15).
- 회원가입, 이메일 인증, 비밀번호 재설정(`frontend/src/features/auth/api.ts`): 가입에서 이미 있는 이메일을 `EMAIL_TAKEN`이라는 이름으로 구분한다. 인증 링크 쓰기와 새 비밀번호 내기는 결과를 됨(`done`)과 쓸 수 없음(`expired`) 둘로 본다. 재설정 링크는 새 비밀번호 화면을 열 때 쓸 수 있는지 먼저 묻는다(`checkResetToken`. 3절 20번의 토큰 확인이 있다고 보고 짰다). 확인 메일 다시 보내기와 재설정 요청은 계정이 있는지 구분하지 않는다.
- 메일의 링크가 여는 프런트 주소는 `/verify-email?token=…`(가입 확인)과 `/password-reset/new?token=…`(재설정)이다. 서버가 메일에 이 주소를 넣어야 한다.

## 5. 시안이 깔고 있는 것

### 5.1 설계의 가정대로 그린 것

가정을 바꾸면 화면도 바뀐다.

| 화면 | 가정 |
|---|---|
| 회원가입, 이메일 인증, 비밀번호 재설정 | 로그인 문서 L4(인증 전에는 로그인할 수 없다), L5(가입 확인 24시간, 재설정 1시간). 가입은 이미 있는 이메일을 알려 주고, 재설정 요청과 다시 보내기는 계정이 있는지 알려 주지 않는다. 비밀번호를 바꾸면 그 계정의 세션이 모두 끊긴다 |
| 경험카드 | 경험카드 문서 C2(올린 파일은 저장하지 않는다), C3(추출은 서버가 뒤에서 돌리고 화면이 상태를 묻는다), C4(공개 범위는 "나만 보기" 하나), C5(추출된 카드는 바로 목록에 "확인 필요"로 들어간다) |
| 그룹 | 공고 문서 P2(공고 본체를 그룹들이 함께 쓴다. 넣은 마감일이 다른 그룹에도 보인다), P4(내려도 행은 남는다), P5(날짜 넣기는 못 읽은 공고에만, 멤버 누구나, 한 번), 그룹 문서 G1(초대는 링크, 7일, 멤버 누구나), G2(그룹장은 한 명이고 나갈 수 없다) |
| 홈·내 공고 | 공고 문서 P1(지원 상태는 결정·단계·결과 세 칸), P7(관심을 꺼도 내 공고에 남는다) |

### 5.2 정해지지 않아 제안으로 그린 것

프런트(dev `295ab2f`)는 모두 시안대로 만들었다. "프런트" 칸은 만든 모습이다.

| 항목 | 시안의 값 | 프런트 |
|---|---|---|
| 비밀번호 규칙 | "8자 이상". 자리만 잡은 글자다 | 시안대로. 안내 글 "8자 이상"을 두고 입력 칸이 8자 미만을 막는다 |
| 그룹이 없는 사람의 첫 화면 | 내 그룹의 빈 상태 | 시안대로. 그룹이 없으면 홈(`/`)이 내 그룹(`/groups`)으로 보낸다 |
| 내 그룹의 자리 | 위쪽 헤더의 "스터디" 메뉴 아래 | 시안대로. 헤더의 "스터디"를 누르면 내 그룹으로 간다 |
| 홈 쪽 메뉴 | 헤더는 그대로 두고 홈 아래에 줄을 하나 더 둔다: 홈, 내 공고, 지원 현황, 달력, 메일 확인함 | 시안대로. 다섯 화면의 위에 같은 줄이 있다 |
| 헤더 오른쪽 | 5·6차는 "로그아웃" 버튼, 7~9차는 내 계정 동그라미(누르면 내 정보). 하나로 맞추지 않았다 | 로그인한 뒤의 모든 화면이 내 계정 동그라미다(누르면 내 정보). 로그아웃은 내 정보에 있다 |
| 공고의 꼭 있어야 하는 칸 | 회사명, 공고명, 마감, 원문 링크 | 시안대로 네 칸을 "꼭 있어야 하는 칸"에 둔다. 비어 있으면 올리지 않는 것은 회사명, 공고명, 마감이고, 원문 링크는 비워도 올린다 |
| 링크 처리 | 서버가 링크를 읽는 길과 본문을 붙여넣는 길을 둘 다 그렸다 | 시안대로 둘 다 있고 파일도 받는다. 가짜 서버는 파일 내용을 읽지 않는다 |
| 상태 바꾸기의 자리 | 지원 현황 화면의 옆 칸 | 시안대로. 공고 상세의 "상태 바꾸기"도 지원 현황의 그 칸을 연다 |
| 카드 확인의 "나중에 보기" | 서버에 남기는 값이 없다. 카드가 "확인 필요"로 남는다 | 시안대로 |
| 받는 파일 형식과 크기 | 자료: PDF, DOCX, HWPX, PPTX, TXT, MD. 공고: PDF, DOCX, HWPX, HWP. 둘 다 20MB까지 | 시안대로 안내 글에 적었다. 파일 고르기 창은 그 형식만 보여 준다. 크기는 막지 않는다 |
| 메일 수신 주소의 꼴, 보내는 주소 등록 | 자리만 잡았다 | 시안대로. 가짜 서버는 `daon-7f3k9x2m@in.readme.example` 같은 주소를 만든다 |

프런트가 시안 없이 정한 것:

- 로그인하지 않은 사람이 `/`로 오면 랜딩(`/welcome`)으로 간다. 다른 주소로 오면 로그인(`/login`)으로 간다.
- 탈퇴한 뒤에도 랜딩으로 간다.

### 5.3 시안끼리 맞지 않아 데이터대로 둔 것

- 그룹 공고 목록의 "내 상태"(4차)와 지원 현황의 상태(8차)는 같은 공고인데 시안의 값이 서로 다르다. 가짜 서버는 8차 값을 기준으로 내 공고 행 하나(`mocks/user-postings.ts`)에 두고, 그룹 공고의 내 상태(지원함일 때만 글자를 싣는다), 내 공고와 지원 현황, 메일 확인함의 반영이 모두 이것을 읽고 쓴다(2026-11-15). 서버의 `user_postings` 하나에서 읽는 것과 같은 모양이다(공고 문서 3절과 공고 문서 5.3). 그래서 지원 현황에서 바꾸면 그룹 공고 목록에도 보인다. 그룹 공고 목록의 내 상태는 4차 시안과 다르다(예시 물류는 4차의 "지원함" 대신 보류라 상태가 없고, 예시 핀테크는 "지원함"이다). 메일 확인함의 두 메일은 8차 상태에서 이미 반영된 값이라, 반영하면 바뀌도록 예시 보안의 2차 면접 안내와 예시 핀테크의 서류 결과로 고쳤다. 메일의 "바뀌기 전"은 지금 내 공고의 상태를 읽는다.
- 예시 숫자가 시안끼리 다른 곳은 데이터에서 센 값을 보인다. 홈의 "메일에서 온 변경"은 시안의 1건 대신 메일 확인함과 같은 2건이고, 탈퇴의 경험카드 수는 시안의 7장 대신 카드 목록과 같은 6장이다.
