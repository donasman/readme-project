지금 상태(2026-11-13): 4절의 API 10개를 서버에 모두 만들었다(`com.readme.grouppost`, `com.readme.posting`). 프런트는 그룹 공고 목록·상세가 있고 가짜 서버를 부른다. 2026-11-15에 내 공고의 목록, 상세, 메모와 공고 고치기, 홈의 그룹 소식을 더해 15개다(4.2, 4.5). 같은 날 그룹 없이 내 공고에 넣기(`POST /api/me/postings`)를 더했다(4.2). 2026-11-16에 공고 분석(필수·우대·업무·키워드·자소서 문항, LLM)을 더했다. 올리거나 넣으면 커밋 뒤 공고마다 한 번 돌고, 두 상세가 `analysis`로 보여 준다(4.7).

| 테이블 | 내용 |
|---|---|
| `postings` | 공고 본체. 회사명, 공고명, 마감, 지원처, 원문 주소, 공고 내용 묶음. (2026-11-16) 공고 분석(V9) |

### 3.1 생성 SQL

`V3__groups.sql`의 뒷부분이다. 앞부분(그룹 테이블 3개)은 그룹 문서 3.1에 있고, 아래 테이블이 그 테이블을 가리킨다. 아래는 마이그레이션 파일과 글자가 같다. 고칠 일이 생기면 마이그레이션 파일이 원본이다.

```sql
-- 리드미 V3: 그룹 · 그룹 공고
set search_path to readme;

-- ── 공고 본체 ─────────────────────────────────────────────────────────
-- 그룹과 무관하게 공고 하나에 한 행. 같은 공고를 여러 그룹이 올리면 이 행을 함께 가리킨다.
create table postings (
  id              bigint generated always as identity primary key,
  posting_key     varchar(300) unique,           -- 같은 공고 판별 키(jobfit 공고키). 만들 수 없으면 null
  company         varchar(200) not null,
  title           varchar(300) not null,
  deadline_kind   varchar(10)  not null check (deadline_kind in ('DATE', 'ALWAYS', 'UNKNOWN')),
  deadline_date   date,
  deadline_name   varchar(50),                   -- 예: '서류 접수 마감'
  apply_at        varchar(100),                  -- 지원처. 예: '회사 채용 홈페이지'
  source_url      varchar(2000),
  sections        jsonb        not null default '[]'::jsonb,  -- 공고 내용 묶음 [{ "title": "주요 업무", "items": ["…"] }]
  created_by      bigint references users(id) on delete set null,
  deadline_set_by bigint references users(id) on delete set null,  -- "날짜 넣기"를 한 사람
  deadline_set_at timestamptz,
  created_at      timestamptz  not null default now(),
  updated_at      timestamptz  not null default now(),
  check ((deadline_kind = 'DATE') = (deadline_date is not null))
);

create table posting_keywords (
  posting_id bigint       not null references postings(id) on delete cascade,
  keyword    varchar(100) not null,              -- 키워드 사전의 대표 표기
  seq        integer      not null,              -- 화면에 보이는 순서
  primary key (posting_id, keyword)
);
create index posting_keywords_keyword_idx on posting_keywords (keyword);

-- ── 그룹 공고 (그룹 × 공고) ───────────────────────────────────────────
create table group_posts (
  group_id      bigint      not null references groups(id)   on delete cascade,
  posting_id    bigint      not null references postings(id) on delete cascade,
  posted_by     bigint references users(id) on delete set null,
  posted_at     timestamptz not null default now(),
  taken_down_at timestamptz,                     -- "그룹에서 내리기". 행은 남기고 목록에서만 뺀다
  taken_down_by bigint references users(id) on delete set null,
  primary key (group_id, posting_id)
);
create index group_posts_posting_idx on group_posts (posting_id);

-- 관심은 그룹별로 기록한다. 멤버 행에 묶여 있어, 그룹을 나가면 그 그룹의 관심이 함께 지워진다.
create table group_post_interests (
  group_id   bigint      not null,
  posting_id bigint      not null,
  user_id    bigint      not null,
  created_at timestamptz not null default now(),
  primary key (group_id, posting_id, user_id),
  foreign key (group_id, posting_id) references group_posts (group_id, posting_id) on delete cascade,
  foreign key (group_id, user_id)    references group_members (group_id, user_id)  on delete cascade
);
create index group_post_interests_member_idx on group_post_interests (group_id, user_id);

-- 댓글은 "그룹 × 공고"에 달린다. 쓴 사람이 그룹을 나가거나 탈퇴해도 댓글은 남는다.
create table group_post_comments (
  id         bigint generated always as identity primary key,
  group_id   bigint        not null,
  posting_id bigint        not null,
  author_id  bigint references users(id) on delete set null,
  body       varchar(2000) not null,             -- 글자 그대로. 링크는 응답을 만들 때 나눈다
  created_at timestamptz   not null default now(),
  updated_at timestamptz   not null default now(),
  foreign key (group_id, posting_id) references group_posts (group_id, posting_id) on delete cascade
);
create index group_post_comments_post_idx on group_post_comments (group_id, posting_id, created_at);

-- ── 내 공고 (지원 상태의 원본) ────────────────────────────────────────
-- 사용자 × 공고에 한 행. 그룹에는 이 값이 공개 범위만큼만 보인다.
create table user_postings (
  user_id    bigint      not null references users(id)    on delete cascade,
  posting_id bigint      not null references postings(id) on delete cascade,
  decision   varchar(10) not null default 'UNDECIDED'
    check (decision in ('UNDECIDED', 'HOLD', 'SKIP', 'APPLIED')),               -- 미정, 보류, 지원안함, 지원함
  stage      varchar(12)
    check (stage in ('DOCUMENT', 'TEST', 'INTERVIEW_1', 'INTERVIEW_2', 'FINAL')), -- 서류, 필기, 1차 면접, 2차 면접, 최종
  result     varchar(12)
    check (result in ('IN_PROGRESS', 'PASSED', 'FAILED')),                       -- 진행 중, 합격, 불합격
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  primary key (user_id, posting_id),
  check ((decision = 'APPLIED') = (stage is not null)),   -- 단계와 결과는 지원함일 때만 있다
  check ((stage is null) = (result is null))
);
create index user_postings_posting_idx on user_postings (posting_id);
```

### 3.2 설계 이유

- **주소와 키가 같다.** `group_posts`의 키는 (그룹, 공고)다. API 주소 `/groups/{groupId}/posts/{postId}`의 두 값이 그대로 키라서 따로 찾을 것이 없다. `postId`는 공고 본체(`postings`)의 id다.
- **관심은 멤버 행에 묶었다.** `group_post_interests`가 (그룹, 사용자)로 `group_members`를 가리킨다. 멤버가 아닌 사람의 관심은 들어가지 않고, 그룹을 나가면 그 그룹의 관심이 함께 지워진다. 코드에서 따로 지울 필요가 없다.
- **댓글은 쓴 사람이 사라져도 남는다.** 나가기는 댓글에 영향이 없고, 탈퇴하면 `author_id`만 빈다.
- **지원 상태는 그룹이 아니라 사용자 × 공고에 둔다.** 정리 문서의 "지원 상태의 원본은 내 지원 관리의 값"을 그대로 옮겼다. 같은 공고가 두 그룹에 있어도 상태는 하나이고, 그룹마다 공개 범위만큼 보인다.
- **마감은 종류와 날짜 두 칸이다.** 화면의 세 경우(날짜, 상시, 확인 필요)를 `deadline_kind`로 구분하고, 날짜는 `DATE`일 때만 있도록 제약을 걸었다.

## 4. API

공통 규칙과 공통 오류 코드는 구조 문서 5절에 있다. 그룹 API와 같이, 모두 그 그룹의 멤버만 부를 수 있다(5.1).

### 4.1 그룹 공고 (11개)

| 메서드·주소 | 하는 일 | 비고 |
|---|---|---|
| `GET /api/groups/{groupId}/posts` | 그룹 공고 목록 | `{ today, posts }`. 내린 공고는 빼고 마감된 공고는 넣는다 |
| `POST /api/groups/{groupId}/posts` | 그룹에 공고 올리기 | 이미 그 그룹에 있으면 409 `ALREADY_IN_GROUP`과 `postId`. 내렸던 공고면 되살린다. (2026-11-15) 키워드와 공고 내용 묶음을 함께 받는다(4.5) |
| `GET /api/groups/{groupId}/posts/{postId}` | 그룹 공고 상세 | `{ today, post }`. 공고 내용, 키워드, 댓글이 더해진다. (2026-11-16) 공고 분석 `analysis`도 더해진다(4.7) |

만들면서 정한 것(2026-11-13). 초안이 정하지 않은 빈칸이다. 앞의 세 줄은 같은 날 확인을 받았다.

- (확인함) 내린 공고는 목록에서만이 아니라 상세, 관심 켜기·끄기, 댓글 달기·수정·삭제, 날짜 넣기에서도 404 `POST_NOT_FOUND`다. P4의 "목록에서만 뺀다"를 "행은 남기되 그룹 안에서는 없는 공고로 본다"로 읽었다. 다시 올리면 행이 되살아나 그대로 보인다.
- (확인함) 댓글 달기는 201 Created 로 답한다. 본문은 앞뒤 공백만 지우고 저장한다. 수정도 같다.
- (확인함) 마감된 공고에도 관심과 댓글을 받는다.

- 내린 공고를 다시 올리면 같은 행이 되살아나고, 올린 사람과 올린 날은 다시 올린 사람과 그날로 바뀐다. 그래서 "새 공고"로 보이고, 다시 올린 사람이 내릴 수 있다.
- 공고키가 300자(칸의 길이)를 넘는 아주 긴 주소는 키를 만들 수 없는 것으로 보고 `posting_key`를 비운다. 이런 공고는 같은 공고로 알아보지 못한다.
- 내리기와 댓글 삭제는 204 다. 이미 내린 공고를 다시 내리면 404 `POST_NOT_FOUND`다.
- (정함, 화면·API 대응 문서 3절 6번) 날짜 넣기의 본문은 올리기의 `deadline`과 같은 꼴이다. 날짜 `{ "kind": "date", "date": "2026-11-20" }`나 상시 `{ "kind": "always" }`를 받고, `unknown`이나 짝이 맞지 않는 본문은 400 `INVALID_INPUT`이다. 바뀐 마감을 같은 꼴로 돌려준다. 지난 날짜도 받는다(넣는 즉시 마감됨이 된다).
- 댓글 수정은 고친 `Comment`를 돌려준다. 그룹장도 남의 댓글은 고치지 못하고 지우기만 한다(5.1). 그 공고의 댓글이 아니면 404 `COMMENT_NOT_FOUND`다.

2026-11-14, 포니테일 진단(backend)에서 나온 것을 고쳤다.

- 원문 주소에 역슬래시(`\`)가 있으면 400 `INVALID_INPUT`이다. 브라우저는 `\`를 `/`로 읽어 앞쪽 호스트를 여는데(`https://evil.example\@www.saramin.co.kr/…`는 `evil.example`), 공고키는 뒤쪽 사이트의 공고키가 되어 다른 그룹의 같은 공고를 가로챌 수 있었다.
- 공고키의 사이트 규칙은 호스트가 그 사이트이거나 하위 도메인일 때만 맞는다(`saramin.co.kr`, `www.saramin.co.kr`, `m.saramin.co.kr`는 사람인, `fakesaramin.co.kr`는 아니다). jobfit 공고키(P3)와 다른 점이다. 진짜 사이트 주소의 키는 jobfit과 같다(10절).
- 링크 없는 공고에 날짜를 넣으면 공고키도 그 날짜로 다시 만든다. 그래서 날짜를 넣은 뒤 같은 회사명·공고명·마감일로 올리면 같은 공고(409 `ALREADY_IN_GROUP`)다. 그 키를 이미 다른 공고가 쓰고 있으면 옛 키를 둔다(두 공고는 따로 남는다). 상시를 넣을 때와 링크로 만든 키는 바뀌지 않는다.
- 댓글의 링크 조각은 주소에 쓰는 글자(RFC 3986)만 잡고, 문장부호(`.,;:!?`)나 닫는 괄호로 끝나지 않는다. `https://…/review에서`의 "에서", `(https://…/a).`의 ")."는 글자 조각이다. 경로에 한글이 그대로 든 주소는 한글 앞에서 끊긴다.
- (정함) 주소의 `#` 뒤가 `/`로 시작하면 공고키에 넣는다. 해시로 화면을 바꾸는 채용 사이트(`https://careers.x.co.kr/#/jobs/101`)는 `#` 뒤가 공고마다 다르기 때문이다. 이전에는 그 사이트의 공고가 모두 같은 키가 되어, 두 번째 공고가 409가 나거나 다른 그룹에서 첫 공고의 값으로 보였다.
  - 키는 `url:careers.x.co.kr#/jobs/101`처럼 된다. `#` 뒤도 경로처럼 끝의 `/`를 떼고 쿼리의 추적값을 뺀다.
  - `#/`뿐이면 첫 화면이라 넣지 않는다.
  - `/`로 시작하지 않는 `#` 뒤(문서 안의 위치 `#apply`, `#!/…`)는 지금처럼 뺀다.
  - 사이트 공고키(`wanted:123` 등)는 바뀌지 않는다.
  - jobfit 공고키(P3)와 다른 점이다(10절).

만들면서 채운 빈칸:

- 목록은 내 공고에 넣은 시각(`user_postings.created_at`)의 역순이다. 화면이 다시 정렬하므로 같은 마감일끼리의 순서만 이것을 따른다.

- `groups`는 그 공고가 올라가 있고 내리지 않은 내 그룹이다. 내가 들어간 순서로, `GET /api/groups`와 같다. 그룹을 나갔거나 그룹에서 내린 공고도 내 공고에는 남고, 그때 `groups`가 빈다.
- `groups`의 `postId`는 그 그룹 공고의 주소(`/groups/{groupId}/posts/{postId}`)에 쓰는 값이다. 서버에서는 공고 id와 같다(3.2의 "주소와 키가 같다"). 프런트의 `PostingGroup` 모양에 맞추려고 `mark`와 함께 싣는다.
- 상세의 `groupStates`는 `groups`와 같은 그룹들에 그 그룹에서의 내 관심, 그 그룹의 댓글 수, 내가 그 그룹에 정한 공개 범위를 붙인 것이다. 프런트의 `MyPostingDetail`이 `MyPosting`을 넓힌 꼴이라 상세에도 `groups`가 있다.
- 상세에는 `deadlineName`을 싣지 않는다. 프런트의 `MyPostingDetail`에 없다.
- 메모는 받은 글자 그대로 저장한다. 비었거나, 공백뿐이거나, `null`이면 `null`로 둔다(메모 지우기). 돌려줄 값이 없어 204다.
- 메모는 내 공고 행이 있을 때만 바꾼다. 상태 바꾸기는 내 그룹의 공고면 행을 만들지만, 메모는 상세 화면에서만 쓰므로 행을 만들지 않는다.
- 마감과 공고 내용 묶음의 응답 모양(`DeadlineResponse`, `PostSection`)은 그룹 공고와 같은 것을 쓴다. `grouppost`에서 `posting`으로 옮겨 `public`으로 열었다.

2026-11-15에 정한 것(그룹 없이 내 공고에 넣기, 화면·API 대응 문서 3절 11번). 넣기의 요청과 같은 공고 처리는 그 문서에서 정했고, 아래는 만들면서 채운 빈칸이다.

- 요청은 `POST /api/groups/{groupId}/posts`의 본문 그대로다(4.4). 서버도 같은 record(`posting/UploadRequest`)를 쓴다. `posting`이 `grouppost`를 부를 수 없으므로 올리기 본문과 마감(`DeadlineInput`)을 `grouppost`에서 `posting`으로 옮겨 `public`으로 열었다. 검사(필수 칸, 길이, 원문 주소, 마감의 짝, 키워드와 공고 내용 묶음(4.5))도 그대로 같다.
- (정함) 응답은 201과 상세(`GET /api/me/postings/{postingId}`)와 같은 `{ today, posting }`이다. 이유: 그룹에 올리기가 201과 상세와 같은 `{ today, post }`를 돌려주므로 같게 했다. 화면이 받은 값으로 바로 상세를 그릴 수 있다.
- (정함) 넣은 내 행은 미정(`undecided`, 단계·결과·메모 없음)으로 시작한다. 이유: 그룹 공고에서 관심을 켤 때 내 공고 행을 만드는 길(`UserPostings.addIfAbsent`)과 같은 상태다. 지원 상태는 상태 바꾸기로 따로 넣는다.
- (정함) 이미 내 공고에 있는 공고면 409 `ALREADY_IN_MY_POSTINGS`이고, 본문 맨 위 칸에 그 공고의 `postingId`가 온다. 내 행과 지원 상태, 메모는 그대로다. 이유: 그룹에 올리기의 409 `ALREADY_IN_GROUP`과 `postId`와 같은 꼴로, 프런트가 그 공고의 상세로 보낼 수 있다. 칸 이름은 내 공고의 주소(`/api/me/postings/{postingId}`)와 상태 바꾸기 응답의 `postingId`를 따랐다. 관심을 켜서나 상태를 넣어서 생긴 행도 이미 있는 것이다.
- 같은 공고는 그룹에 올리기와 같이 공고키로 알아본다(P3, `Postings.findOrCreate`). 있는 공고의 값(회사명, 마감 등)은 고치지 않고 처음 올린 사람이 넣은 값이 남는다(4.1). 그 공고가 내 그룹에 올라와 있으면 응답의 `groups`, `groupStates`에 그 그룹이 바로 보인다.
- 두 번 눌러도 내 행은 하나다. 공고키가 있는 공고 본체와 내 행을 조건이 붙은 native insert(`on conflict do nothing`)로 넣고, 내 행을 넣지 못했으면 409다. 유일 제약 위반으로 실패하지 않는다.
- 넣기는 어느 그룹에도 올리지 않는다. 그룹이 없으므로 멤버 확인(404)도 없다. 로그인하지 않았으면 401 `UNAUTHENTICATED`다.

| `FILE_UNREADABLE` | 422 | 새로(2026-11-15). 형식은 맞는데 읽지 못했다: 손상된 파일, 열람 암호가 걸린 PDF, 암호·배포용 한글 문서, DTD가 든 XML, 읽는 프로세스가 메모리(256MB)나 시간(30초)을 넘었다 |

### 4.5 만들면서 정한 것 (2026-11-15)

2026-11-15에 정한 것(9절의 세 결정, 화면·API 대응 문서 3절 14번, 목록의 원문 주소):

- **지원한 뒤 관심 끄기**: 상세에 끄기를 둔다. 서버는 전부터 지원 상태가 있어도 관심을 끈다(`PUT …/interest { "interested": false }`). 끄면 이 그룹의 관심 행만 지우고, 내 공고 행과 지원 상태는 그대로다(P7). 서버에서 고친 것은 없고 테스트로 확인했다(`GroupPostChangeTests`).
- **관심을 끈 그룹의 관심 멤버**: 내 화면에서도 관심 멤버에 나를 넣지 않는다. 다른 멤버가 보는 것과 같다. 서버는 전부터 `interests`에서 보는 사람을 빼고 `me`로 따로 준다(5.2). 그래서 서버에서 고친 것은 없다. 지원 상태가 있어도 `me.interested`가 `false`면 나를 넣지 않는 것은 프런트가 한다(8절 14번). 내 상태 알약에 쓰는 `me.status`는 그대로 준다.
- **공고 고치기**: 그 그룹에 공고를 올린 사람(`group_posts.posted_by`)이 `PUT /api/groups/{groupId}/posts/{postId}`로 회사명, 공고명, 마감을 고친다.
  - 본문은 `{ "company": "예시 커머스", "title": "백엔드 개발자 신입", "deadline": { "kind": "date", "date": "2026-11-30" } }`이다. 마감은 올리기의 `deadline`과 같은 꼴이고, 짝이 맞지 않으면(날짜 없는 `date`, 날짜 있는 `always`·`unknown`) 400 `INVALID_INPUT`이다.
  - `unknown`은 마감이 아직 `unknown`인 공고에만 받는다. 마감을 모르는 공고의 회사명만 고칠 때 없는 날짜를 지어 넣지 않게 했다. 마감이 있는 공고를 `unknown`으로 되돌리면 409 `DEADLINE_ALREADY_SET`이다(날짜 넣기를 다시 열지 않는다).
  - 회사명 200자, 공고명 300자(칸의 길이)로 올리기와 같게 검사하고, 앞뒤 공백을 지운다.
  - 응답은 올리기와 같은 `{ today, post }`다.
  - 공고 본체(`postings`)를 고치므로(P2) 같은 공고를 올린 다른 그룹에도 그대로 보인다.
  - 그래서 같은 공고가 다른 그룹에도 올라와 있고(내리지 않은) 그 그룹에 올린 사람이 내가 아니면 409 `POSTING_SHARED`다. 그 그룹에 올린 사람이 탈퇴해 비어 있어도 그렇다. 가입과 그룹 만들기가 열려 있어서, 남이 혼자인 그룹을 만들어 같은 링크를 올리면 그 그룹의 "올린 사람"이 되어 다른 그룹들이 보는 공고 본체를 고칠 수 있기 때문이다. 같은 공고를 올린 그룹이 모두 내가 올린 것이면(내가 두 그룹에 올렸으면) 고친다. 내린 그룹은 막지 않는다. 다시 올리면 고친 값이 보인다.
  - 살펴본 뒤 고치기 전에 다른 그룹에 같은 공고가 막 올라오면 고쳐진다. 두 사람이 같은 순간에 해야 생기므로 그대로 둔다.
  - 올린 사람이 아니면 그룹장도 403 `FORBIDDEN`이다. 멤버가 아니면 404 `GROUP_NOT_FOUND`, 내린 공고는 404 `POST_NOT_FOUND`다.
  - 원문 주소와 공고키는 고치지 않는다. 공고 본체는 주인인 `posting/Postings`의 `edit`으로만 고친다.
  - 날짜 넣기(P5)는 다른 멤버에게 그대로다. 마감을 읽지 못한 공고에만 한 번이다. 올린 사람의 고치기는 마감이 이미 있어도 언제든 날짜나 상시로 바꾼다.
  - 고치기는 조건이 붙은 native update 하나다(마감이 `unknown`일 때만 `unknown`을 넣는다). 그래서 같은 순간의 날짜 넣기를 `unknown`으로 덮지 않고, 공고키도 건드리지 않는다.
- **올리기의 키워드와 공고 내용 묶음**(화면·API 대응 문서 3절 8번): 올리기 본문에 `keywords: string[]`와 `sections: [{ title, items: string[] }]`를 더했다(4.4). 둘 다 넣지 않아도 된다. 그룹에 올리기와 내 공고 넣기(4.2)가 같은 본문(`posting/UploadRequest`)이라 둘 다 받는다. 칸 확인 화면이 보내는 `DraftSection`의 `from`은 받아도 버린다. 서버는 읽어 오기(4.6)의 결과를 들고 있지 않으므로 받은 값을 다시 검사한다.
  - (정함) 키워드는 사전의 대표 표기로 바꾸고(`keyword/KeywordDictionary`의 `normalize`), 사전에 없는 것은 뺀다. 이유: `posting_keywords`는 사전의 대표 표기를 담는 칸이고(3.1), 칸 확인 화면도 키워드를 "키워드 사전의 대표 표기로 뽑았습니다"로 보여 줄 뿐 손으로 넣는 칸이 없다. 사람이 치는 카드 태그(사전에 없으면 친 그대로 두고 검사가 경고한다)와 다르다. 빈 키워드도 뺀다. 바꾼 뒤 겹치면 처음 것만 두고, 남은 순서가 `seq`(1부터)다.
  - (정함) 묶음은 이름과 항목의 앞뒤 공백을 지우고, 빈 항목을 빼고, 항목이 없는 묶음을 뺀다. 이름이 비면 400 `INVALID_INPUT`이다. 같은 이름의 묶음은 그대로 둔다. 이유: 읽어 오기가 묶음을 만드는 규칙(항목이 없는 묶음은 넣지 않는다, 포지션마다 같은 머리가 되풀이될 수 있다)과 같고, 칸 확인 화면도 이렇게 보낸다.
  - (정함) 한도는 키워드 100개(하나 100자, `posting_keywords.keyword` 칸), 묶음 100개(이름 50자), 묶음의 이름과 항목을 모두 더해 50,000자다. 넘으면 400 `INVALID_INPUT`이다. 이유: 50,000자는 읽어 오기가 받는 본문의 한도(4.6)라 붙여넣은 글에서 읽은 묶음은 늘 들어간다. 항목의 수와 길이는 따로 막지 않고 이 합으로 막는다. 키워드 100개는 사전의 대표 표기(227개) 가운데 한 공고에 나올 만한 수를 넉넉히 잡았고, 묶음 100개는 머리 11종이 포지션마다 되풀이되는 공고(포지션 10개 × 머리 4개 = 40)도 들어가는 수다. 카드의 태그 30개처럼 개수를 넘으면 400인 것과 같다.
  - (정함) 같은 공고(공고키)가 이미 있으면 받은 키워드와 묶음은 넣지 않고 처음 올린 사람의 값을 둔다. 있는 공고의 묶음이 비어 있어도 채우지 않는다. 이유: 회사명·마감처럼 공고 본체의 값은 처음 올린 사람의 것이 남는다(4.1, `Postings.findOrCreate`). 빈 칸을 채우게 하면 남이 다른 그룹들이 보는 공고 본체를 바꾸는 길이 된다(공고 고치기의 `POSTING_SHARED`와 같은 이유).
  - 공고 본체를 새로 만들 때 같은 트랜잭션에서 `postings.sections`(jsonb)를 넣고 `posting_keywords`에 행을 넣는다. 쓰기는 주인인 `posting/Postings`에만 있다.
  - 올리기와 넣기의 응답이 상세 모양이라 저장된 묶음과 키워드가 바로 보인다. 그룹 공고 상세와 내 공고 상세가 같은 값을 읽는다.
  - 읽어 오기는 아직 키워드를 주지 않는다(4.6). 사전을 읽어 오기에 붙이면 그 결과를 그대로 보내면 된다.
- **홈의 그룹 소식**: `GET /api/me/group-activity`. 내 그룹에 최근 7일 동안 올라온 공고와 달린 댓글을 프런트의 `GroupNews` 모양으로 준다. 본 시각을 담는 칸이 없으므로 "마지막으로 본 뒤"가 아니라 늘 최근 7일이다.
- **목록의 원문 주소**: 목록의 줄에 `sourceUrl`(없으면 `null`)을 싣는다. 목록에서 여는 마감일 넣기 창이 "원문 열기" 링크를 보여야 해서다. 상세의 `sourceUrl`은 전처럼 같은 값이다(8절 28번).

만들면서 채운 빈칸:

- 7일은 한국 날짜로 오늘과 그 앞 7일이다(오늘이 11-13이면 11-06 00:00부터). 프런트의 "올린 지 3일 이내"(새 공고), "7일 안에 마감"과 같은 셈이다. 본 소식도 7일 동안 다시 보인다.
- 새 공고는 그룹마다 한 줄 "새 공고 2건"이고 `postId`는 `null`이다. 시안의 "그룹별 새 공고 수"다. 마감된 공고도 센다(목록의 "새 공고" 표시는 마감된 공고를 빼므로 다를 수 있다).
- 댓글은 공고 × 쓴 사람마다 한 줄 "나래 님이 예시 공사 공고에 댓글을 남겼습니다"이고 `postId`는 그 공고다. 같은 사람이 같은 공고에 여러 번 달아도 한 줄이다.
- 최근 것부터 20줄까지 준다. 새 공고 줄의 시각은 그 그룹에서 가장 늦게 올린 공고의 시각, 댓글 줄의 시각은 마지막 댓글의 시각이다.
- 넣지 않는 것: 내린 공고와 그 댓글, 내가 없는 그룹(같은 공고를 함께 쓰는 남의 그룹의 댓글 포함), 내가 올린 공고, 내가 쓴 댓글, 탈퇴한 사람의 댓글.
- 소식에는 그룹(id, 이름, 표시 글자), 글자, 공고 id만 싣는다. 댓글 본문과 지원 상태는 싣지 않으므로 공개 범위(5.2) 밖의 값이 나가지 않는다.
- 응답은 목록 그대로(`[…]`)다. `GET /api/groups`와 같다.
- 내린 공고를 다시 올리면 올린 날이 바뀌므로(4.1) 새 공고로 센다.
- 링크 없는 공고(`local:` 키)를 고쳐도 공고키는 고치기 전의 회사명·공고명·마감일로 만든 그대로다. 그래서 고친 값으로 다시 올리면 다른 공고가 된다(고치기 전 값으로 올리면 같은 공고다). 코드에 `shortcut:`으로 적었다.

### 4.6 공고 읽어 오기 (1개)

| 메서드·주소 | 하는 일 | 비고 |
|---|---|---|
| `POST /api/postings/read` | 링크, 붙여넣은 본문, 파일에서 올리기의 칸을 규칙으로 읽는다 | JSON `{ url }`이나 `{ text, sourceUrl }`, 또는 multipart의 `file`(PDF, DOCX, HWPX, HWP · 20MB, 2026-11-15) 가운데 하나에 `groupId`를 더할 수 있다. 읽은 결과는 서버에 두지 않는다. 화면·API 대응 문서 3절 7번·9번(2026-11-15 정함). 규칙으로 못 읽은 필수 칸은 LLM으로 채운다(2026-11-16, 아래 4.6의 LLM 보완). 글자가 없는 파일을 LLM으로 읽는 것은 다음 작업이다 |

요청:

```json
{ "url": "https://www.saramin.co.kr/zf_user/jobs/view?rec_idx=10000001", "groupId": 1 }
```

```json
{ "text": "[(주)예시랩] 백엔드 개발자\n마감일 : ~11/20(목) 23:59\n담당 업무\n- 주문 API 개발", "sourceUrl": "", "groupId": 1 }
```

파일(2026-11-15)은 같은 주소에 `multipart/form-data`로 보낸다. 자료 올리기(`POST /api/card-sources`)와 같은 꼴이다. `groupId`는 폼 칸이고 넣지 않아도 된다.

```
POST /api/postings/read
Content-Type: multipart/form-data; boundary=…

file:    채용공고.pdf (PDF, DOCX, HWPX, HWP · 20MB까지)
groupId: 1
```

파일의 응답은 같은 글을 붙여넣었을 때와 같다. 원문 링크가 없어 `sourceUrl`은 `""`이고 `unread`에 있으며, `duplicate`는 오지 않는다.

응답(200). jobfit의 사람인 합성 픽스처를 읽은 값이다:

```json
{
  "company": "예시랩",
  "title": "백엔드 (Backend) 개발자",
  "deadline": { "kind": "date", "date": "2026-10-27" },
  "deadlineName": "",
  "applyAt": "",
  "sourceUrl": "https://www.saramin.co.kr/zf_user/jobs/view?rec_idx=10000001",
  "evidence": {
    "company": "[(주)예시랩] 백엔드 (Backend) 개발자(D-7) - 사람인",
    "title": "[(주)예시랩] 백엔드 (Backend) 개발자(D-7) - 사람인",
    "deadline": "마감일 2026.10.27 23:59"
  },
  "unread": ["deadlineName", "applyAt"],
  "sections": [
    { "title": "회사 소개", "items": ["예시랩은 제조 현장의 센서 데이터를 다루는 가상의 회사입니다."], "from": "회사 소개" },
    { "title": "모집 부문", "items": ["백엔드 (Backend) 개발자"], "from": "모집부문" },
    { "title": "주요 업무", "items": ["Python 기반 RESTful API 및 서비스 서버 개발", "…"], "from": "담당 업무" },
    { "title": "필수 요건", "items": ["주요 언어 : Python / Java 중 1개 이상", "…"], "from": "필요 스택" },
    "… 필수 요건(필수 경험과 역량), 우대 사항, 전형 절차, 근무 조건, 접수 방법"
  ],
  "keywords": ["데이터베이스", "Java", "Python", "배포", "Docker", "Git", "Kotlin", "MongoDB", "PostgreSQL", "REST API", "SQL", "Spring Boot", "백엔드", "서버 개발", "성능 최적화"],
  "source": { "title": "[(주)예시랩] 백엔드 (Backend) 개발자(D-7)", "text": "…메뉴를 걷어낸 요약 페이지와 상세요강의 글자…" }
}
```

이 값은 `postingread/PostingReaderTests`가 확인한다.

`groupId`를 넣었고 링크의 공고가 이미 그 그룹에 있으면 `duplicate`가 더해진다. 없으면 이 칸이 응답에 없다.

```json
"duplicate": { "postId": 12, "company": "예시 커머스", "title": "백엔드 개발자 신입", "postedBy": { "id": 2, "name": "가람" }, "postedAt": "2026-11-05" }
```

만들면서 정한 것(2026-11-15). 앞의 다섯 줄은 같은 날 정한 것을 옮겼다(화면·API 대응 문서 3절 7번·9번, 정리 문서 7절의 링크 처리와 필수값).

- (정함) 먼저 규칙으로 읽는다. jobfit의 필수값 읽기(`meta.py`)와 사이트별 규칙(`sites.py`)으로 읽고, 못 읽은 칸은 `unread`로 알린다.
- **정함(2026-11-16)** LLM 보완(`postingread/PostingFieldsByLlm`, 프롬프트 `resources/prompts/posting-fields.md`, `llm`의 `POSTING_FIELDS`, effort low):
  - 규칙이 필수 칸(회사명, 공고명, 마감) 가운데 하나라도 못 읽었을 때만 부른다. 다 읽었으면 LLM을 부르지 않는다(돈이 들지 않는다).
  - 부를 때는 마감의 이름(`deadlineName`)과 지원처(`applyAt`)도 함께 묻는다. 규칙은 이 둘을 읽지 않는다.
  - 규칙이 읽은 칸은 바꾸지 않는다. 읽지 못한 칸만 채우고 `unread`에서 뺀다.
  - 원문(페이지 제목과 글)의 앞 8,000자만 보낸다. 필수 칸은 대개 앞에 있고, 50,000자를 다 보내면 한 번에 0.3달러쯤 든다. 연도가 없는 마감을 맞추려고 오늘 날짜(서울)를 함께 보낸다.
  - 근거(`evidence`)는 LLM이 준 조각이 원문에 글자 그대로 있을 때만 싣는다. 값이 올리기의 칸 길이(회사명 200, 공고명 300, 마감 이름 50, 지원처 100)를 넘거나 마감 날짜가 `YYYY-MM-DD`가 아니면 그 칸은 읽지 못한 채로 둔다.
  - 사용액은 읽는 사람에게 넣는다. 한 달 한도에 닿았거나 LLM이 실패하면(키 없음, API 오류, 거절) 오류를 내지 않고 규칙으로 읽은 결과를 그대로 돌려준다(2026-11-16 사용자 결정). 응답 모양은 그대로다.
  - 링크의 공고가 이미 그룹에 있어 받지 않은 경우(`duplicate`)는 원문이 없어 부르지 않는다.
- (정함) 필수 칸은 회사명, 공고명, 마감(날짜나 상시)이다. 원문 링크는 있으면 넣는다. 올리기는 지금처럼 마감 `unknown`도 받는다. 날짜 넣기(P5)가 그것에 기대고, 칸 확인 화면에 "모름"이 있다.
- (정함) 읽은 결과는 서버에 두지 않는다. 프런트가 올리기 전까지 들고 있다. 테이블을 더하지 않았다.
- (정함) `groupId`를 넣으면 먼저 멤버인지 본다(아니면 404 `GROUP_NOT_FOUND`). 링크(본문이면 `sourceUrl`)의 공고키(`posting/PostingKeys`)로 그 그룹에 내리지 않은 같은 공고가 있으면 `duplicate`를 싣는다. 올릴 때의 409 `ALREADY_IN_GROUP`은 그대로다. 둘이 같이 올릴 수 있다.
- (정함) 링크는 사용자가 준 페이지 한 장만 받는다. 아래 "링크 받기"에 있다.
- 같은 공고가 링크로 확인되면 그 페이지를 받지 않는다. 칸은 비고(`sourceUrl`만 있다) `duplicate`만 뜻이 있다. 이미 그룹에 있는 공고를 다시 받지 않으려는 것이다. 본문이면 읽은 칸과 `duplicate`를 함께 준다. 링크 없는 본문은 같은 공고를 알아보지 않는다(올릴 때 회사명·공고명·마감으로 알아본다).
- 읽어 오기는 로그인한 사람이면 `groupId` 없이도 부를 수 있다. 그룹 없이 내 공고에 넣기(화면·API 대응 3절 11번)가 같은 읽기를 쓴다.
- 입력 검사(400 `INVALID_INPUT`): `url`과 `text` 가운데 꼭 하나다. 빈칸만 있는 본문은 없는 것으로 본다. `sourceUrl`은 `text`와 함께만 받는다. 주소는 올리기의 원문 주소와 같은 규칙이다(http·https만, 공백과 역슬래시 없이, 2,000자). 본문은 50,000자까지다.
- `unread`는 올리기의 칸 `company`, `title`, `deadline`, `deadlineName`, `applyAt`, `sourceUrl` 가운데 빈 것이다. 마감은 `unknown`이면 읽지 못한 것이다. `deadlineName`과 `applyAt`은 규칙으로 읽지 않아 늘 들어 있다(지원처 읽기 `channel.py`는 아직 옮기지 않았다). 못 읽은 칸의 값은 `""`다.
- `evidence`는 읽은 칸만, 그 값을 읽은 원문 조각 그대로다: 페이지 제목(og:title이 먼저), JSON-LD의 값, 요약 칸의 "키 값"(`마감일 2026.10.27 23:59`), 붙여넣은 글의 첫 줄.
- 붙여넣은 본문: 첫 줄이 `[회사] 공고명` 꼴이면 회사명과 공고명으로 읽는다. 사람인 제목과 같은 규칙이고 jobfit은 붙여넣은 글에서 이 둘을 읽지 않는다. 마감은 요약 칸(마감일, 접수마감, 접수기간)에서 읽는다. 본문이 없어 보여도 막지 않는다. 사용자가 본문이라고 준 것이다(jobfit과 같다).
- 링크: 사이트 규칙대로 요약 페이지를 받고, 거기에 공고 본문이 없을 때만 같은 공고의 상세요강(사람인·잡코리아)이나 같은 호스트 iframe 하나를 더 받는다. 본문은 jobfit의 판정을 쓴다(짧은 줄에 섹션 머리 묶음이 둘 이상, 그중 자격요건이나 주요업무). 둘 다 본문이 없으면 422 `FETCH_FAILED`다. 상세요강을 받지 못하면 그 이유가 오류가 된다.
- 마감 글자: 상시·수시·채용 시 마감은 `always`, 미정·협의는 `unknown`이다. 연도 없는 날짜("~11/20(목) 23:59")는 서버의 오늘(서울)에서 앞뒤 6개월 안의 해로 읽는다. 12월에 읽은 "1/5"는 다음 해, 1월에 읽은 "12/28"은 지난해다. 그 해가 평년이면 "2/29"는 읽지 못한 것이다. 기간이면 물결표 뒤를 읽는다. 전각 글자는 NFKC로 바꿔 읽는다. JSON-LD의 마감(`validThrough`)에 시간대가 붙어 있으면 서울 날짜로 바꾼다.
- `sections`의 `title`은 화면의 묶음 이름이다. jobfit의 섹션 이름을 띄어 쓰고 자격요건은 "필수 요건"으로 한다(예시 데이터와 같다): 모집 부문, 주요 업무, 필수 요건, 우대 사항, 인재상, 자기소개서, 전형 절차, 근무 조건, 복리후생, 회사 소개, 접수 방법. `from`은 원문의 머리 줄이다. 머리 없는 앞부분과 항목이 없는 묶음은 넣지 않는다(`source.text`에는 있다). 항목 앞의 글머리(`-`, `ㆍ`, `•` 등)는 뗀다. `※`는 둔다.
- (정함) `keywords`는 키워드 사전(`keyword/KeywordDictionary.find`, jobfit `keywords.py`의 `find`)이 글에서 찾은 대표 표기다(k8s → Kubernetes). 규칙만 쓴다. 영문 표기는 앞뒤가 영문·숫자가 아닐 때만 맞고(Java ≠ JavaScript, JS ≠ Node.js, C ≠ C# ≠ C++), 바로 뒤의 한글 조사는 막지 않는다("Java를"). 한 글자 표기(C)만 한글이 붙으면 뺀다("C언어"). 한글 표기는 글자 그대로 찾는다. 대소문자를 가리지 않고, 긴 표기부터 찾아 그 자리를 가려 "Spring Boot" 안의 "Spring", "자바스크립트" 안의 "자바"를 따로 세지 않는다. 요건을 LLM으로 분석해 키워드를 고르는 것은 다음 작업이다(화면·API 대응 문서 3절 13번). (2026-11-16) 공고 분석은 올리거나 넣은 뒤에 돌고 상세의 `analysis`에 따로 담긴다(4.7). 읽어 오기의 키워드는 그대로 규칙으로 찾는다.
- (정함) 찾는 글은 주요 업무, 필수 요건, 우대 사항 섹션이다. 셋 다 없거나 셋 모두 내용이 비었으면 섹션을 나눈 글 전체(붙여넣은 글, 링크면 본문이 있는 페이지)에서 찾는다. 내용이 빈 섹션은 머리 줄만 있는 것("…경험\n우대 사항")과, 짧은 줄이라 내용째 머리 줄로 읽힌 것("주요 업무 Java 로 API 개발")이다. 이유: jobfit은 페이지 글자 전체에서 찾지만 그 목록을 LLM에 힌트로만 줬다. 리드미는 칸 확인 화면에 그대로 보이므로 회사 소개, 복리후생, 자소서 문항, 페이지의 다른 공고 목록의 낱말이 섞이면 안 된다. jobfit의 실측 사람인 상세요강을 전체에서 찾으면 회사 소개의 AI가 18번으로 맨 앞이었다. 헤더 없이 붙여넣은 글은 전체에서 찾는다(jobfit의 `_order`도 요건 섹션이 없으면 머리를 요건 자리에 둔다).
- (정함) 순서는 많이 나온 순이고, 같으면 대표 표기의 글자 순이다(영문이 한글보다 앞). jobfit `find`의 순서 그대로다. 이유: 여러 섹션에 되풀이된 낱말이 그 공고의 중심이고, jobfit과 같은 값이어야 옮긴 테스트와 `python -I` 값으로 확인할 수 있다. 처음 나온 순은 jobfit에 없는 규칙이다.
- (정함) 15개까지다. 이유: jobfit의 공고 분석이 공고마다 남기는 키워드 수(`analyze.py`의 `LIST_LIMITS`)와 같다. 위 예시(사람인 합성 픽스처)는 18개를 찾아 한 번씩 나온 것 가운데 글자 순으로 뒤인 센서 데이터, 자동화, 테스트가 잘렸다.
- (정함) 직무 이름(백엔드, 서버 개발 등)도 사전 낱말이라 그대로 둔다. jobfit도 키워드를 찾을 때는 두고, 카드와 맞출 때(`match.py`의 `ROLE_WORDS`) 뺀다. 맞는 카드(화면·API 대응 문서 3절 13번)를 옮길 때 같이 뺀다.
- 같은 공고라 페이지를 받지 않은 응답(`duplicate`)의 `keywords`는 `[]`다.
- 속도: 표기(약 600개)마다 정규식을 글 전체에 돌리면 5만 자에 0.8초, 1MB에 15초 걸렸다. 대소문자를 접은 글에서 그 표기가 나온 자리(`indexOf`)에서만 정규식을 맞춰 본다. 5만 자에 20ms, 1MB에 0.3초이고 모든 표기가 든 글도 같다. 찾은 자리를 가릴 때 jobfit은 글을 다시 만들어(찾은 수 × 글 길이) 같은 낱말이 많은 긴 글에서 제곱이 되는데, 리드미는 찾은 글자만 공백으로 바꾼다. 찾은 자리는 시작·끝 정수 둘로만 들고 있다(`MatchResult`로 들면 1MB의 "c c c …"에 95MB, "깃"×100만에 217MB였고, 지금은 `find` 전체가 10MB, 21MB다). 결과는 jobfit과 같다(10절).
- 오류 코드 둘(`FETCH_BLOCKED`, `FETCH_FAILED`)은 422다. 서버의 고장이 아니라 그 링크의 사정이고, 사용자가 할 일은 본문 붙여넣기다. 502로 하면 서버 오류처럼 보여 프런트가 다시 시도하게 된다. 메시지는 이유마다 다르게 싣는다(4.3).

링크 받기(2026-11-15, 정리 문서 7절의 링크 처리):

- 사용자가 준 페이지 한 장과, 위의 경우 같은 공고의 상세요강 한 장만 받는다. 다른 링크를 따라가지 않고, 미리 받거나 다시 받지 않는다.
- User-Agent는 `ReadmeFetcher/1.0 (+<연락처>)`이다. 연락처는 `app.posting-read.contact`이고, 운영은 환경 변수 `FETCHER_CONTACT`로 꼭 넣는다(없으면 서버가 뜨지 않는다). 개발은 비워 두면 프런트 주소를 쓴다. 프런트 주소는 로그인 화면이라 사이트 운영자가 연락할 수 없으므로, 출시 전에 로그인 없이 열리는 공개 페이지나 실제로 받는 `mailto:` 주소를 넣는다. 로그인, 쿠키, 프록시, 캡차·차단 우회는 쓰지 않는다.
- Referer는 사람인·잡코리아에서 사용자가 준 주소를 보낸다. 주소에 한글 같은 ASCII 밖의 글자가 있으면(검색어 `searchword=백엔드`) 보내지 않는다. HTTP 머리 값이 될 수 없어서다.
- 서버 한 대에서 한 번에 읽는 링크는 셋까지다. 넷째는 기다리지 않고 422 `FETCH_FAILED`("지금 읽고 있는 링크가 많습니다…")다. 큰 페이지를 읽은 문서가 메모리를 많이 쓰고(1MB의 빈 태그만으로 문서 하나에 약 55MB), 느린 사이트가 요청 스레드를 오래 잡기 때문이다. 한 페이지는 한 번만 읽어 글자, 필수값, iframe을 모두 그 문서에서 찾고, 상세요강을 읽기 전에 버린다. 이 수도 서버 한 대의 메모리에만 있다.
- 받는 페이지마다 그 사이트의 robots.txt를 따른다(RFC 9309, 10절). robots.txt가 4xx면 없는 것으로 보고 받는다. 5xx나 연결 실패면 받지 않는다(422 `FETCH_FAILED`). 사이트마다 한 시간 기억한다.
- 같은 호스트에는 1초에 하나만 보낸다. 5초 넘게 기다려야 하면 받지 않는다(422 `FETCH_FAILED`). robots.txt 기억과 간격은 서버 한 대의 메모리에만 있다. 서버를 여러 대 띄우면 공유 저장소로 옮긴다.
- 주소 검사(SSRF): http·https만, 사용자 정보(`user:pass@`) 없이 받는다. 호스트 이름을 풀어 나온 주소가 하나라도 루프백, 사설망, 링크 로컬(169.254.169.254), 통신사 NAT(100.64.0.0/10), 멀티캐스트, 지정 안 됨, 예약 대역, IPv6 고유 로컬이거나 이런 IPv4를 품은 IPv6(매핑, 호환, NAT64, 6to4)면 받지 않는다(422 `FETCH_FAILED`, "읽을 수 없는 주소입니다"). 넘어가라는 응답(redirect)은 직접 따라가며 세 번까지, 넘어갈 때마다 주소 검사와 robots.txt를 다시 한다. 주소 검사는 같은 호스트의 차례를 기다린 뒤, 보내기 바로 앞에 한다. 기다리기 앞에 검사하면 기다리는 몇 초 사이에 이름이 메타데이터 주소로 바뀔 수 있었다(2026-11-15 고침).
- 연결 5초, 응답 전체 10초, 본문 1MB까지 받는다(jobfit의 실측 페이지 가운데 가장 큰 것이 470KB다). HttpClient의 시간 한도는 응답 머리까지만 보므로, 머리를 보낸 뒤 본문을 늦게 보내는 사이트는 연결과 응답을 더한 전체 한도(15초)가 끊는다. `text/html`과 `application/xhtml+xml`만 받는다. 인코딩은 응답 머리의 charset → 앞 4KB의 meta charset → UTF-8 → CP949 순으로 오류 없이 풀리는 것을 쓴다(jobfit과 같다).
- 받은 본문은 기록하지 않는다. 실패하면 호스트와 이유만 남긴다.
- 남은 틈: 주소를 검사하고 몇 밀리초 뒤 HttpClient가 이름을 다시 푼다. 그 조회는 대개 JVM이 30초 동안 기억한 답(`networkaddress.cache.ttl` 기본값), 곧 검사한 주소를 받는다. 앞선 조회로 생긴 기억이 바로 그 몇 밀리초 안에 끝나면 HttpClient가 새로 묻고, 그때 이름이 사설 주소로 바뀌어 있으면(DNS rebinding) 막지 못한다. 공격자는 이 순간을 맞히려 되풀이해 볼 수 있다. 닫으려면 검사한 주소로 바로 연결하거나, 나가는 요청을 공개 주소로만 보내는 프록시·방화벽을 둔다. AWS에서는 인스턴스 메타데이터를 IMDSv2만 받게 하고(토큰 필수, hop limit 1) 169.254.169.254로 나가는 요청을 막는다. GET만 보내는 이 요청으로는 IMDSv2 토큰을 받을 수 없다. 배포에서 `networkaddress.cache.ttl`을 0으로 두지 않는다.
- 정규식: jobfit의 정규식 가운데 공백(`\s*`)으로 시작하는 다섯(회사명의 영문 괄호, 공고명의 D-day, 제목 끝의 사이트 이름 둘, 괄호 머리의 닫는 괄호)은 긴 공백 줄에서 공백 수의 제곱만큼 걸렸다(공백 4만 칸에 몇 초, JSON-LD 의 1MB 회사명이면 한 시간쯤). 찾기를 시작한 자리이거나 바로 앞이 공백이 아닌 자리에서만 맞추기 시작하게 고쳤다. 결과는 같다. JSON-LD의 회사명·공고명은 칸의 길이(200자, 300자)를 넘으면 읽지 않고, 글머리를 뗀 줄이 60자를 넘으면 괄호 머리를 찾지 않고 내용으로 본다(2026-11-15).
- 테스트는 내 PC에 띄운 사이트(127.0.0.1)를 읽으므로 루프백만 허용하는 설정 `app.posting-read.allow-loopback-for-tests`를 test 프로필에만 켠다(구조 문서 8절).

파일 읽기(2026-11-15, 화면·API 대응 문서 3절 7번의 "PDF, DOCX, HWPX, HWP · 20MB"):

- (정함) 같은 주소가 `multipart/form-data`의 `file` 칸 하나로 받는다. 이유: 자료 올리기(경험카드 4.2)가 같은 주소에서 `Content-Type`으로 파일과 JSON을 나누고 프런트의 `request`도 `FormData`를 그대로 보낸다. 주소를 하나 더 만들 까닭이 없다.
- (정함) 파일의 글은 자료 올리기의 코드로 읽는다(`extraction/UploadedFiles.documentText`): 형식을 확장자가 아니라 내용으로 알아내고, PDF·HWP는 서버와 다른 프로세스(힙 256MB, 30초)에서, DOCX·HWPX는 zip·XML 상한(항목 10,000개, 푼 크기 100MB, DTD 거부)을 두고 읽고, 같은 규칙으로 다듬는다(경험카드 4.4). 이유: 사용자가 올린 파일을 믿지 않는 방어(압축 폭탄, XXE, 메모리)가 거기 다 있다. 따로 만들면 같은 방어를 두 번 지켜야 한다.
- (정함) 동시에 읽는 파일 수(2개)는 자료 올리기와 함께 센다. 세마포어 하나(`UploadedFiles`)를 둘이 나눠 쓴다. 이유: 파일 하나를 읽는 데 메모리가 수십~수백 MB 들고(PDF·HWP는 256MB 힙의 프로세스), 배포의 메모리 계산은 그런 프로세스가 서버 한 대에 둘까지 뜬다고 본다(경험카드 4.4, `readme-api.service`). 기능마다 따로 세면 넷이 된다. 차례를 기다리는 것도 자료 올리기와 같다(링크 읽기처럼 바로 거절하지 않는다). 파일은 이미 다 받았고 읽기는 30초를 넘지 않는다.
- (정함) 원문 링크(`sourceUrl`)는 파일과 함께 받지 않는다. 이유: 프런트의 파일 입력(`PostReadInput`의 `kind: "file"`)에 원문 링크 칸이 없고, 정리 문서 7절도 원본 URL은 "붙여넣기와 파일에는 없을 수 있다"고 했다. 칸 확인 화면에서 넣는다. 그래서 파일에는 `duplicate`가 없다. 같은 공고는 올릴 때 409 `ALREADY_IN_GROUP`으로 안다(링크 없는 본문과 같다). `groupId`는 멤버 확인에만 쓴다. 멤버가 아니면 파일을 읽기 전에 404 `GROUP_NOT_FOUND`다.
- (정함) 읽은 글은 붙여넣은 본문과 같은 길(`PostingReader.fromText`)로 읽는다. 그래서 응답이 같은 글을 붙여넣었을 때와 같다. 원문 제목(`source.title`)과 회사명·공고명의 근거도 붙여넣은 본문처럼 첫 줄이다. 파일 이름을 쓰지 않은 이유: 공고 파일의 첫 줄은 대개 공고 제목이고, 파일 이름은 "공고문(최종).hwp"처럼 공고를 말하지 않는 것이 많다. 파일 이름은 응답에 싣지 않는다(프런트가 이미 안다).
- (정함) 받는 형식은 PDF, DOCX, HWPX, HWP다. 자료 올리기가 읽는 PPTX, TXT, MD는 415 `FILE_UNSUPPORTED_TYPE`이다. 사진은 자료 올리기처럼 글자가 없는 파일(422 `FILE_NO_TEXT`)로 본다. 이유: 3절 7번이 정한 넷만 받는다. 사진은 정리 문서 7절의 OCR 대체(LLM에 PDF와 이미지를 넣는다)가 붙으면 읽을 수 있는 쪽이다.
- (정함) 읽은 글은 붙여넣은 본문과 같은 5만 자(UTF-16 글자 수, `@Size`와 같은 셈)까지다. 넘으면 413 `FILE_TOO_LARGE`다. 이유: 같은 글을 붙여넣으면 받지 않는 길이를 파일로는 받으면 상한이 둘이 된다. 400 `INVALID_INPUT`이 아닌 것은 요청의 꼴이 아니라 파일 내용의 사정이라서다. 자료 올리기도 글이 상한을 넘으면 413이다.
- (정함) 오류 코드는 `FILE_` 넷을 새로 두었다(4.3). 자료 올리기의 `SOURCE_` 코드를 그대로 쓰지 않은 이유: 그 메시지는 자료 올리기의 것이라(받는 형식에 PPTX·TXT·MD, "곧 읽을 수 있게 할 예정", "100만 자까지") 여기서는 틀리고, 공고 읽어 오기의 오류는 `FETCH_`처럼 붙여넣기를 안내해야 한다. 짝은 `SOURCE_TOO_LARGE` → `FILE_TOO_LARGE`, `SOURCE_UNSUPPORTED_TYPE` → `FILE_UNSUPPORTED_TYPE`, `SOURCE_UNREADABLE` → `FILE_UNREADABLE`, `SOURCE_NO_TEXT`·`SOURCE_EMPTY` → `FILE_NO_TEXT`이고 HTTP 상태도 같다. 바꾸는 곳은 `PostingReadController`다. 그래서 `extraction`의 `ExtractionErrorCode`를 `public`으로 열었다(구조 문서 3절).
- (정함) 글자가 없는 파일은 지금 422 `FILE_NO_TEXT`로 붙여넣기를 안내한다. LLM으로 읽는 것(OCR 대체, 정리 문서 7절: Claude에 PDF를 그대로 넣는다)은 자료 올리기의 스캔본(남은 작업 5-8)과 함께 다음 작업이다. 그때 이 오류 대신 LLM이 읽는다. 못 읽은 칸 채우기는 2026-11-16에 들어갔다.
- 20MB를 넘는 파일: 실제 서버에서는 Tomcat의 multipart 제한(`max-file-size: 20MB`)이 먼저 걸린다. 자료 올리기처럼 이 컨트롤러도 그 오류(`MaxUploadSizeExceededException`)를 413 `FILE_TOO_LARGE`로 답한다. 서버 앞의 Caddy는 25MB를 넘는 요청을 본문 없는 413으로 끊는다(`code`가 없다, 경험카드 6절 7번).
- 원본 파일은 두지 않는다. 메모리에서 읽고 버린다(PDF·HWP는 읽는 프로세스에 넘기려고 잠깐 임시 파일에 쓰고 바로 지운다). 파일 이름과 내용은 기록하지 않는다(자료 올리기와 같다).

### 4.7 공고 분석 (2026-11-16)

API는 늘지 않았다. 그룹에 올리기와 내 공고 넣기가 분석을 시작하고, 두 상세가 결과를 싣는다. 남은 작업 6-2이고, 정리 문서 5절의 "공고당 1회"와 화면·API 대응 문서 3절 13번의 "공고 분석 결과를 담을 곳"이다.

- **정함(2026-11-16 사용자 결정) 언제 도는가**: 그룹에 올리거나(`POST /api/groups/{groupId}/posts`) 내 공고에 넣을 때(`POST /api/me/postings`) 그 공고에 분석이 없으면, 트랜잭션이 커밋된 뒤 뒤에서 한 번 돈다. 사용액은 올리거나 넣은 사람에게 든다. 그 사람이 이번 달 한도에 닿았으면 돌리지 않는다. 다음에 누가 올리거나 넣을 때 다시 본다. 실패해도 올리기·넣기의 응답(201)은 그대로다.
- **담는 것**: 필수 역량(`must`, 6개까지), 우대 역량(`nice`, 6개), 주요 업무(`duties`, 5개), 키워드(`keywords`, 15개), 자기소개서 문항(`questions`: `text`, `limit`). jobfit `analyze`의 칸과 개수(`LIST_LIMITS`)다. 한 줄 요약(`role_summary`)과 인재상(`values`)은 쓰는 화면이 없어 뺐다.
- **(정함) 저장**: `postings`에 칸 둘을 더했다(V9, 3.1). `analysis`(jsonb)에 위의 다섯을 통째로 둔다. 이유: 분석은 공고 본체의 것이고(P2) 공고마다 하나다. 화면은 통째로 읽기만 한다. 테이블을 따로 두면 공고마다 한 행인 테이블이 하나 더 생길 뿐이다.
- **(정함) 올리기의 묶음·키워드와 따로 둔다**: `sections`와 `posting_keywords`는 그대로 두고 `analysis`를 따로 싣는다. 빈 묶음을 분석으로 채우지 않는다. 이유는 셋이다.
  - 묶음은 원문의 줄을 그대로 옮긴 것이고 분석은 LLM이 줄인 명사구다. 섞으면 어느 것이 원문인지 알 수 없다.
  - 원문은 저장하지 않으므로(4.6) 분석에 보내는 글이 곧 묶음이다. 묶음이 비면 분석할 글도 없어 "빈 묶음 채우기"는 생기지 않는다.
  - 분석의 키워드는 사전에 없는 낱말도 둔다(jobfit의 `normalize`). `posting_keywords`는 사전의 대표 표기만 담는다(4.5). 맞는 카드(화면·API 대응 3절 13번)는 둘을 함께 쓸 수 있다.
- **(정함) 보내는 글**: 회사명, 공고명, 공고 내용 묶음이다. 묶음은 jobfit의 섹션 우선순위대로 놓는다: 필수 요건, 주요 업무, 우대 사항, 자기소개서, 인재상, 모집 부문, 전형 절차, 근무 조건, 접수 방법, 회사 소개, 이름 모를 묶음, 복리후생. 2,500자(jobfit `POSTING_LIMIT`)까지 보낸다. 넘으면 낮은 묶음부터 통째로 빼고, 하나만 남아도 넘치면 자르고 " …(잘림)"을 붙인다. 담당자 이메일과 전화는 가린다(jobfit `mask_contacts`). 묶음이 없는 공고는 부르지 않는다.
  - 이유: jobfit이 쓴 값이다. 요건, 업무, 우대, 문항은 대개 이 안에 들어간다. 비용은 생각을 포함한 출력이 대부분이다. 한도는 실제 결과를 보고 다시 본다.
  - 이름 모를 묶음(칸 확인 화면에서 손으로 붙인 이름)은 jobfit의 머리(헤더 없는 본문) 자리다. 필수 요건도 주요 업무도 없으면 맨 앞이다(jobfit `_order`).
- **(정함) 프롬프트**: `resources/prompts/posting-analysis.md`. jobfit `analyze.md`의 규칙을 옮겼다. "내 경험 태그" 자리에 키워드 사전의 대표 표기 227개를 모두 싣는다. 그래서 누가 올려도 지시문이 같고 결과가 사용자에 기대지 않는다(정리 문서 5절). 지시문이 고정이라 나중에 프롬프트 캐시를 붙일 수 있다.
  - 사용자 글에는 사전이 묶음 글에서 찾은 키워드 20개(참고), `## 공고 — 회사명 / 공고명`, 묶음 글이 들어간다.
  - jobfit의 "스크립트가 찾은 문항 후보"는 넣지 않았다. 문항 찾기(`sections.py`의 `find_questions`)를 옮기지 않았다. 받은 문항은 원문과 대조해 거른다.
- **답 검사(jobfit `validate`)**:
  - 목록마다 앞뒤 공백을 지우고, 빈 것과 겹치는 것을 빼고, 개수를 넘으면 앞에서 자른다. 키워드는 사전의 대표 표기로 바꾸고 사전에 없으면 그대로 둔다.
  - 필수 역량과 주요 업무가 둘 다 비면 쓸 수 없는 답이다. 저장하지 않는다(사용액은 든다). 다음에 올리거나 넣을 때 다시 돈다.
  - 문항은 묶음 글 전체(줄이지도 가리지도 않은 것)에 그대로 있을 때만 둔다. 공백, 따옴표, 앞 번호 하나는 무시하고 NFKC로 맞춰 견준다. 6자보다 짧으면 버린다.
  - 글자 수는 그 문항 앞 30자, 뒤 60자 안에 그 숫자("800"이나 "1,000")가 있을 때만 둔다. 구조화 출력이라 글자 수는 숫자 칸이다. 없으면 0으로 받아 `null`로 둔다.
- **(정함) 같은 공고를 두 번 돌리지 않는다**: 시작할 때 `analysis_started_at`을 조건이 붙은 update로 잡는다. 분석이 없고, 돌고 있는 분석이 없거나 그것이 10분 넘게 끝나지 않았을 때만 잡힌다. 못 잡으면 돌리지 않는다. 끝나면(성공도 실패도) 놓는다. 저장도 분석이 아직 없을 때만 한다. 10분은 서버가 분석 중에 내려가 잡힌 채 남은 공고를 다시 돌리기까지의 시간이다. 한 번의 분석은 대개 몇 분 안에 끝난다.
- **뒤에서 돌리기**: `posting/Postings.findOrCreate`가 이벤트를 내고 `posting/PostingAnalyses`가 커밋 뒤(`@TransactionalEventListener`) 다른 스레드(`@Async`, Boot의 `applicationTaskExecutor`)에서 받는다. 되돌려진 올리기(409 등)는 분석하지 않는다.
  - 할 일은 서버의 메모리에만 있다. 서버가 내려가면 기다리던 분석이 사라진다(코드에 `shortcut:`). 그 공고를 다음에 누가 올리거나 넣으면 다시 돈다.
  - 통합 테스트에서는 요청이 돌아오기 전에 끝난다(구조 문서 8절의 `AwaitAsyncConfiguration`).
- **관심 켜기와 상태 바꾸기는 분석을 시작하지 않는다**: 둘 다 내 공고 행을 만들 수 있지만 공고를 올리거나 넣는 일이 아니다. 관심 버튼을 누른 사람에게 사용액이 들지 않게 했다. 그 공고는 그룹에 올릴 때 이미 시작됐다.
- 한도는 시작할 때 한 번 본다(`Llm.requireBudget`, 경험카드 설계 4.5). LLM은 트랜잭션 밖에서 부른다.
- 기록(log)에는 공고 id, 오류 코드, 쓸 수 없는 답의 이유, 버린 문항 수만 남긴다. 공고 글은 남기지 않는다.
- **응답**: 두 상세에 `analysis`가 더해진다. 아직 없으면 `null`이고, 있으면 `{ must, nice, duties, keywords, questions: [{ text, limit }] }`다(4.4). 올리기와 넣기의 응답도 상세 모양이지만 분석이 뒤에서 돌므로 대개 `null`이다. 상세를 다시 열면 보인다.
- 다시 분석하는 길은 없다. 프롬프트를 바꾸거나 공고를 고쳐도(4.5) 있는 분석은 그대로다. 필요해지면 칸을 비우는 마이그레이션이나 관리 기능을 따로 둔다.

## 5. 규칙

### 5.1 권한

그룹 API는 모두 로그인한 그 그룹의 멤버만 부를 수 있다. 멤버가 아니거나 그룹이 없으면 404 `GROUP_NOT_FOUND`를 준다(그룹 문서 G3).

| 동작 | 할 수 있는 사람 |
|---|---|
| 보기, 공고 올리기, 관심, 댓글 달기, 날짜 넣기 | 그 그룹의 멤버. 관심 끄기는 지원 상태가 있어도 된다(4.5) |
| 공고 고치기(회사명, 공고명, 마감) | 그 그룹에 올린 사람. 그룹장도 못 한다. 다른 사람이 다른 그룹에도 올린(내리지 않은) 공고면 아무도 못 한다(4.5) |
| 그룹에서 내리기 | 올린 사람, 그룹장 |
| 댓글 수정 | 쓴 사람 |
| 댓글 삭제 | 쓴 사람, 그룹장 |
| 내 지원 상태 바꾸기 | 본인. 내 그룹에 있거나 이미 내 공고에 있는 공고만(4.2) |
| 내 공고 보기, 메모 | 본인. 내 공고에 있는 공고만(4.2) |
| 그룹 없이 내 공고에 넣기 | 로그인한 사람 누구나. 내 행만 만든다(4.2) |
| 그룹 소식 보기 | 본인. 내가 멤버인 그룹의 것만(4.5) |

### 5.2 공개 범위 적용

`interests`에는 그 그룹에서 관심을 켠 멤버만 나온다. 보는 사람 자신은 빼고 `me`로 따로 준다. 지원 표시는 서버가 그 멤버의 공개 범위에 맞춰 잘라 보낸다.

| 그 멤버의 공개 범위 | `applied` | `progress` |
|---|---|---|
| 관심만(`INTEREST`) | 항상 `false` | 없음 |
| 지원 여부까지(`APPLIED`) | 지원함이면 `true` | 없음 |
| 단계·결과까지(`PROGRESS`) | 지원함이면 `true` | 상태 글자가 "지원함"이 아닐 때 그 글자 |

`me.status`는 내 값이라 공개 범위와 무관하게 준다.

### 5.3 상태 글자

`user_postings`의 세 값을 화면 글자 하나로 바꾸는 규칙이다. `me.status`와 `progress`에 쓴다.

| 결정 | 단계 | 결과 | 글자 |
|---|---|---|---|
| 지원함이 아님 | | | 없음(`null`) |
| 지원함 | 서류 | 진행 중 | 지원함 |
| 지원함 | 필기, 1차 면접, 2차 면접, 최종 | 진행 중 | "필기 단계"처럼 단계 + " 단계" |
| 지원함 | 어느 단계든 | 합격 | "서류 합격"처럼 단계 + " 합격" |
| 지원함 | 어느 단계든 | 불합격 | "필기 불합격"처럼 단계 + " 불합격" |

### 5.4 날짜

- `today`는 서버의 한국 날짜(`Asia/Seoul`)다. 서버 시간대와 무관하게 계산한다.
- 마감됨은 `deadline_date < today`다. 마감일 당일은 진행 중이다. 프런트의 `isClosed`와 같다.
- 열린 공고 수도 같은 `today`로 센다.
- `postedAt`은 올린 시각의 한국 날짜("YYYY-MM-DD")다. 댓글의 `createdAt`만 시각까지 ISO 8601로 준다.

## 7. 화면과 API

| 화면 | 쓰는 API |
|---|---|
| 그룹 공고 목록 | `GET …/posts`. 관심 켜기·끄기는 `PUT …/interest`, 날짜 넣기는 `PUT …/deadline`, 공고 올리기는 `POST …/posts` |
| 그룹 공고 상세 | `GET …/posts/{postId}`. 관심은 `PUT …/interest`, 그룹에서 내리기는 `DELETE …/posts/{postId}`, 댓글은 `POST`·`PUT`·`DELETE …/comments`, 공개 범위 바꾸기는 `PUT …/me/disclosure` |
| 공고 올리기, 칸 확인 | 읽어 오기는 `POST /api/postings/read`(4.6), 올리기는 `POST …/posts` |
| 내 공고, 지원 현황, 달력 | `GET /api/me/postings`. 상태 바꾸기는 `PUT /api/me/postings/{postingId}`, "공고 넣기"는 읽어 오기(4.6) 뒤 `POST /api/me/postings` |
| 공고 상세(내 공고) | `GET /api/me/postings/{postingId}`. 상태 바꾸기는 `PUT /api/me/postings/{postingId}`, 메모는 `PUT …/memo` |
| 홈 | `GET /api/me/postings`의 오늘과 내 공고만. 카드 수, 메일에서 온 변경, 그룹 소식은 이 문서에 없다 |

프런트의 `api.ts` 함수와의 대응: `getGroupPosts` → `GET …/posts`, `getGroupPost` → `GET …/posts/{postId}`, `setInterest` → `PUT …/interest`, `addComment` → `POST …/comments`. 내 공고(`features/my-posts/api.ts`): `getMyPostings` → `GET /api/me/postings`, `getMyPosting` → `GET /api/me/postings/{postingId}`, `updateMyState` → `PUT /api/me/postings/{postingId}`, `saveMemo` → `PUT …/memo`.

화면별로 보이는 값은 화면·API 대응 문서 2.3~2.5절에 있다. 시안이 요구하는데 이 문서에 없는 것: 맞는 카드(13번), 홈의 모음(14번), 전형 일정(15번). 그룹 없이 내 공고에 넣기(11번)는 2026-11-15에 4.2에, 올리기 요청의 칸(8번)은 같은 날 4.5에 넣었다. 내 공고 조회(10번)와 메모(12번)는 2026-11-15에 4.2에 넣었다. 공고 읽어 오기(3절 7번)와 읽는 단계의 중복 안내(9번)는 같은 날 4.6으로 만들었다(파일 읽기도 같은 날 더했다. LLM 보완은 아직).

## 8. 프런트와 맞출 것

1. id가 숫자다(구조 문서 5절). `types.ts`의 `id: string`을 바꾸거나 서버가 문자열로 보낸다.
2. 목록과 상세 응답에 `viewer`, `group`이 없다. `{ today, posts }`, `{ today, post }`만 온다.
3. `postedBy`와 댓글의 `author`가 `null`일 수 있다(탈퇴한 사람). 지금 타입은 `Member`다.
4. 올리기가 409 `ALREADY_IN_GROUP`을 주면 응답의 `postId`로 기존 공고에 보낸다.
5. `progress` 글자가 예시 데이터의 "면접 단계"가 아니라 "1차 면접 단계"처럼 온다(5.3).
6. "새 공고"는 프런트가 `postedAt`과 `today`로 정한다. 서버는 값을 주지 않는다.
7. 없는 그룹과 공고는 404에 `GROUP_NOT_FOUND`, `POST_NOT_FOUND`로 온다. 지금의 `NotFoundError`에 대응한다.
8. (같은 날) 서버가 만든 댓글의 `createdAt`은 `2026-11-13T16:56:26.381516+09:00`처럼 소수 초가 붙을 수 있다. 예시 데이터의 댓글은 초까지다.
9. (같은 날, 나머지 API) 올리기의 409 `ALREADY_IN_GROUP`은 `postId`를 본문의 맨 위 칸으로 준다(4.3절). 4번의 "응답의 `postId`"가 이것이다.
10. (같은 날) 올리기는 상세와 같은 `{ today, post }`를, 날짜 넣기는 `Deadline`을, 댓글 수정은 `Comment`를 돌려준다. 받은 값으로 화면의 그 부분만 바꾸면 된다.
11. 로그인하지 않은 요청은 모두 401 `UNAUTHENTICATED`다(구조 문서 5절, 6절).
12. (같은 날) 날짜 넣기는 `Deadline` 꼴을 보낸다: 날짜 `{ "kind": "date", "date": "2026-11-20" }`, 마감일 넣기 창의 "날짜 없이 상시 채용입니다"는 `{ "kind": "always" }`.
13. (2026-11-15, 내 공고) `getMyPostings`는 `GET /api/me/postings`, `getMyPosting`은 `GET /api/me/postings/{postingId}`다. 모양은 지금 함수와 같은 `{ today, postings }`, `{ today, posting }`이다. 그룹의 `id`와 `postId`도 숫자다(1번).
14. 목록의 줄과 상세에 `status`(서버의 상태 글자. 지원함이 아니면 `null`)가 더 온다. 화면은 지금처럼 `statusLabel`로 그려도 된다.
15. 상세의 `memo`는 메모가 없으면 `""`가 아니라 `null`이다.
16. 메모 저장은 `PUT /api/me/postings/{postingId}/memo { "memo": "…" }`이고 204다. 빈 글자를 보내면 메모가 지워진다. 2,000자를 넘으면 400 `INVALID_INPUT`이다.
17. 상세에 `matches`, `unmatched`(맞는 카드, 화면·API 대응 문서 3절 13번)가 없다. 서버가 맞추기를 아직 하지 않는다.
18. 홈의 `HomeData` 가운데 `today`와 `postings`만 `GET /api/me/postings`로 받는다. `news`는 `GET /api/me/group-activity`로 받는다(22번). `unverifiedCards`, `mailChanges`(3절 14번)는 서버에 없다. 지원 현황과 달력의 전형 일정(15번)도 없다.
19. 상태 바꾸기(`updateMyState`)의 응답은 `MyPosting`이 아니라 `{ postingId, decision, stage, result, status }`다(4.2). 화면이 가진 줄에 이 값을 덮으면 된다.
20. 내 공고에 없는 공고의 상세와 메모는 404 `POSTING_NOT_FOUND`다. 지금의 `NotFoundError`에 대응한다.
21. 목록은 내 공고에 넣은 시각의 역순으로 온다. 화면이 지금처럼 다시 정렬하고, 지원 현황의 숫자 넷도 지금처럼 `boardCounts`로 센다.
22. (2026-11-15) 홈의 그룹 소식은 `GET /api/me/group-activity`가 `GroupNews[]`를 목록 그대로 준다. `HomeData.news`에 그대로 넣는다. `group.id`와 `postId`는 숫자다(1번). 홈은 지금 줄의 key를 `group.id + text`로 만드는데, 같은 사람이 한 그룹에서 회사명이 같은 두 공고에 댓글을 달면 글자가 같아진다. key에 `postId`도 넣는다.
23. (같은 날) 관심 멤버에 나를 넣는 조건을 `me.interested`만으로 바꾼다. 지금 `group-posts/my-state.ts`의 `isInterestedOrApplied`는 지원 상태만 있어도 나를 넣는다. 서버는 `interests`에 나를 넣지 않으므로 서버에서 바꿀 것은 없다. 상태 알약은 `me.status`로 그대로 그린다(4.5).
24. (같은 날) 상세에 관심 끄기를 둔다. 지원 상태가 있어도 `PUT …/interest { "interested": false }`가 된다. 응답의 `status`는 그대로 오고, 내 공고에서 빠지지 않는다(4.5).
25. (같은 날) 공고 고치기는 `PUT /api/groups/{groupId}/posts/{postId}`에 `{ company, title, deadline }`을 보내 `{ today, post }`를 받는다. `deadline`은 날짜나 상시이고, 마감이 아직 `unknown`인 공고는 `{ "kind": "unknown" }`을 그대로 보내도 된다(회사명만 고칠 때). 마감이 있는 공고를 `unknown`으로 보내면 409 `DEADLINE_ALREADY_SET`이다. 버튼은 `post.postedBy.id`가 나일 때만 둔다(아니면 403 `FORBIDDEN`). 다른 사람이 다른 그룹에도 올린 공고는 409 `POSTING_SHARED`이고, 메시지를 그대로 보여 주면 된다. 고친 값은 같은 공고를 올린 다른 그룹에도 보인다(4.5).
26. (같은 날) 내 공고의 "공고 넣기"는 읽어 오기(`POST /api/postings/read`, `groupId` 없이) 뒤 `POST /api/me/postings`에 그룹 올리기와 같은 본문(`{ company, title, deadline, deadlineName, applyAt, sourceUrl }`)을 보낸다. `keywords`와 `sections`도 함께 받는다(27번). 201에 상세와 같은 `{ today, posting }`(`getMyPosting`의 모양)이 오고, 넣은 행은 `decision: "undecided"`다. 이미 내 공고에 있으면 409 `ALREADY_IN_MY_POSTINGS`와 본문 맨 위 칸의 `postingId`가 오므로 그 공고의 상세로 보낸다(그룹 올리기의 `postId`와 이름이 다르다). 같은 공고가 이미 서버에 있으면(다른 사람이 그룹에 올린 공고 등) 그 공고에 내 행이 생기고, 회사명 등은 처음 올린 사람의 값이다. 지금 프런트의 "공고 넣기"(`my-posts-page.tsx`)는 화면이 없어 눌러도 아무 일이 없다.
27. (같은 날) 올리기(`uploadPost`)와 내 공고 넣기는 `PostUpload`의 `keywords`(문자열 목록)와 `sections`(`[{ title, items }]`)를 함께 보낸다. 지금 `group-posts/api.ts`의 `uploadPost`는 두 칸을 빼고 보낸다(shortcut 주석). `DraftSection`의 `from`은 보내도 서버가 버린다. 서버가 다시 검사한다: 키워드는 사전의 대표 표기로 바뀌고, 사전에 없는 것과 겹치는 것은 빠진다. 빈 항목과 항목이 없는 묶음도 빠진다(칸 확인 화면이 지금 보내는 대로다). 키워드 100개(하나 100자), 묶음 100개(이름 50자), 묶음의 글자를 모두 더해 50,000자를 넘거나 묶음 이름이 비면 400 `INVALID_INPUT`이다. 묶음의 50,000자 한도는 링크로 읽은 결과에서도 걸릴 수 있다. 링크 읽기는 글자 수가 아니라 받는 본문 1MB(바이트)로 자르므로(4.6), 긴 페이지에서 읽은 묶음이 50,000자를 넘을 수 있다. 그래서 올리기의 400은 메시지를 그대로 보여 준다. 지금 칸 확인 화면의 `submit`은 `try`/`finally`만 있고 `catch`가 없어 400이 화면에 보이지 않는다. 응답(`{ today, post }`, `{ today, posting }`)의 `keywords`, `sections`가 저장된 값이다. 같은 공고가 이미 있으면 처음 올린 사람의 값이 남는다(4.5).
28. (같은 날) 그룹 공고 목록의 줄에도 `sourceUrl`(원문 주소, `string | null`)이 온다(4.5). `types.ts`의 `GroupPost`에 `sourceUrl: string | null`을 더하고 `GroupPostDetail`의 것은 빼도 된다(상세는 전처럼 같은 값을 준다). 그러면 `post-dialogs.tsx`의 마감일 넣기 창의 "원문 열기" 자리(`PlaceholderLink`)를 링크로 바꿀 수 있다. `null`이면 링크를 두지 않는다.
30. (2026-11-16, 공고 분석) 그룹 공고 상세(`GroupPostDetail`)와 내 공고 상세(`MyPostingDetail`)에 `analysis`가 더 온다(4.7). 두 `types.ts`에 없다. 아직 없으면 `null`이고, 있으면 `{ must: string[], nice: string[], duties: string[], keywords: string[], questions: { text: string, limit: number | null }[] }`다. `must`는 필수 역량, `nice`는 우대 역량, `duties`는 주요 업무, `questions`는 공고에 적힌 자기소개서 문항과 글자 수다. 분석 키워드에는 사전에 없는 낱말도 있다. 올리기·넣기의 응답에서는 분석이 뒤에서 돌아 대개 `null`이다. 상세를 다시 열면 보인다. 공고 내용(`sections`)과 키워드(`keywords`)는 전처럼 원문에서 읽은 값이고 분석으로 채우지 않는다. 묶음 없이 올린 공고는 분석도 없다. 화면에 어떻게 둘지(공고 내용 옆의 요약, 맞는 카드의 "카드로 답하지 못한 요건"의 재료)는 프런트가 정한다. 지금 화면은 이 칸을 무시해도 깨지지 않는다.

읽어 오기(4.6, 2026-11-15). 프런트의 `readPost`와 `types.ts`의 `ReadPostResult`·`PostDraft`와 다른 곳이다.

13. 결과는 `{ status, … }` 셋으로 갈리지 않는다. 읽으면 200 에 `PostDraft`에 가까운 응답 하나, 읽지 못하면 422 `FETCH_BLOCKED`·`FETCH_FAILED`(메시지에 이유와 붙여넣기 안내), 같은 공고는 200 응답의 `duplicate`다. 가짜 서버의 `"failed"`는 422 로, `"duplicate"`는 `duplicate`가 있는 응답으로 바꾼다.
14. 요청은 `{ "url": … }`이나 `{ "text": …, "sourceUrl": … }`에 `groupId`를 더한 것이다. `PostReadInput`의 `kind`는 보내지 않는다. 파일(`kind: "file"`)은 29번이다.
15. `duplicate`는 `{ postId, company, title, postedBy, postedAt }`이다. `types.ts`의 `Pick<GroupPost, "id" | …>`는 `id`다. `postedBy`는 `null`일 수 있다(3번). 링크로 읽었을 때는 페이지를 받지 않아 다른 칸이 비어 있다.
16. `PostDraft`에 없는 `deadlineName`이 응답에 있고 `unread`에도 `"deadlineName"`이 들어간다(`DraftField`에 없다). 규칙으로 읽지 않아 늘 `""`이고 늘 `unread`에 있다. `applyAt`도 지금은 늘 그렇다.
17. `source`는 `{ title, text }`다. `paragraphs`와 `note`가 없다. 원문은 `text`(줄바꿈이 든 글자)로, 묶음은 `sections`(`from`이 원문의 머리 줄)로 그린다.
18. `evidence`의 값은 원문 조각 그대로다. 가짜 서버처럼 `페이지 제목 "…"`으로 설명을 붙이지 않는다. 조각이 `source.text`에 있으면 그 부분을 굵게 보일 수 있다. 페이지 제목과 JSON-LD 의 값은 `text`에 없을 수 있다.
19. (2026-11-15 해결) 응답에 `keywords`(키워드 사전의 대표 표기, 15개까지)가 있다(4.6). `PostDraft.keywords`와 같은 `string[]`이다. 프런트는 `api.ts`의 `readPost`에서 `keywords: []`로 덮는 shortcut 주석과 그 덮기, `ReadResponse`의 `Omit<PostDraft, "unread" | "keywords">`의 `"keywords"`를 지우고 응답의 `keywords`를 그대로 쓰면 된다. 찾은 것이 없거나 `duplicate`인 응답은 `[]`다.
20. 못 읽은 칸의 값은 `null`이 아니라 `""`다(`PostDraft`와 같다). 마감은 `{ "kind": "unknown" }`이다.
29. (2026-11-15, 파일) `readPost`의 파일(`kind: "file"`)은 지금처럼 실패로 돌려주지 않고 서버에 보낸다(`api.ts`의 shortcut 주석을 걷는다). `FormData`에 `file`(파일)과 `groupId`(그룹 id)를 넣어 `POST /api/postings/read`로 보낸다. 카드의 `uploadSource`처럼 `request`가 `FormData`를 그대로 보낸다. 원문 링크는 보내지 않는다(받지 않는다, 4.6). 응답은 붙여넣은 본문과 같은 모양이고 `sourceUrl`은 `""`이며 `duplicate`는 오지 않는다. 오류 넷(4.3)은 메시지에 붙여넣기 안내가 있으니 `FETCH_BLOCKED`·`FETCH_FAILED`처럼 `{ status: "failed", message }`로 보여 준다: 413 `FILE_TOO_LARGE`, 415 `FILE_UNSUPPORTED_TYPE`, 422 `FILE_UNREADABLE`·`FILE_NO_TEXT`. 413은 서버 앞의 Caddy가 본문 없이 끊을 수도 있어 `code`와 관계없이 "너무 크다"로 본다(`code`가 없으면 "파일이 너무 큽니다. 20MB까지 올릴 수 있습니다."처럼, 경험카드 문서 6절 7번). `post-new-page.tsx`의 `ACCEPT`(`.pdf,.docx,.hwpx,.hwp`)와 "20MB까지"는 서버와 같다. 20MB를 넘는 파일은 보내기 전에 막는다(그 파일의 shortcut 주석).

## 9. 새로 생긴 결정

| 항목 | 내용 | 선택지 |
|---|---|---|
| 지원 상태는 있는데 그 그룹에서 관심은 꺼져 있을 때 | 다른 그룹에서 관심을 켜고 지원한 공고가 이 그룹에도 있으면 생긴다 | **정함(2026-11-15)**: 내 화면에서도 관심 멤버에 넣지 않는다. 다른 멤버가 보는 것과 내가 보는 것을 같게 한다. 상태 알약은 내 화면에만 그대로 보인다 |
| 지원한 뒤 관심 끄기 | 상태가 있으면 화면에 관심 버튼 대신 상태 알약만 나온다. 끌 방법이 없다 | **정함(2026-11-15)**: 그룹 공고 상세에 끄기를 둔다. 꺼도 내 공고 목록에는 남는다(정리 문서 7절) |
| 공고 고치기 | 회사명, 공고명, 마감을 잘못 올렸을 때 고칠 길이 없다. 날짜 넣기는 한 번뿐이다 | **정함(2026-11-15)**: 그룹에 그 공고를 올린 사람이 회사명, 공고명, 마감을 고친다. 공고 본체는 그룹끼리 같이 쓰므로 고친 값은 그 공고가 있는 모든 그룹에 보인다 |

정리 문서 7절의 지원 상태 값의 구조, 같은 공고 판별, 공고 단위, 필수값 목록, 링크 처리도 이 설계에 걸려 있다.

- 사이트 규칙이 호스트가 그 사이트이거나 하위 도메인일 때만 맞는다. jobfit은 이름으로 끝나기만 보아서 `fakesaramin.co.kr`도 사람인 공고키가 된다. 리드미는 공고키가 같으면 다른 그룹이 공고 본체(원문 링크 포함)를 함께 쓰므로, 남의 호스트가 사이트 공고를 가로챌 수 있다. jobfit에도 같은 빈틈이 있다.
