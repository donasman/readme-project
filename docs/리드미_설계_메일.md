# 리드미 설계: 메일 자동화

2026-11-16. 화면·API 대응 3절 16번(받는 길, 2026-11-15에 정함)과 15번(전형 일정 테이블)을 설계로 키운 것이다. 서버에 들어갔다(`inboundmail` 패키지, `V10__inbound_mail.sql`). 받는 Worker는 `deploy/cloudflare/inbound-mail-worker.js`다.

- 왜 이 길인가(예약작업 경로를 쓰지 않는 이유, 도메인 둘): 정리 문서 6절, 7절의 "예약작업 경로", "도메인"
- 화면: 시안 9차 "메일 확인함", "메일 자동화"(화면·API 대응 2.6). 지금은 프런트가 가짜 서버를 부른다(남은 작업 프런트엔드 9-5)
- 메일 분류의 LLM 바탕: 경험카드 문서 4.5(`LlmFeature.MAIL_CLASSIFY`, effort `low`)

**아직 실제 메일로 확인하지 않았다.** 수신 전용 도메인을 사고(남은 작업 8-1) Worker를 올린 뒤 6절의 순서로 확인한다.

## 1. 범위

사용자가 메일 서비스(Gmail 등)에 자동 전달 규칙을 한 번 만들면, 리드미의 자기 수신 주소로 온 채용 메일을 읽어 내 공고와 지원 상태에 반영한다. 리드미는 사용자 메일함에 들어가지 않는다.

이 문서에 있는 것: 받는 API와 서명, 수신 주소와 보내는 주소, 분류와 반영 규칙, 메일 확인함 API, 전형 일정 테이블(15번)과 읽기 API.

이 문서에 없는 것: 화면(프런트엔드 9-5), 도메인과 Cloudflare 설정(운영 8-1), 일정을 손으로 넣고 지우는 API(화면이 없다).

생성 SQL은 `backend/src/main/resources/db/migration/V10__inbound_mail.sql`에 있다.

`inbound_mails.status`:

| 값 | 뜻 |
|---|---|
| `WAITING` | 분류를 기다린다(막 받았거나, LLM이 답하지 않았거나, 한도에 닿았다) |
| `READING` | 분류하는 중. 10분이 지나면 멈춘 것으로 보고 다시 잡는다 |
| `READ` | 분류가 끝났다. 본문 글은 지웠다 |
| `FORWARDING` | Gmail 전달 확인 메일(M7) |

`review`는 확인 필요의 상태다: `PENDING`(기다림), `APPLIED`(반영), `IGNORED`(무시). 확인할 것이 없는 메일(새 공고만 넣은 것)은 비어 있다.

## 4. API

### 4.1 받기 (Worker → 서버)

`POST /api/inbound-mail`. 본문은 메일 원문(RFC 822) 그대로다.

| 헤더 | 값 |
|---|---|
| `X-Readme-Timestamp` | 유닉스 초 |
| `X-Readme-Envelope-From` | `message.from`(봉투 MAIL FROM) |
| `X-Readme-Envelope-To` | `message.to`(봉투 RCPT TO). 전달된 메일의 `To:` 헤더는 사용자의 원래 주소라 쓰지 않는다 |
| `X-Readme-Auth-Results` | `message.headers.get("authentication-results")`. 없으면 빈 글자 |
| `X-Readme-Signature` | M2의 서명 |

| 응답 | 언제 |
|---|---|
| 204 | 받았다. 받지 않고 버린 메일(모르는 주소, 확인되지 않은 보낸 사람, 이미 받은 메일)도 204다 |
| 401 `MAIL_SIGNATURE_INVALID` | 서명이 틀렸거나, 시각이 5분 넘게 다르거나, 비밀 값이 없다 |
| 413 `MAIL_TOO_LARGE` | 원문이 10MB를 넘는다. Worker가 먼저 거절한다 |

같은 메일은 사람마다 `Message-ID`(없으면 원문의 SHA-256)로 한 번만 받는다.

### 4.2 메일 자동화 설정

| API | 내용 |
|---|---|
| `GET /api/me/mail-settings` | `{ inboundAddress, senders: [ ... ] }`. 처음 부르면 수신 주소를 만들고 계정 이메일을 보내는 주소에 넣는다. 수신 도메인 설정이 없으면 `inboundAddress`가 null이다 |
| `POST /api/me/mail-settings/inbound-address` | 수신 주소를 새로 만든다. 새 설정을 돌려준다 |
| `POST /api/me/mail-settings/senders` | 본문 `{ email }`. 이미 있으면 그대로 둔다. 204. 형식이 틀리면 400 `INVALID_INPUT`, 10개를 넘으면 409 `TOO_MANY_SENDERS` |
| `DELETE /api/me/mail-settings/senders?email=…` | 지운다. 없어도 204 |

### 4.3 분류 (LLM)

지시문은 `backend/src/main/resources/prompts/mail-classify.md`. 보내는 글: 오늘 날짜, 보낸 곳, 제목, 본문 앞 6,000자, 내 공고 목록(`id | 회사 | 공고명 | 지금 상태`).

받는 칸(`MailAnswer`): `recruiting`(이 사람의 지원·공고에 관한 채용 메일인지), `postingId`(목록의 id, 없으면 0), `company`·`title`·`deadline`(목록에 없는 공고일 때), `stage`·`result`(메일이 알리는 지원 상태. 정해진 값이나 ""), `scheduleDate`·`scheduleTime`(다음 전형 날짜와 시각), `quote`(근거 문장, 메일에 있는 그대로), `summary`(확인함과 홈에 보일 짧은 이름).

서버의 규칙(`MailRules`):

- `recruiting`이 아니면 버린다.
- 공고: `postingId`가 목록에 있으면 그 공고. 아니면 회사명과 공고명이 있을 때 새 공고로 넣는다(같은 공고키의 공고가 있으면 그 공고). 둘 다 아니면 버린다.
- 상태: `stage`와 `result`가 모두 정해진 값이면 "지원함 · 그 단계 · 그 결과"를 제안한다. 지금 상태와 같고 새 일정도 없으면 제안하지 않는다.
- 일정: 제안한 단계가 있고 날짜가 맞는 꼴일 때만 둔다.
- 근거 문장은 본문에 그대로 있을 때만 싣는다(띄어쓰기는 가리지 않는다).
- 새로 넣은 공고도 제안도 없으면 버린다.

### 4.4 메일 확인함

| API | 내용 |
|---|---|
| `GET /api/me/mailbox` | `{ pending, added, forwarding, waiting }`. 아래 |
| `POST /api/me/mailbox/{id}/apply` | 확인 필요를 반영한다: 지원 상태를 바꾸고, 일정이 있으면 넣는다. 204 |
| `POST /api/me/mailbox/{id}/ignore` | 확인 필요나 전달 확인 메일을 확인함에서 뺀다. 204 |
| `POST /api/me/mailbox/{id}/revert` | 메일로 넣은 공고를 내 공고에서 뺀다(M12). 204 |

내 메일이 아니거나 그 동작을 할 수 없는 메일(이미 반영했거나 무시했다, 새로 넣은 공고가 아니다, 이미 되돌렸다)은 404 `MAIL_NOT_FOUND`다.

- `pending[]`: `{ id, from, receivedAt, subject, summary, postingId, company, title, before, after, schedule, quote }`. `before`는 지금 내 상태(`{ decision, stage, result }`, 내 공고 행이 없으면 null), `after`는 반영할 상태, `schedule`은 `{ stage, date, time }`이나 null, `quote`는 null일 수 있다. 회사명과 공고명은 공고 본체의 지금 값이다.
- `added[]`: `{ id, from, receivedAt, subject, postingId, company, title }`. 되돌리지 않은 것만.
- `forwarding[]`: `{ id, receivedAt, subject, code }`. `code`는 못 꺼냈으면 null.
- `waiting`: 분류를 기다리는 메일 수.
- 모두 받은 때의 역순이다. `from`은 `From:`의 이름이 있으면 이름, 없으면 주소다.

### 4.5 전형 일정

`GET /api/me/schedules`: 내 일정 전부. `[{ postingId, company, title, stage, date, time }]`, 날짜순. `time`은 `"HH:mm"`이나 null이다.

### 4.6 오류 코드

| 코드 | HTTP | 언제 |
|---|---|---|
| `MAIL_SIGNATURE_INVALID` | 401 | 4.1 |
| `MAIL_TOO_LARGE` | 413 | 4.1 |
| `TOO_MANY_SENDERS` | 409 | 보내는 주소가 이미 10개다 |
| `MAIL_NOT_FOUND` | 404 | 4.4 |

### 4.7 만들면서 정한 것

- 분류에 실패하면: LLM이 답하지 않았으면(503) `WAITING`으로 되돌려 10분 뒤 다시 본다. 답은 받았는데 쓸 수 없거나(502) 답을 받은 뒤에 오류가 났으면 그 메일을 지운다. 다시 부르면 또 돈이 든다.
  shortcut: 지운 메일은 사용자에게 알리지 않는다(서버 기록에만 남는다). 잦으면 확인함에 "읽지 못한 메일"을 둔다.
- 메일 본문의 전화번호·주민번호는 가리지 않고 LLM에 보낸다. 분류가 끝나면 본문을 지운다. 자료 올리기(경험카드 문서 4.4)와 달리 저장하지 않기 때문이다.
- 본문 글: `text/plain`이 있으면 그것, 없으면 `text/html`의 글자다. 문자 집합 `euc-kr`, `ks_c_5601-1987`은 CP949로 읽는다(한국 메일이 이 이름으로 CP949 글자를 보낸다).
- Gmail 외의 메일 서비스(네이버, Outlook 등)의 자동 전달과 확인 절차는 확인하지 않았다. 봉투 주소를 그대로 두고 전달하는 서비스는 M6의 ①에 맞지 않을 수 있다.

## 5. 프런트와 맞출 것

- 확인함(`features/mail/types.ts`): 서버는 `pending`·`added`에 더해 `forwarding`(Gmail 확인 코드)과 `waiting`(기다리는 메일 수)을 준다. `MailChange`에 `schedule`이 더 있고 `quote`가 null일 수 있다. `MailAdded`의 `note`는 서버가 주지 않는다(모두 "새 공고로 내 공고에 넣음"이다). id는 숫자다. `receivedAt`은 시각(`+09:00`)이다.
- 설정(`features/settings/types.ts`의 `MailSettings`): 모양이 같다. `inboundAddress`가 null일 수 있다(수신 도메인이 없는 서버). 보내는 주소 지우기는 주소를 경로가 아니라 `?email=`로 보낸다.
- 홈의 "메일에서 온 변경 N건": `GET /api/me/mailbox`의 `pending` 수와 첫 `summary`로 센다.
- 달력의 전형 일정: `GET /api/me/schedules`(4.5). 지금 달력은 마감일만 보인다.

## 6. 실제 메일로 확인할 것 (도메인을 산 뒤)

1. Cloudflare에서 수신 도메인의 Email Routing을 켜고, 모든 주소 받기(catch-all)를 Worker로 보낸다. Worker의 비밀 값(`INBOUND_MAIL_SECRET`)과 서버 주소(`INBOUND_MAIL_URL`)를 넣는다.
2. 서버에 `INBOUND_MAIL_DOMAIN`, `INBOUND_MAIL_SECRET`을 넣는다.
3. Gmail에서 전달 주소로 내 수신 주소를 넣고, 확인 메일이 확인함의 `forwarding`에 코드와 함께 오는지 본다(M7).
4. 채용 메일 하나를 전달해 확인함에 들어오는지 본다. 들어오지 않으면 서버의 `logging.level.com.readme.inboundmail`을 `debug`로 두고 다시 보내, 버린 메일의 봉투 From과 `Authentication-Results` 값이 M6의 ①에 맞는지 본다. 맞지 않으면 M3·M6을 고친다. 주소가 기록에 남으므로 확인이 끝나면 되돌린다.
5. Worker가 오류를 내면(서버가 꺼졌을 때) 보낸 쪽이 다시 보내는지 본다. 다시 보내지 않으면 그 사이의 메일을 잃는다.
