# 리드미 설계 초안: 그룹·그룹 공고

2026-11-13 기준. 만들어 둔 화면(그룹 공고 목록, 그룹 공고 상세, 헤더의 그룹 전환)을 기준으로 잡은 테이블 구조와 API 목록이다. 화면에는 없지만 이 화면들이 서버와 붙으려면 있어야 하는 로직도 점검했다(6절). 초안이고, 2절의 가정은 바꿀 수 있다.

- 화면이 기대는 응답 모양: `frontend/src/features/group-posts/types.ts`
- 그룹 공고에서 정한 것: `claude/리드미_리서치_재사용_정리.md`의 "그룹 공고 (2026-11-13에 정함)"
- 로그인과 계정 테이블: `claude/리드미_설계_로그인_경험카드.md`
- 프런트 구조: `claude/리드미_프런트_구조_계획.md`

## 1. 범위

| 묶음 | 화면에 있는 것 | 화면에 없지만 넣은 것 |
|---|---|---|
| 그룹 | 그룹 전환 메뉴, 멤버 수, 멤버 필터, 공개 범위 바꾸기(자리만) | 그룹 만들기, 초대 링크, 초대 수락, 나가기 |
| 그룹 공고 | 목록, 상세, 관심 켜기·끄기, 댓글 달기. 자리만 있는 것: 공고 올리기, 날짜 넣기, 그룹에서 내리기, 댓글 수정·삭제 | 같은 공고 판별, 내리고 다시 올리기 |
| 내 공고 | "지원함", "필기 단계" 같은 내 상태 표시 | 지원 상태의 원본 테이블, 상태를 넣는 API 하나 |

이 초안에 없는 것: 공고 등록 화면의 자동 채우기(URL 수집, LLM 분석), 멤버·초대 관리 화면, 지원 관리 화면, 알림, 요청 횟수 제한.

## 2. 초안이 깔고 있는 가정

| # | 항목 | 초안의 값 | 다른 선택지 | 바뀌는 곳 |
|---|---|---|---|---|
| 1 | 지원 상태 값의 구조 | 결정·단계·결과 세 칸(정리 문서 7절의 제안) | jobfit 7종을 한 칸에 | `user_postings`, 상태 글자 규칙(5.3) |
| 2 | 공고 본체 | 그룹과 무관하게 공고 하나에 한 행. 여러 그룹이 같은 행을 가리킨다 | 그룹마다 사본 | `postings`, `group_posts`. 한 그룹의 "날짜 넣기"가 다른 그룹에도 보인다 |
| 3 | 같은 공고 판별 | jobfit 공고키(사이트별 공고번호 → 추적값을 뺀 URL → 회사명·직무·마감일 해시)를 `posting_key`에 둔다 | 정리 문서 7절의 다른 안 | 키를 만드는 규칙. 테이블은 같다 |
| 4 | 그룹에서 내리기 | 행은 남기고 목록에서만 뺀다. 다시 올리면 같은 행이 되살아나고 댓글과 관심이 그대로다 | 행을 지운다(댓글·관심도 지워진다) | `group_posts.taken_down_at`, 내리기 API |
| 5 | 날짜 넣기 | 마감을 못 읽은 공고에만, 멤버 누구나, 한 번 | 언제든 고칠 수 있게 / 올린 사람과 그룹장만 | 날짜 넣기 API |
| 6 | 초대 | 링크(추측할 수 없는 토큰), 7일 뒤 만료, 멤버 누구나 만든다 | 그룹장만 만든다 / 메일 초대 | `group_invites`, 권한 |
| 7 | 그룹장 | 그룹당 한 명. 그룹장은 나갈 수 없다 | 넘기기 / 공동 그룹장 | `group_members`의 그룹장 제약, 나가기 API |
| 8 | 멤버가 아닌 사람의 요청 | 그룹이 없을 때와 같은 404 | 403 | 오류 코드 |
| 9 | 목록 | 한 번에 전부 준다. 탭 개수, 필터, 정렬, 묶음은 프런트가 한다(지금 화면 그대로) | 서버가 필터·정렬하고 나눠 준다 | 목록 API |
| 10 | 관심 끄기 | 내 공고 행은 남긴다(정리 문서의 제안) | 함께 지운다 | 관심 API |
| 11 | id | 숫자(`bigint`). 주소도 `/groups/1/posts/12` 꼴 | 문자열 | 프런트 타입(지금은 `string`) |
| 12 | 공고 내용 묶음 | `jsonb` 한 칸 | 행으로 따로 저장 | `postings.sections` |

1번과 3번은 정리 문서 7절에 미정으로 남아 있는 항목이다. 이 초안은 제안된 안을 값으로 썼다.

## 3. 테이블

새 테이블 9개다. Flyway `V3__groups.sql`로 넣는다.

| 테이블 | 내용 |
|---|---|
| `groups` | 그룹. 이름, 표시 글자 |
| `group_members` | 그룹 × 사용자. 역할(그룹장·멤버), 이 그룹에 정한 공개 범위 |
| `group_invites` | 초대 링크의 토큰(해시로 보관), 만료 시각 |
| `postings` | 공고 본체. 회사명, 공고명, 마감, 지원처, 원문 주소, 공고 내용 묶음 |
| `posting_keywords` | 공고의 키워드(키워드 사전의 대표 표기) |
| `group_posts` | 그룹 × 공고. 올린 사람, 올린 시각, 내린 시각 |
| `group_post_interests` | 그룹 × 공고 × 사용자. 관심 표시 |
| `group_post_comments` | 그룹 × 공고의 댓글 |
| `user_postings` | 사용자 × 공고. 내 공고 목록의 한 줄이자 지원 상태의 원본 |

### 3.1 생성 SQL (Flyway `V3__groups.sql`)

PostgreSQL 16에서 V1, V2 위에 실행해 확인했다(3.3).

```sql
-- 리드미 V3: 그룹 · 그룹 공고
set search_path to readme;

-- ── 그룹 ─────────────────────────────────────────────────────────────
create table groups (
  id         bigint generated always as identity primary key,
  name       varchar(50) not null,
  mark       varchar(4)  not null,               -- 헤더 동그라미 안의 글자. 비워 보내면 서버가 이름 첫 글자를 넣는다
  created_by bigint references users(id) on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table group_members (
  group_id   bigint      not null references groups(id) on delete cascade,
  user_id    bigint      not null references users(id)  on delete cascade,
  role       varchar(10) not null default 'MEMBER'  check (role in ('LEADER', 'MEMBER')),
  disclosure varchar(10) not null default 'APPLIED' check (disclosure in ('INTEREST', 'APPLIED', 'PROGRESS')),
  joined_at  timestamptz not null default now(),
  primary key (group_id, user_id)
);
create unique index group_members_leader_key on group_members (group_id) where role = 'LEADER';  -- 그룹장은 한 명
create index group_members_user_idx on group_members (user_id);

create table group_invites (
  id         bigint generated always as identity primary key,
  group_id   bigint      not null references groups(id) on delete cascade,
  token_hash char(64)    not null unique,        -- 토큰 원문은 초대 링크에만 있다. DB에는 SHA-256
  created_by bigint references users(id) on delete set null,
  expires_at timestamptz not null,
  revoked_at timestamptz,
  created_at timestamptz not null default now()
);
create index group_invites_group_idx on group_invites (group_id);

-- ── 공고 본체 ─────────────────────────────────────────────────────────
-- 그룹과 무관하게 공고 하나에 한 행. 같은 공고를 여러 그룹이 올리면 이 행을 함께 가리킨다.
create table postings (
  id              bigint generated always as identity primary key,
  posting_key     varchar(300) unique,           -- 같은 공고 판별 키(jobfit 공고키). 만들 수 없으면 null
  company         varchar(200) not null,
  title           varchar(300) not null,
  deadline_kind   varchar(10)  not null check (deadline_kind in ('DATE', 'ALWAYS', 'UNKNOWN')),
  deadline_date   date,
  deadline_name   varchar(50),                   -- 예: '서류 접수 마감'
  apply_at        varchar(100),                  -- 지원처. 예: '회사 채용 홈페이지'
  source_url      varchar(2000),
  sections        jsonb        not null default '[]'::jsonb,  -- 공고 내용 묶음 [{ "title": "주요 업무", "items": ["…"] }]
  created_by      bigint references users(id) on delete set null,
  deadline_set_by bigint references users(id) on delete set null,  -- "날짜 넣기"를 한 사람
  deadline_set_at timestamptz,
  created_at      timestamptz  not null default now(),
  updated_at      timestamptz  not null default now(),
  check ((deadline_kind = 'DATE') = (deadline_date is not null))
);

create table posting_keywords (
  posting_id bigint       not null references postings(id) on delete cascade,
  keyword    varchar(100) not null,              -- 키워드 사전의 대표 표기
  seq        integer      not null,              -- 화면에 보이는 순서
  primary key (posting_id, keyword)
);
create index posting_keywords_keyword_idx on posting_keywords (keyword);

-- ── 그룹 공고 (그룹 × 공고) ───────────────────────────────────────────
create table group_posts (
  group_id      bigint      not null references groups(id)   on delete cascade,
  posting_id    bigint      not null references postings(id) on delete cascade,
  posted_by     bigint references users(id) on delete set null,
  posted_at     timestamptz not null default now(),
  taken_down_at timestamptz,                     -- "그룹에서 내리기". 행은 남기고 목록에서만 뺀다
  taken_down_by bigint references users(id) on delete set null,
  primary key (group_id, posting_id)
);
create index group_posts_posting_idx on group_posts (posting_id);

-- 관심은 그룹별로 기록한다. 멤버 행에 묶여 있어, 그룹을 나가면 그 그룹의 관심이 함께 지워진다.
create table group_post_interests (
  group_id   bigint      not null,
  posting_id bigint      not null,
  user_id    bigint      not null,
  created_at timestamptz not null default now(),
  primary key (group_id, posting_id, user_id),
  foreign key (group_id, posting_id) references group_posts (group_id, posting_id) on delete cascade,
  foreign key (group_id, user_id)    references group_members (group_id, user_id)  on delete cascade
);
create index group_post_interests_member_idx on group_post_interests (group_id, user_id);

-- 댓글은 "그룹 × 공고"에 달린다. 쓴 사람이 그룹을 나가거나 탈퇴해도 댓글은 남는다.
create table group_post_comments (
  id         bigint generated always as identity primary key,
  group_id   bigint        not null,
  posting_id bigint        not null,
  author_id  bigint references users(id) on delete set null,
  body       varchar(2000) not null,             -- 글자 그대로. 링크는 응답을 만들 때 나눈다
  created_at timestamptz   not null default now(),
  updated_at timestamptz   not null default now(),
  foreign key (group_id, posting_id) references group_posts (group_id, posting_id) on delete cascade
);
create index group_post_comments_post_idx on group_post_comments (group_id, posting_id, created_at);

-- ── 내 공고 (지원 상태의 원본) ────────────────────────────────────────
-- 사용자 × 공고에 한 행. 그룹에는 이 값이 공개 범위만큼만 보인다.
create table user_postings (
  user_id    bigint      not null references users(id)    on delete cascade,
  posting_id bigint      not null references postings(id) on delete cascade,
  decision   varchar(10) not null default 'UNDECIDED'
    check (decision in ('UNDECIDED', 'HOLD', 'SKIP', 'APPLIED')),               -- 미정, 보류, 지원안함, 지원함
  stage      varchar(12)
    check (stage in ('DOCUMENT', 'TEST', 'INTERVIEW_1', 'INTERVIEW_2', 'FINAL')), -- 서류, 필기, 1차 면접, 2차 면접, 최종
  result     varchar(12)
    check (result in ('IN_PROGRESS', 'PASSED', 'FAILED')),                       -- 진행 중, 합격, 불합격
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  primary key (user_id, posting_id),
  check ((decision = 'APPLIED') = (stage is not null)),   -- 단계와 결과는 지원함일 때만 있다
  check ((stage is null) = (result is null))
);
create index user_postings_posting_idx on user_postings (posting_id);
```

### 3.2 설계 이유

- **주소와 키가 같다.** `group_posts`의 키는 (그룹, 공고)다. API 주소 `/groups/{groupId}/posts/{postId}`의 두 값이 그대로 키라서 따로 찾을 것이 없다. `postId`는 공고 본체(`postings`)의 id다.
- **관심은 멤버 행에 묶었다.** `group_post_interests`가 (그룹, 사용자)로 `group_members`를 가리킨다. 멤버가 아닌 사람의 관심은 들어가지 않고, 그룹을 나가면 그 그룹의 관심이 함께 지워진다. 코드에서 따로 지울 필요가 없다.
- **댓글은 쓴 사람이 사라져도 남는다.** 나가기는 댓글에 영향이 없고, 탈퇴하면 `author_id`만 빈다.
- **지원 상태는 그룹이 아니라 사용자 × 공고에 둔다.** 정리 문서의 "지원 상태의 원본은 내 지원 관리의 값"을 그대로 옮겼다. 같은 공고가 두 그룹에 있어도 상태는 하나이고, 그룹마다 공개 범위만큼 보인다.
- **마감은 종류와 날짜 두 칸이다.** 화면의 세 경우(날짜, 상시, 확인 필요)를 `deadline_kind`로 구분하고, 날짜는 `DATE`일 때만 있도록 제약을 걸었다.
- **그룹장은 부분 유일 인덱스로 한 명만 둔다.** 역할은 계정이 아니라 그룹 가입 정보에 있다(정리 문서 7절의 제안).
- **값은 영문 대문자다.** V1의 `provider`, `status`와 같은 방식이다. 화면 글자("지원 여부까지", "필기 단계")는 서버가 응답을 만들 때 바꾼다.
- **`groups`라는 이름.** PostgreSQL에서는 따옴표 없이 테이블 이름으로 쓸 수 있다(실행해 확인했다).

| 그룹 삭제: 그룹 공고·관심·댓글은 지워지고 공고 본체와 내 공고는 남는다 | 통과 |

확인하지 않은 것: JPA 매핑(복합 키 포함), Flyway를 거친 실행, 목록 쿼리의 속도.

2026-11-13 서버에서 더 확인한 것: V3 를 이 절의 SQL 그대로 `V3__groups.sql`로 넣어 Flyway 가 PostgreSQL 16 에 적용했고, 복합 키 테이블(`user_postings`, `group_post_interests`)의 JPA 매핑이 `ddl-auto: validate`를 통과했다. 목록 쿼리의 속도는 아직 재지 않았다.

## 4. API

새로 16개다. 규칙은 설계 초안(로그인·경험카드) 4절과 같다. 주소는 `/api` 아래, 본문은 JSON, 로그인은 세션 쿠키로 확인하고, 바꾸는 요청에는 `X-XSRF-TOKEN`을 붙인다. 오류는 `{ "code": "...", "message": "..." }` 꼴이다. 메서드는 GET, POST, PUT, DELETE만 쓴다. `SecurityConfig`의 CORS 설정이 이 넷만 받는다.

**모든 API에 공통인 오류 코드** (2026-11-13, 서버 `common/error/CommonErrorCode`). 아래 표의 기능별 코드(`GROUP_NOT_FOUND` 등)와 함께 프런트가 처리한다.

| code | HTTP | 언제 |
|---|---|---|
| `INVALID_INPUT` | 400 | 본문을 읽을 수 없거나, 값이 검사를 통과하지 못했거나, 주소의 값 꼴이 틀렸다(`/groups/abc`). 검사에 걸린 칸 이름이 메시지 끝에 붙는다 |
| `UNAUTHENTICATED` | 401 | 로그인하지 않았다 |
| `FORBIDDEN` | 403 | 로그인은 했지만 이 동작을 할 수 없다 |
| `CSRF_INVALID` | 403 | 바꾸는 요청에 `X-XSRF-TOKEN` 헤더가 없거나 `XSRF-TOKEN` 쿠키의 값과 다르다. 화면을 새로 받아 쿠키를 다시 읽은 뒤 보내면 된다 |
| `NOT_FOUND` | 404 | 없는 주소. 없는 그룹·공고는 `GROUP_NOT_FOUND`, `POST_NOT_FOUND`를 쓴다 |
| `METHOD_NOT_ALLOWED` | 405 | 그 주소가 받지 않는 메서드 |
| `INTERNAL_ERROR` | 500 | 서버의 예상하지 못한 오류. 내부 내용은 응답에 싣지 않는다 |

**기능별 오류 코드** (2026-11-13 서버에 넣은 것). "새로"는 초안의 API 표에 없던 코드다.

| code | HTTP | 언제 |
|---|---|---|
| `GROUP_NOT_FOUND` | 404 | 그룹이 없거나 멤버가 아니다(가정 8) |
| `LEADER_CANNOT_LEAVE` | 409 | 그룹장이 나가려 했다(가정 7) |
| `INVITE_NOT_FOUND` | 404 | 새로. 그런 초대 링크가 없다(주소가 잘렸거나 잘못 옮겨졌다) |
| `INVITE_EXPIRED` | 410 | 만료되었거나 취소된 초대 링크 |
| `POST_NOT_FOUND` | 404 | 그 그룹에 없거나 내린 공고 |
| `ALREADY_IN_GROUP` | 409 | 이미 그 그룹에 있는 공고를 올렸다. 본문에 `postId`가 함께 온다: `{ "code": "ALREADY_IN_GROUP", "message": "…", "postId": 12 }` |
| `DEADLINE_ALREADY_SET` | 409 | 마감이 `unknown`이 아닌 공고에 날짜를 넣었다 |
| `COMMENT_NOT_FOUND` | 404 | 새로. 그 공고에 없는 댓글 |
| `POSTING_NOT_FOUND` | 404 | 새로. `PUT /api/me/postings/{postingId}`에서 없는 공고이거나, 내 그룹에도 내 공고에도 없는 공고 |

보는 사람은 기존 `GET /api/me`로 읽는다. 그룹 API의 응답에는 보는 사람과 그룹을 다시 싣지 않는다. 프런트 구조 계획 4절의 방향과 같다.

### 4.1 그룹 (6개)

| 메서드·주소 | 하는 일 | 비고 |
|---|---|---|
| `GET /api/groups` | 내가 속한 그룹들 | 화면의 `Group` 모양: 멤버 목록, 그룹장, 열린 공고 수, 내 공개 범위 |
| `POST /api/groups` | 그룹 만들기 | `name`, `mark`(비우면 이름 첫 글자). 만든 사람이 그룹장이 된다 |
| `PUT /api/groups/{groupId}/me/disclosure` | 이 그룹에 보일 내 공개 범위 바꾸기 | `interest` · `applied` · `progress` |
| `DELETE /api/groups/{groupId}/me` | 그룹 나가기 | 그룹장이면 409 `LEADER_CANNOT_LEAVE`(가정 7) |
| `POST /api/groups/{groupId}/invites` | 초대 링크 만들기 | 응답: 링크, 만료 시각 |
| `POST /api/group-invites/{token}/accept` | 초대 수락 | 이미 멤버면 그대로 성공. 만료·취소된 토큰은 410 `INVITE_EXPIRED` |

만들면서 정한 것(2026-11-13). 초안이 정하지 않은 빈칸이다.

- 그룹 만들기는 201 이고, 만든 그룹을 `GET /api/groups`의 한 항목 모양으로 돌려준다. 이름은 앞뒤 공백을 지운다. 표시 글자의 "이름 첫 글자"는 첫 유니코드 글자다.
- 공개 범위 바꾸기는 바뀐 그룹(같은 모양)을 돌려준다. 나가기는 204 다.
- 초대 링크 만들기는 201 과 `{ "link": "<프런트 주소>/invites/<토큰>", "expiresAt": "2026-11-20T00:30:00+09:00" }`이다. 만료 시각은 초 단위다. 프런트에는 아직 `/invites/:token` 화면이 없다.
- 초대 수락은 들어간 그룹(같은 모양)을 돌려준다. 없는 토큰은 404 `INVITE_NOT_FOUND`다. 이미 멤버면 링크가 만료·취소되었어도 성공으로 본다. 로그인한 사람만 수락한다(로그인 없이 여는 주소는 더하지 않았다).

### 4.2 그룹 공고 (9개)

| 메서드·주소 | 하는 일 | 비고 |
|---|---|---|
| `GET /api/groups/{groupId}/posts` | 그룹 공고 목록 | `{ today, posts }`. 내린 공고는 빼고 마감된 공고는 넣는다 |
| `POST /api/groups/{groupId}/posts` | 그룹에 공고 올리기 | 이미 그 그룹에 있으면 409 `ALREADY_IN_GROUP`과 `postId`. 내렸던 공고면 되살린다 |
| `GET /api/groups/{groupId}/posts/{postId}` | 그룹 공고 상세 | `{ today, post }`. 공고 내용, 키워드, 댓글이 더해진다 |
| `DELETE /api/groups/{groupId}/posts/{postId}` | 그룹에서 내리기 | 올린 사람과 그룹장만. 아니면 403 `FORBIDDEN` |
| `PUT /api/groups/{groupId}/posts/{postId}/deadline` | 날짜 넣기 | 마감이 `unknown`일 때만. 아니면 409 `DEADLINE_ALREADY_SET` |
| `PUT /api/groups/{groupId}/posts/{postId}/interest` | 관심 켜기·끄기 | `{ interested }`를 받아 화면의 `MyState`를 돌려준다. 켤 때 내 공고 행이 없으면 만든다 |
| `POST /api/groups/{groupId}/posts/{postId}/comments` | 댓글 달기 | `{ text }`를 받아 화면의 `Comment`를 돌려준다 |
| `PUT /api/groups/{groupId}/posts/{postId}/comments/{commentId}` | 댓글 수정 | 쓴 사람만 |
| `DELETE /api/groups/{groupId}/posts/{postId}/comments/{commentId}` | 댓글 삭제 | 쓴 사람과 그룹장 |

만들면서 정한 것(2026-11-13). 초안이 정하지 않은 빈칸이다. 앞의 세 줄은 같은 날 확인을 받았다.

- (확인함) 내린 공고는 목록에서만이 아니라 상세, 관심 켜기·끄기, 댓글 달기·수정·삭제, 날짜 넣기에서도 404 `POST_NOT_FOUND`다. 가정 4의 "목록에서만 뺀다"를 "행은 남기되 그룹 안에서는 없는 공고로 본다"로 읽었다. 다시 올리면 행이 되살아나 그대로 보인다.
- (확인함) 댓글 달기는 201 Created 로 답한다. 본문은 앞뒤 공백만 지우고 저장한다. 수정도 같다.
- (확인함) 마감된 공고에도 관심과 댓글을 받는다.
- 올리기는 201 과 상세와 같은 `{ today, post }`를 돌려준다. 회사명·공고명은 앞뒤 공백을 지우고, 빈 `deadlineName`·`applyAt`·`sourceUrl`은 넣지 않은 것으로 본다. 날짜는 마감이 `date`일 때만, 꼭 넣는다(아니면 400 `INVALID_INPUT`).
- 같은 공고는 공고키로 알아본다(가정 3, `posting/PostingKeys`). 다른 그룹에 이미 있는 공고면 그 공고 본체를 함께 쓰고, 그 본체의 값(회사명, 마감 등)은 고치지 않는다. 처음 올린 사람이 넣은 값이 남는다(9절의 "공고 고치기"가 정해지면 다시 본다).
- 내린 공고를 다시 올리면 같은 행이 되살아나고, 올린 사람과 올린 날은 다시 올린 사람과 그날로 바뀐다. 그래서 "새 공고"로 보이고, 다시 올린 사람이 내릴 수 있다.
- 공고키가 300자(칸의 길이)를 넘는 아주 긴 주소는 키를 만들 수 없는 것으로 보고 `posting_key`를 비운다. 이런 공고는 같은 공고로 알아보지 못한다.
- 내리기와 댓글 삭제는 204 다. 이미 내린 공고를 다시 내리면 404 `POST_NOT_FOUND`다.
- 날짜 넣기는 바뀐 마감 `{ "kind": "date", "date": "…" }`을 돌려준다. 지난 날짜도 받는다(넣는 즉시 마감됨이 된다).
- 댓글 수정은 고친 `Comment`를 돌려준다. 그룹장도 남의 댓글은 고치지 못하고 지우기만 한다(5.1). 그 공고의 댓글이 아니면 404 `COMMENT_NOT_FOUND`다.

### 4.3 내 공고 (1개)

| 메서드·주소 | 하는 일 | 비고 |
|---|---|---|
| `PUT /api/me/postings/{postingId}` | 내 지원 상태 바꾸기 | `decision`, `stage`, `result`. 지원 관리 화면이 생길 때까지 "지원함" 표시를 넣는 유일한 길이다. 그 화면을 만들 때 주소와 모양을 다시 본다 |

만들면서 정한 것(2026-11-13). 초안이 정하지 않은 빈칸이다.

- 값은 소문자로 주고받는다. `decision`: `undecided` · `hold` · `skip` · `applied`, `stage`: `document` · `test` · `interview_1` · `interview_2` · `final`, `result`: `in_progress` · `passed` · `failed`. 단계와 결과는 `applied`일 때만, 둘을 함께 넣는다(아니면 400 `INVALID_INPUT`).
- 응답은 `{ "postingId": 12, "decision": "applied", "stage": "test", "result": "in_progress", "status": "필기 단계" }`이다. `status`는 그룹 공고의 `me.status`와 같은 글자(5.3)다.
- 내 그룹에 올라온(내리지 않은) 공고이거나 이미 내 공고에 있는 공고만 바꿀 수 있다. 아니면 404 `POSTING_NOT_FOUND`다. 공고 id 를 넣어 보며 남의 공고를 알아내지 못하게 했다.
- 상태를 넣어도 관심은 저절로 켜지지 않는다(9절의 첫 결정과 이어진다).

### 4.4 응답 모양

`types.ts`의 모양 그대로다. 달라지는 곳은 8절에 모았다.

`GET /api/groups`의 한 항목:

```json
{
  "id": 1,
  "name": "백엔드 스터디",
  "mark": "백",
  "members": [{ "id": 1, "name": "다온" }, { "id": 2, "name": "가람" }],
  "leaderId": 2,
  "openPostCount": 6,
  "myDisclosure": "applied"
}
```

`GET /api/groups/1/posts`:

```json
{
  "today": "2026-11-13",
  "posts": [
    {
      "id": 12,
      "groupId": 1,
      "company": "예시 커머스",
      "title": "백엔드 개발자 신입",

      "interests": [
        { "member": { "id": 2, "name": "가람" }, "applied": true },

        { "member": { "id": 4, "name": "라온" }, "applied": false }

    }

```

상세(`post`)에는 위에 아래가 더해진다.

```json
{
  "deadlineName": "서류 접수 마감",
  "applyAt": "회사 채용 홈페이지",

    {
      "id": 31,
      "author": { "id": 3, "name": "나래" },

      "body": [{ "text": "작년 지원 후기를 찾았어요. " }, { "text": "https://example.com/review", "href": "https://example.com/review" }]
```

```json
{

  "title": "백엔드 개발자 신입",
```

## 5. 규칙

### 5.1 권한

그룹 API는 모두 로그인한 그 그룹의 멤버만 부를 수 있다. 멤버가 아니거나 그룹이 없으면 404 `GROUP_NOT_FOUND`를 준다(가정 8).

| 동작 | 할 수 있는 사람 |
|---|---|
| 보기, 공고 올리기, 관심, 댓글 달기, 날짜 넣기, 초대 링크 만들기 | 그 그룹의 멤버 |
| 그룹에서 내리기 | 올린 사람, 그룹장 |
| 댓글 수정 | 쓴 사람 |
| 댓글 삭제 | 쓴 사람, 그룹장 |
| 공개 범위 바꾸기, 나가기 | 본인 |

### 5.2 공개 범위 적용

`interests`에는 그 그룹에서 관심을 켠 멤버만 나온다. 보는 사람 자신은 빼고 `me`로 따로 준다. 지원 표시는 서버가 그 멤버의 공개 범위에 맞춰 잘라 보낸다.

| 그 멤버의 공개 범위 | `applied` | `progress` |
|---|---|---|
| 관심만(`INTEREST`) | 항상 `false` | 없음 |
| 지원 여부까지(`APPLIED`) | 지원함이면 `true` | 없음 |
| 단계·결과까지(`PROGRESS`) | 지원함이면 `true` | 상태 글자가 "지원함"이 아닐 때 그 글자 |

`me.status`는 내 값이라 공개 범위와 무관하게 준다.

### 5.3 상태 글자

`user_postings`의 세 값을 화면 글자 하나로 바꾸는 규칙이다. `me.status`와 `progress`에 쓴다.

| 결정 | 단계 | 결과 | 글자 |
|---|---|---|---|
| 지원함이 아님 | | | 없음(`null`) |
| 지원함 | 서류 | 진행 중 | 지원함 |
| 지원함 | 필기, 1차 면접, 2차 면접, 최종 | 진행 중 | "필기 단계"처럼 단계 + " 단계" |
| 지원함 | 어느 단계든 | 합격 | "서류 합격"처럼 단계 + " 합격" |
| 지원함 | 어느 단계든 | 불합격 | "필기 불합격"처럼 단계 + " 불합격" |

### 5.4 날짜

- `today`는 서버의 한국 날짜(`Asia/Seoul`)다. 서버 시간대와 무관하게 계산한다.
- 마감됨은 `deadline_date < today`다. 마감일 당일은 진행 중이다. 프런트의 `isClosed`와 같다.
- 열린 공고 수도 같은 `today`로 센다.
- `postedAt`은 올린 시각의 한국 날짜("YYYY-MM-DD")다. 댓글의 `createdAt`만 시각까지 ISO 8601로 준다.

| 10 | 내린 공고의 뒤처리 | 댓글과 관심이 사라지거나, 다시 올릴 때 유일 제약에 걸린다 | 가정 4 | |

## 7. 화면과 API 대응

| 화면 | 쓰는 API |
|---|---|
| 헤더(그룹 전환, 내 계정) | `GET /api/me`, `GET /api/groups` |
| 그룹 공고 목록 | `GET …/posts`. 관심 켜기·끄기는 `PUT …/interest`, 날짜 넣기는 `PUT …/deadline`, 공고 올리기는 `POST …/posts` |
| 그룹 공고 상세 | `GET …/posts/{postId}`. 관심은 `PUT …/interest`, 그룹에서 내리기는 `DELETE …/posts/{postId}`, 댓글은 `POST`·`PUT`·`DELETE …/comments`, 공개 범위 바꾸기는 `PUT …/me/disclosure` |
| 화면이 아직 없는 것 | `POST /api/groups`, `DELETE …/me`, `POST …/invites`, `POST /api/group-invites/{token}/accept`, `PUT /api/me/postings/{postingId}` |

프런트의 `api.ts` 함수와의 대응: `getMyGroups` → `GET /api/groups`, `getGroupPosts` → `GET …/posts`, `getGroupPost` → `GET …/posts/{postId}`, `setInterest` → `PUT …/interest`, `addComment` → `POST …/comments`.

## 8. 프런트와 맞출 것

1. id가 숫자다. `types.ts`의 `id: string`을 바꾸거나 서버가 문자열로 보낸다(가정 11).
2. 목록과 상세 응답에 `viewer`, `group`이 없다. `{ today, posts }`, `{ today, post }`만 온다.
3. `postedBy`와 댓글의 `author`가 `null`일 수 있다(탈퇴한 사람). 지금 타입은 `Member`다.
4. 올리기가 409 `ALREADY_IN_GROUP`을 주면 응답의 `postId`로 기존 공고에 보낸다.
5. `progress` 글자가 예시 데이터의 "면접 단계"가 아니라 "1차 면접 단계"처럼 온다(5.3).
6. "새 공고"는 프런트가 `postedAt`과 `today`로 정한다. 서버는 값을 주지 않는다.
7. 없는 그룹과 공고는 404에 `GROUP_NOT_FOUND`, `POST_NOT_FOUND`로 온다. 지금의 `NotFoundError`에 대응한다.
8. (2026-11-13 서버를 만들며 더함) `GET /api/groups`의 `leaderId`가 `null`일 수 있다(그룹장이 계정을 지운 그룹, 9절). 지금 타입은 `string`이다.
9. (같은 날) `GET /api/me`는 `Viewer`의 `id`, `name`에 `email`, `hasPassword`, `providers`(예: `["google"]`)를 더해 준다. 프런트는 둘만 쓰면 된다.
10. (같은 날) 서버가 만든 댓글의 `createdAt`은 `2026-11-13T16:56:26.381516+09:00`처럼 소수 초가 붙을 수 있다. 예시 데이터의 댓글은 초까지다.
11. (같은 날) 그룹 목록은 내가 들어간 순서다. 첫 화면이 가는 "내 첫 그룹"은 처음 들어간 그룹이다.
12. (같은 날) 로그인하지 않은 요청은 모두 401 `UNAUTHENTICATED`다. 서버를 붙일 때 로그인 전 처리가 필요하다. 지금은 dev 프로필의 임시 로그인(`POST /api/auth/dev-login`, `backend/CLAUDE.md`)으로 들어간다.
13. (같은 날, 나머지 API) 올리기의 409 `ALREADY_IN_GROUP`은 `postId`를 본문의 맨 위 칸으로 준다(4절의 기능별 오류 코드 표). 8절 4번의 "응답의 `postId`"가 이것이다.
14. (같은 날) 초대 링크는 `<프런트 주소>/invites/<토큰>`이다. 프런트에 이 화면을 만들고, 로그인한 뒤 `POST /api/group-invites/{token}/accept`를 부르면 된다.
15. (같은 날) 그룹 만들기·공개 범위 바꾸기·초대 수락은 `Group` 모양을, 올리기는 상세와 같은 `{ today, post }`를, 날짜 넣기는 `Deadline`을, 댓글 수정은 `Comment`를 돌려준다. 받은 값으로 화면의 그 부분만 바꾸면 된다.

## 9. 새로 생긴 결정

| 항목 | 내용 | 선택지 |
|---|---|---|
| 지원 상태는 있는데 그 그룹에서 관심은 꺼져 있을 때 | 다른 그룹에서 관심을 켜고 지원한 공고가 이 그룹에도 있으면 생긴다. 지금 화면은 나를 관심 멤버 칸에 넣고 상태 알약을 보여 주는데, 다른 멤버에게는 내가 보이지 않는다 | 내 화면에서도 관심 멤버에 넣지 않는다 / 지원할 때 그 공고가 있는 내 그룹에 관심을 켤지 묻는다 |
| 지원한 뒤 관심 끄기 | 상태가 있으면 화면에 관심 버튼 대신 상태 알약만 나온다. 끌 방법이 없다 | 상세에 끄기를 둔다 / 내 공고에서 "지원안함"으로 바꿀 때 끌지 묻는다(정리 문서의 남은 세부와 같은 질문) |
| 그룹장이 없어질 때 | 그룹장은 나갈 수 없게 했지만 계정을 지우면 그룹장 없는 그룹이 남는다 | 넘기기 API를 둔다 / 가장 먼저 들어온 멤버가 이어받는다 / 탈퇴하기 전에 넘기게 막는다 |
| 공고 고치기 | 회사명, 공고명, 마감을 잘못 올렸을 때 고칠 길이 없다. 날짜 넣기는 한 번뿐이다 | 올린 사람이 고친다 / 멤버 누구나 고친다 / 내리고 다시 올린다 |
| 초대 | 누가 만드는지, 며칠 가는지, 인원 제한이 있는지 | 가정 6의 값(멤버 누구나, 7일, 제한 없음) / 그룹장만 |
| 로그인과의 순서 | 그룹 API는 로그인이 있어야 부를 수 있다 | **정함(2026-11-13)**: dev 프로필에서만 켜지는 임시 로그인을 두고 그룹부터 만든다. 임시 로그인은 실제 로그인과 같은 세션을 만들고, 실제 로그인을 만들 때 걷어낸다(`backend/CLAUDE.md`) |

정리 문서 7절의 지원 상태 값의 구조, 같은 공고 판별, 공고 단위, 필수값 목록, 링크 처리도 이 설계에 걸려 있다.

## 10. 패키지와 옮길 것

기존 패키지(`auth`, `card`, `extraction`, `keyword`, `llm`, `common`) 옆에 셋을 더하는 안이다.

| 패키지 | 테이블 | API |
|---|---|---|
| `com.readme.group` | `groups`, `group_members`, `group_invites` | `/api/groups`, `/api/group-invites` |
| `com.readme.posting` | `postings`, `posting_keywords`, `user_postings` | `/api/me/postings` |
| `com.readme.grouppost` | `group_posts`, `group_post_interests`, `group_post_comments` | `/api/groups/{groupId}/posts/**` |

jobfit에서 이 단계에 필요한 것은 `jobkey.py`(공고키) 하나다. 정리 문서의 옮기는 순서표 2번에 들어 있다. 필수값 읽기, 섹션 정규식, 사이트별 수집 규칙, 공고 분석은 공고 등록의 자동 채우기를 만들 때 옮긴다.

(2026-11-13) `jobkey.py`의 `derive`, `normalize_url`을 `com.readme.posting.PostingKeys`로 옮겼다. `tests/test_jobkey.py`의 테스트 6개를 JUnit 으로 먼저 옮겼고, `jobkey.py`를 Python 3.13 으로 직접 돌려 얻은 값 12개(쿼리 인코딩, 잘못된 퍼센트 인코딩, 스킴 없는 주소 등)도 같이 맞춘다. 게시처 판정(`kind`)과 폴더 이름(`key_to_dirname`)은 쓰는 곳이 없어 옮기지 않았다.
