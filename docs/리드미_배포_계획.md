# 리드미 배포 계획 초안

2026-11-12 기준. 수익화까지 가는 것을 전제로, 프런트는 Cloudflare Pages 무료 플랜, 서버는 AWS(남은 크레딧 100달러)에 올리는 구성이다. 가격과 한도는 이날 조회한 값이다.

- 설계 초안: `claude/리드미_설계_로그인_경험카드.md`
- 정리 문서: `claude/리드미_리서치_재사용_정리.md`

## 1. 구성

```
브라우저
 ├─ app.도메인 ─→ Cloudflare Pages (React 빌드 결과)
 └─ api.도메인 ─→ Cloudflare 프록시 ─→ AWS Lightsail 서울 (Caddy → Spring Boot)
                                          ├─→ Supabase Postgres 서울
                                          ├─→ Claude API
                                          └─→ Amazon SES (가입 확인·재설정 메일)

채용 메일 ─→ Cloudflare Email Routing ─→ Worker ─→ api.도메인   (메일 자동화, 나중)
```

| 부분 | 둘 곳 | 월 비용 | AWS 크레딧 |
|---|---|---|---|
| 프런트 | Cloudflare Pages 무료 | 0 | 해당 없음 |
| DNS, 프록시 | Cloudflare 무료 | 0 | 해당 없음 |
| 서버 | AWS Lightsail 서울, 2GB | 12달러 | 적용(4절 확인 필요) |
| DB | Supabase 무료 → 유료 사용자가 생기면 Pro | 0 → 25달러 | 적용 안 됨 |
| 메일 발송 | Amazon SES | 1,000통에 0.10달러 | 적용 |
| 도메인 | 등록처에서 구입 | 연 단위, 별도 | 적용 안 됨 |

프런트와 서버를 `app`, `api` 하위 주소로 나누는 이유: 세션 쿠키는 같은 사이트 안에서만 문제없이 동작한다. 같은 도메인의 하위 주소는 같은 사이트다. `/api`를 Pages에서 서버로 넘기는 방식은 Pages Functions를 거쳐야 해서 무료 한도(하루 100,000건)를 쓴다. 하위 주소로 나누면 Functions를 쓰지 않는다.

## 2. 프런트: Cloudflare Pages 무료로 충분한가

충분하다. 정적 파일 요청에는 한도가 없고, 걸릴 수 있는 것은 빌드 횟수뿐이다.

| 항목 | 무료 플랜 | 리드미에서 |
|---|---|---|
| 정적 파일 요청 | 무료, 무제한 | React 화면은 전부 정적 파일이다 |
| 빌드 | 월 500회, 동시 1개, 20분 제한 | 하루 약 16회. `frontend` 폴더가 바뀔 때만 빌드하게 한다 |
| 파일 수, 크기 | 20,000개, 파일당 25MiB | Vite 빌드 결과는 수십~수백 개 |
| 사용자 도메인 | 프로젝트당 100개 | 1개 |
| Functions | Workers 무료 한도(하루 100,000건)에 포함 | 쓰지 않는다 |
| 화면 주소 처리 | 최상위에 `404.html`이 없으면 모든 경로에 첫 화면을 내보낸다 | React 라우터가 그대로 동작한다 |

- Vercel 무료(Hobby) 플랜은 비상업 개인 용도로만 쓸 수 있다. 결제 요청·처리, 상품 판매 광고, 광고 게재가 상업 이용 예시로 적혀 있다. 수익화하면 Pro가 필요하다.
- Cloudflare Pages의 한도 문서에는 비상업 조건이 없다. 약관 전체에서 상업 이용 금지 조항을 따로 확인하지는 못했다.

## 3. 서버

### 3.1 선택지와 비용

| 안 | 구성 | AWS 월 비용 | 100달러로 | 비고 |
|---|---|---|---|---|
| A | Lightsail 2GB + Supabase 무료 | 12달러 | 8.3개월 | 시작점으로 고른 안 |
| B | Lightsail 1GB + Supabase 무료 | 7달러 | 14.3개월 | 크레딧 만료가 먼저 온다. 메모리가 빠듯할 수 있다 |
| C | Lightsail 2GB에 Postgres까지 설치 | 12달러 + 스냅샷 | 약 8개월 | DB 운영과 백업을 직접 한다. Supabase를 쓰지 않는다 |
| D | Lightsail 1GB + Lightsail 관리형 DB | 22달러 | 4.5개월 | 15달러 DB는 메모리 1GB, 암호화 없음 |
| E | EC2 t4g.small + 공인 IPv4 + RDS db.t4g.micro | 36.8달러 이상 | 2.7개월 | 디스크 비용 별도 |

- Lightsail 가격(공인 IPv4 포함): 0.5GB 5달러, 1GB 7달러, 2GB 12달러, 4GB 24달러. 모두 vCPU 2개이고 디스크(20~80GB)와 전송량(1~4TB), 고정 IP가 포함된다. 서울은 전송량이 절반으로 줄어드는 리전 목록에 없다.
- E안 계산: EC2 t4g.small 서울 시간당 0.0208달러 × 730시간 = 15.18달러, 공인 IPv4 시간당 0.005달러 × 730시간 = 3.65달러, RDS db.t4g.micro 약 18달러. IPv4 단가는 이번에 다시 조회하지 않은 값이다.

**A안을 고른 이유**

- "개발은 로컬 Postgres, 올릴 때 Supabase"라는 순서와 맞다. 무료에서 Pro로는 결제만 바꾸면 되어 DB를 옮길 일이 없다.
- 서버에 Spring Boot만 올라가 서버를 새로 만들어도 데이터가 영향받지 않는다.
- 2GB는 추정이다. Spring Boot에 PDF·HWP·DOCX 읽기가 더해져 1GB는 빠듯할 수 있다고 봤다. 띄워서 실제 메모리를 본 뒤 1GB로 내릴 수 있다. 크레딧이 남아 있는 동안은 차액 부담이 없다.

**C안이 나은 경우**: 크레딧을 서버 한 곳에 다 쓰고 외부 서비스를 하나라도 줄이고 싶을 때. 대신 백업(매일 덤프, 스냅샷은 GB당 월 0.05달러)을 직접 챙겨야 하고 나중에 Supabase로 옮기는 작업이 생긴다.

### 3.2 서버에 올리는 방법

| 단계 | 내용 |
|---|---|
| 한 번만 | Lightsail 인스턴스(서울, Ubuntu) 생성, 고정 IP 연결, 방화벽은 443과 22만 연다 |
| 한 번만 | Java 실행 환경과 Caddy 설치. Caddy가 HTTPS를 받아 Spring Boot(8080)로 넘긴다 |
| 한 번만 | Spring Boot를 systemd 서비스로 등록. 비밀 값은 서버의 환경변수 파일에 둔다 |
| 한 번만 | Cloudflare에서 `api.도메인`을 서버 IP로 연결(프록시 켬) |
| 매번 | GitHub Actions: `backend` 폴더가 바뀌면 테스트 → JAR 빌드 → 서버로 복사 → 서비스 재시작 → 상태 확인 주소 호출 |

- 다른 방식: Docker Compose. 이미지를 빌드해 저장소에 올리고 서버가 받아 실행한다. 서버 환경이 코드로 남는 대신 이미지 저장소와 Docker가 추가된다. 서버에 올라가는 것이 Spring Boot 하나라서 JAR + systemd로도 충분하다고 봤다.
- 재시작하는 동안 수십 초가량 응답이 끊긴다(추정). 이 단계에서는 감수하고, 진행 중이던 추출 작업은 이어서 돌게 만든다(6절).
- Cloudflare 프록시를 거치면 요청 하나가 125초 안에 응답해야 한다(무료 플랜에서는 바꿀 수 없다). LLM을 부르는 일은 설계 초안대로 비동기 작업 + 상태 조회로 둔다.

## 4. AWS 크레딧 조건

남은 100달러가 2025년 7월 이후 새 계정에 주는 가입 크레딧이라면 아래가 적용된다. 다른 종류의 크레딧이면 조건이 다르다.

| 항목 | 내용 |
|---|---|
| Free 플랜의 끝 | 계정을 만든 지 6개월 또는 크레딧 소진 중 먼저 오는 때. 계정이 닫히고 자원과 데이터에 접근할 수 없다 |
| 닫힌 뒤 | 90일 동안 보관. 그 안에 Paid 플랜으로 올리지 않으면 삭제된다 |
| Paid 플랜으로 올리면 | 남은 크레딧은 이후 청구서에 자동 적용된다. 크레딧을 넘는 사용분은 카드로 청구된다 |
| 크레딧 만료 | FAQ의 플랜 전환 설명에는 계정 생성 12개월 뒤라고 적혀 있다. 같은 FAQ에 6개월이라는 문장도 있어 콘솔에서 만료일을 확인해야 한다 |
| Free 플랜의 서비스 범위 | 일부 서비스만 쓸 수 있다. Lightsail이 포함되는지는 문서에서 확인하지 못했다 |

- **실제 서비스를 올리려면 Paid 플랜이어야 한다.** Free 플랜은 기한이 오면 계정이 닫힌다.
- **크레딧의 실제 값은 남은 기간에 달려 있다.** 만료까지 4개월 남았다면 월 12달러로는 48달러만 쓴다.
- 확인할 곳: 콘솔 첫 화면의 Cost and Usage 위젯(잔액, 남은 일수), Billing의 Credits(만료일).

## 5. DB와 메일

**DB: Supabase**

- 리전은 서울(`ap-northeast-2`)을 고를 수 있다. 서버와 같은 리전에 둔다.
- 서버에서는 세션 모드 풀러 주소(IPv4, 포트 5432)로 붙는다. 서버 쪽 IPv6 설정이 필요 없다.
- 무료 플랜: 500MB, 1주일 미사용 시 일시 정지, 자동 백업 없음. 시범 운영 동안은 서버에서 매일 덤프를 떠 외부에 둔다.
- 용량 추정: 자료 본문과 카드가 글자뿐이라 사용자 한 명에 0.2MB 정도로 잡으면 500MB는 2,000명 이상이다. 공고 본문이 쌓이면 달라진다.
- 유료 사용자가 생기면 Pro(월 25달러, 7일치 일일 백업, 일시 정지 없음)로 올린다.

**메일 발송: Amazon SES**

- 1,000통에 0.10달러. 가입 확인·재설정 메일 규모에서는 사실상 0이고 크레딧 적용 대상이다.
- 새 SES 계정은 인증한 주소로만 보낼 수 있는 상태로 시작한다. 도메인을 인증하고 운영 전환을 신청해야 한다.
- Cloudflare Email Service의 발송은 임의의 수신자에게 보내려면 Workers Paid 플랜이 필요해 뺐다.

**메일 수신(메일 자동화): Cloudflare Email Routing**

- 수신은 무료이고 건수 제한이 없다. 메일 크기는 25MiB까지다.
- 받은 메일을 Worker로 넘길 수 있다. Worker가 내용을 `api.도메인`으로 보낸다. Worker 호출은 하루 100,000건 한도에 포함된다.
- 규칙은 도메인당 200개다. 사용자마다 규칙을 하나씩 만드는 방식은 안 된다. 모든 주소를 한 규칙으로 받는 설정이 되는지는 문서에서 확인하지 못했다.

## 6. 배포를 고려해 뼈대에 미리 넣을 것

| # | 항목 | 이유 |
|---|---|---|
| 1 | 설정을 전부 환경변수로: DB 주소, 구글 클라이언트 값, Claude API 키, 메일 계정, 프런트 주소, 쿠키 도메인 | 로컬과 운영이 같은 코드로 돈다. 비밀 값이 저장소에 들어가지 않는다 |
| 2 | `dev`, `prod` 프로필 | dev는 로컬 Postgres(Docker)와 Vite 프록시, prod는 Supabase와 SES |
| 3 | CORS: `app.도메인` 하나만 허용, 쿠키 포함 허용 | 하위 주소 둘로 나눴기 때문 |
| 4 | 프런트의 모든 요청에 쿠키 포함(`credentials: 'include'`), API 주소는 빌드 환경변수 | 위와 같다 |
| 5 | 세션 쿠키 `Secure; HttpOnly; SameSite=Lax`, CSRF 쿠키는 상위 도메인으로 | `app` 화면의 스크립트가 CSRF 값을 읽어 헤더에 실어야 한다 |
| 6 | 프록시 뒤 설정(`server.forward-headers-strategy`) | 구글 로그인이 돌아올 주소가 `https://api.도메인`으로 만들어져야 한다 |
| 7 | 상태 확인 주소(Actuator health) | 배포 뒤 확인과 감시에 쓴다 |
| 8 | 추출 작업 이어하기: 서버가 뜰 때 `RUNNING`으로 남은 작업을 다시 돌린다 | 배포로 재시작되면 작업이 끊긴다. `done_parts`가 있어 조각 단위로 이어진다 |
| 9 | 종료 대기(`server.shutdown=graceful`) | 처리 중인 요청을 끝내고 내려간다 |
| 10 | 올리기 크기 제한(예: 20MB), DB 연결 수 작게(예: 5) | 서버 메모리와 Supabase 무료 플랜의 연결 수 |
| 11 | GitHub Actions 둘: `backend` 경로, `frontend` 경로 | 바뀐 쪽만 배포한다. 프런트는 Pages의 Git 연동으로 대신할 수 있다 |

## 7. 단계

| 단계 | 하는 일 | 비용 |
|---|---|---|
| 지금: 개발 | 로컬에서 Postgres(Docker), Vite 프록시, 메일은 로컬 수신기로 확인 | 0 |
| 첫 배포: 지인 그룹 시범 운영 | 도메인 구입 → Cloudflare에 연결 → Pages(`app`) → Lightsail(`api`) → Supabase 무료 → SES 운영 전환 → 구글 로그인 돌아올 주소 등록 | AWS 월 12달러(크레딧), 도메인 |
| 수익화 | AWS Paid 플랜, Supabase Pro, 서버 크기 재검토 | 월 37달러 + 도메인 |

## 8. 정할 것과 확인하지 못한 것

**정할 것**

| 항목 | 선택지 |
|---|---|
| 도메인 | 이름과 등록처. 메일 자동화의 수신 주소에도 쓴다 |
| 서버 크기 | 2GB(12달러, 초안) / 1GB(7달러) |
| DB를 처음 둘 곳 | Supabase 무료(초안) / 같은 서버 |
| 서버 배포 방식 | JAR + systemd(초안) / Docker Compose |
| 저장소 | 모노레포(`backend`, `frontend`) / 저장소 둘 |

**확인하지 못한 것**

- AWS: 계정의 플랜과 크레딧 만료일, Free 플랜에서 Lightsail을 만들 수 있는지, EC2 디스크와 RDS 저장소 가격.
- Cloudflare: 무료 플랜의 상업 이용 조항, Email Routing에서 모든 주소를 한 규칙으로 Worker에 넘기는 설정.
- 서버 메모리: 1GB로 충분한지는 띄워 봐야 안다.
- 구글: 기본 범위만 쓰는 앱이 운영 상태에서 인증 없이 되는지(설계 초안 8절).
