# 리드미 설계: 경험카드 우선순위

2026-11-23. 내 공고 상세에서 "공고 내용"과 "나만 보는 메모" 사이에, 이 공고에 먼저 쓸 경험카드를 순서대로 둔다. 초안은 LLM이 짜고, 그 뒤에는 사용자가 순서를 바꾸고 빼고 더한다. 시안은 없다.

- 옆 칸의 "맞는 카드"(공고 설계 4.8, `CardMatching`)는 규칙으로 센 요건별 결과이고 그대로 둔다. 우선순위는 사용자가 고쳐 저장하는 목록이다.
- LLM 바탕: 경험카드 문서 4.5(`LlmFeature.CARD_PRIORITY`, effort `low`, 출력 상한 8,000)

## 1. 범위

이 문서에 있는 것: 테이블, 초안 만들기와 순서 바꾸기 API, LLM에 보내는 것.

이 문서에 없는 것: 문항별로 카드를 배정하기(맞는 카드의 "옮기지 않은 것"), 그룹 공고 상세의 우선순위(내 공고에만 둔다).

## 2. 정한 것

| # | 항목 | 정한 값 | 이유 |
|---|---|---|---|
| CP1 | 초안을 만드는 때 | **정함(2026-11-23, 사용자 결정)**: 사용자가 "LLM으로 초안 만들기"를 누를 때만. 공고 분석처럼 저절로 돌리지 않는다 | 사용액은 사람마다 한 달 한도가 있다. 카드가 바뀐 뒤 다시 짜고 싶을 때도 같은 버튼이다 |
| CP2 | 목록의 크기와 내용 | **정함(2026-11-23, 사용자 결정)**: 5장까지. LLM이 고른 카드에는 고른 이유 한 줄(60자 안을 바라고, 200자에서 자른다)이 붙는다. 사용자가 더한 카드는 이유가 없다 | |
| CP3 | 순서 바꾸기 | **정함(2026-11-23, 사용자 결정)**: 끌어서 옮기기와 위·아래 버튼을 함께 둔다. 빼기, 다른 카드 더하기도 된다. 바꿀 때마다 목록 전체를 저장한다 | 버튼은 키보드와 화면 읽기 프로그램을 위한 길이다 |
| CP4 | 새 초안과 앞 목록 | 새 초안은 앞 목록을 통째로 바꾼다. 화면은 앞 목록이 있으면 바꿀지 먼저 묻는다 | |
| CP5 | LLM에 보내는 것 | 공고는 분석(필수·우대·업무·키워드)을, 분석이 없으면 공고 내용 묶음(공고 분석과 같은 순서·길이 규칙, 연락처를 가림)을 보낸다. 카드는 최근에 고친 60장까지, 칸마다 300자까지(제목, 경험 이름, 기간, 역할, 요약, 상황·과제·행동·결과, 어려움, 배운 점, 태그) | 카드가 많으면 오래 고치지 않은 카드가 빠진다(코드의 `shortcut:`) |
| CP6 | LLM 답 검사 | 내 카드가 아닌 id와 겹친 id는 버리고 앞에서 5장까지 둔다. 남는 것이 없으면 빈 목록으로 저장한다 | 지어낸 id가 남의 카드를 가리키지 못하게 |
| CP7 | 함께 지워지는 것 | 카드를 지우면 그 줄이, 내 공고에서 빼면 목록 전체가 외래 키로 지워진다 | |

## 3. 테이블

`V13__user_posting_cards.sql`(파일이 원본이다). 주인은 `posting` 패키지다(`user_postings`와 같다).

```sql
create table user_posting_cards (
  user_id    bigint       not null,
  posting_id bigint       not null,
  card_id    bigint       not null references experience_cards(id) on delete cascade,
  position   smallint     not null,              -- 0 이 첫째
  reason     varchar(200),                       -- LLM 이 고른 이유. 사용자가 더한 카드는 null
  primary key (user_id, posting_id, card_id),
  foreign key (user_id, posting_id) references user_postings(user_id, posting_id) on delete cascade
);
```

## 4. API

| API | 하는 일 | 응답 |
|---|---|---|
| `GET /api/me/postings/{postingId}` | 상세에 `cardPriority`가 더해진다 | `[{ cardId, title, experience, reason }]`, 첫째가 앞. 없으면 `[]` |
| `POST /api/me/postings/{postingId}/card-priority/draft` | LLM 초안을 만들어 앞 목록을 바꾼다 | `{ cards: [...] }` (위와 같은 모양) |
| `PUT /api/me/postings/{postingId}/card-priority` | 본문 `{ "cardIds": [3, 1] }`(5개까지, `[]`이면 비운다)의 순서로 둔다. 앞 목록에 있던 카드는 이유가 남는다 | `{ cards: [...] }` |

### 4.1 만들면서 정한 것

- 초안: 한도 검사와 LLM 호출은 트랜잭션 밖이다. 저장은 한 트랜잭션에서 내 공고 행을 `for update`로 잠근 뒤 지우고 다시 넣는다. 그래서 같은 사람이 두 번 함께 눌러도 기본 키 충돌 없이 나중 것이 남는다.
- 실패하면(한도, LLM 오류) 앞 목록은 그대로다.

### 4.2 오류 코드

| 코드 | HTTP | 때 |
|---|---|---|
| `POSTING_NOT_FOUND` | 404 | 내 공고에 없는 공고(두 API) |
| `NO_CARDS` | 409 | 초안: 내 경험카드가 하나도 없다 |
| `NO_POSTING_CONTENT` | 409 | 초안: 공고 분석도 공고 내용 묶음도 없다 |
| `LLM_LIMIT_REACHED` | 429 | 초안: 이번 달 한도에 닿았다 |
| `LLM_UNAVAILABLE` / `LLM_FAILED` | 503 / 502 | 초안: 답을 못 받았다 / 쓸 수 없는 답이다(사용액은 든다) |
| `INVALID_INPUT` | 400 | 바꾸기: `cardIds`가 없거나 5개를 넘거나, 겹치거나, 내 카드가 아닌 id가 있다 |
