# 리드미 설계 초안: 로그인·경험카드

2026-11-12 기준. 화면구조도에서 먼저 만들기로 한 화면 8개의 테이블 구조와 API 목록이다. 초안이고, 2절의 가정은 바꿀 수 있다.

- 화면구조도: https://claude.ai/artifact/4HhMKRTdrUmF6yqrV33zvV
- 정리 문서: `claude/리드미_리서치_재사용_정리.md`
- 화면마다 쓰는 API와 설계에 없는 것: `claude/리드미_화면_API_대응.md`

2026-11-13에 이 여덟 화면의 시안이 모두 나왔고, 로그인, 회원가입, 이메일 인증, 비밀번호 재설정, 카드 목록은 프런트에 들어갔다(가짜 서버를 부른다. 프런트가 기대는 것은 화면·API 대응 문서 4절). 서버에는 이 초안의 API 중 `GET /api/me`만 있다. 세션은 실제 로그인이 쓸 것을 이미 쓰고, 들어가는 길은 dev 프로필의 임시 로그인이다(`backend/CLAUDE.md`). 시안이 요구하는데 이 초안에 없는 것은 화면·API 대응 문서 3.4절과 3.5절에 모았다.

## 1. 범위

| 묶음 | 화면 |
|---|---|
| 로그인 | 로그인, 회원가입, 이메일 인증, 비밀번호 재설정 |
| 경험카드 | 카드 목록, 카드 상세·편집, 자료로 카드 만들기, 카드 확인 |

정해진 것: Spring Boot, React + Vite, PostgreSQL(나중에 Supabase에 올림), 로그인은 구글 + 이메일·비밀번호, 인증은 Spring Security가 맡음, 로그인 유지는 서버 세션 쿠키.

이 초안에 없는 것: 탈퇴, 내 정보 고치기, 가입·재설정 요청 횟수 제한, 스캔본·이미지 자료 읽기(OCR 대체가 미정). 그룹과 그룹 공고는 `claude/리드미_설계_그룹_공고.md`에 따로 있다.

## 2. 초안이 깔고 있는 가정

정해지지 않은 부분은 아래 값으로 두고 설계했다. 다른 선택지를 고르면 오른쪽 칸이 바뀐다.

| # | 항목 | 초안의 값 | 다른 선택지 | 바뀌는 곳 |
|---|---|---|---|---|
| 1 | 인증 담당 | **확정**: Spring Security. Supabase는 DB로만 쓴다 | Supabase Auth(구글·이메일 가입, 인증 메일 포함) | 계정 테이블 3개와 인증 API 전부 |
| 2 | 로그인 유지 | **확정**: 서버 세션 쿠키(Spring Session JDBC) | JWT(access + refresh) | 세션 테이블, 프런트 요청 방식, CSRF 처리 |
| 3 | 계정 연결 | 구글 이메일과 같은 이메일의 계정이 있으면 한 계정으로 연결(아래 3.2) | 항상 별도 계정 / 로그인한 상태에서만 직접 연결 | 구글 콜백 로직. 테이블은 같다 |
| 4 | 인증 전 계정 | 이메일 인증 전에는 로그인 불가 | 로그인은 되고 기능만 제한 | 로그인 API, 프런트 안내 |
| 5 | 스키마 | 전용 스키마 `readme` | `public` | JDBC 주소 한 곳 |
| 6 | 태그·문항 유형 저장 | 카드별 행으로 따로 저장 | Postgres 배열(`text[]`) | 필터 쿼리, JPA 매핑 |
| 7 | 올린 원본 파일 | 저장하지 않는다. 읽어 낸 본문만 둔다 | 파일도 보관(디스크 / 객체 저장소) | `card_sources`, 파일 저장 위치 결정 |
| 8 | 추출 실행 | 서버 안 비동기 작업 + 상태 조회 | 요청 하나가 끝까지 기다림 / SSE | `card_extraction_jobs`, 진행 표시 |
| 9 | 카드 공개 범위 | 칸만 두고 값은 `PRIVATE` 하나 | 그룹을 만들 때 값 추가 | `visibility` 제약 |
| 10 | 추출된 카드 | 바로 카드 목록에 들어가고 `verified = false`(jobfit과 같다) | 확인 전에는 임시 테이블에 둔다 | 카드 확인 화면, 테이블 1개 |
| 11 | 토큰 유효 시간 | 가입 확인 24시간, 비밀번호 재설정 1시간 | 다른 값 | 설정값 |

1번과 2번은 2026-11-12에 확정했다. 3~11번은 아직 가정이다.

**1번을 Spring Security로 정한 이유**

- Supabase Auth를 쓰면 첫날부터 Supabase가 필요하다. "지금은 Postgres, Supabase는 나중에 생각"이라는 순서와 맞지 않는다.
- 계정이 Supabase의 `auth.users`에 생기고 리드미 데이터는 Spring이 관리하는 테이블에 있어, 사용자 저장소가 둘이 된다. 탈퇴·그룹 초대처럼 계정을 건드리는 기능마다 Spring이 Supabase 관리 API를 불러야 한다.
- Supabase Auth가 덜어 주는 것 중 메일 발송은 실제로는 덜어지지 않는다. 기본 메일 서버는 팀 구성원 주소로만 보내고 시간당 2통 제한이며 운영용이 아니라고 문서에 적혀 있다. 어느 쪽이든 발송 수단을 따로 붙여야 한다.
- 남는 차이는 가입·인증·재설정 API 7개를 직접 만드느냐인데, Spring Security가 비밀번호 해시, 구글 로그인, 세션, CSRF를 이미 제공한다.
- 잃는 것: Supabase Auth의 요청 횟수 제한, 유출 비밀번호 검사, 2단계 인증 같은 기능은 필요해지면 직접 붙여야 한다.

**2번을 세션 쿠키로 정한 이유**

- 접속하는 쪽이 React 웹 화면 하나다. JWT가 유리한 경우(모바일 앱, 외부 개발자용 API, 서버 여러 대가 서로 호출)가 지금 없다.
- Spring Security의 구글 로그인은 기본이 세션 방식이다. JWT로 가면 구글 로그인 중간 상태 보관, 토큰 발급, refresh 토큰 보관·교체·폐기를 직접 만들어야 한다. 직접 만드는 보안 코드가 늘어난다.
- 로그아웃, 비밀번호 재설정, 탈퇴, 그룹 강퇴가 즉시 반영된다. 세션 행을 지우면 끝이다. JWT는 만료 전까지 유효해서 차단 목록을 따로 둬야 한다.
- 쿠키를 `HttpOnly`로 두면 화면의 스크립트가 로그인 정보를 읽을 수 없다.
- 세션을 DB에 두므로(Spring Session JDBC) 서버를 다시 배포해도 로그인이 풀리지 않는다.
- 조건: 프런트와 서버가 같은 사이트 주소 아래 있어야 한다(9절). 메일 자동화에 쓸 도메인이 어차피 필요하므로 그 도메인 아래 두면 된다. 개발 때는 Vite 프록시로 `/api`를 서버에 넘긴다.
- 나중에 모바일 앱이나 리드미 커넥터가 생기면 그쪽에만 토큰 인증을 추가한다. 웹의 세션은 그대로 둔다.

## 3. 테이블

리드미 테이블 10개와 Spring Session이 쓰는 테이블 2개다.

| 테이블 | 내용 |
|---|---|
| `users` | 계정. 이메일, 인증 시각, 비밀번호 해시(구글로만 가입하면 비어 있음), 표시 이름 |
| `user_identities` | 계정에 연결된 소셜 로그인. 지금은 `GOOGLE`만 |
| `email_tokens` | 가입 확인·비밀번호 재설정 메일의 토큰(해시로 보관) |
| `card_sources` | 올린 자료에서 읽어 낸 본문 |
| `card_extraction_jobs` | 카드 추출 작업의 상태와 진행도 |
| `experience_cards` | 경험카드 본체 |
| `card_tags` | 카드의 태그(키워드 사전의 대표 표기) |
| `card_usable_for` | 카드로 답할 수 있는 문항 유형 |
| `card_facts` | 카드의 확정 수치·사실 |
| `llm_usage` | LLM 호출별 토큰 수. 월 크레딧 추적과 나중의 무료 한도에 쓴다 |
| `spring_session`, `spring_session_attributes` | 로그인 세션. spring-session-jdbc에 들어 있는 `schema-postgresql.sql`을 Flyway V2로 넣는다 |

### 3.1 생성 SQL (Flyway `V1__init.sql`)

PostgreSQL 16에서 실행해 확인했다(3.3).

```sql
-- JDBC 주소에 currentSchema=readme 를 붙여 쓴다. Flyway, JPA, Spring Session 이 모두 이 스키마를 본다.
create schema if not exists readme;
set search_path to readme;

-- ── 계정 ─────────────────────────────────────────────────────────────
create table users (
  id                bigint generated always as identity primary key,
  email             varchar(320) not null,
  email_verified_at timestamptz,                 -- null 이면 아직 인증 전
  password_hash     varchar(100),                -- 구글로만 가입한 계정은 null
  display_name      varchar(50)  not null,
  created_at        timestamptz  not null default now(),
  updated_at        timestamptz  not null default now(),
  last_login_at     timestamptz
);
create unique index users_email_key on users (lower(email));

create table user_identities (
  id               bigint generated always as identity primary key,
  user_id          bigint       not null references users(id) on delete cascade,
  provider         varchar(20)  not null check (provider in ('GOOGLE')),
  provider_user_id varchar(255) not null,        -- 구글 ID 토큰의 sub
  provider_email   varchar(320),                 -- 연결할 때 구글이 준 이메일(참고용)
  created_at       timestamptz  not null default now(),
  unique (provider, provider_user_id),
  unique (user_id, provider)
);

create table email_tokens (
  id         bigint generated always as identity primary key,
  user_id    bigint      not null references users(id) on delete cascade,
  purpose    varchar(20) not null check (purpose in ('VERIFY_EMAIL', 'RESET_PASSWORD')),
  token_hash char(64)    not null unique,        -- 토큰 원문은 메일에만 있다. DB에는 SHA-256
  expires_at timestamptz not null,
  used_at    timestamptz,
  created_at timestamptz not null default now()
);
create index email_tokens_user_idx on email_tokens (user_id, purpose);

-- ── 경험카드 ─────────────────────────────────────────────────────────
create table card_sources (
  id           bigint generated always as identity primary key,
  user_id      bigint      not null references users(id) on delete cascade,
  kind         varchar(10) not null check (kind in ('FILE', 'TEXT')),
  file_name    varchar(255),
  content_type varchar(100),
  byte_size    bigint,
  sha256       char(64)    not null,             -- 같은 자료를 다시 올렸는지 판별
  body         text        not null,             -- 읽어 낸 본문. 숫자 원문 대조에 쓴다
  char_count   integer     not null,
  created_at   timestamptz not null default now(),
  unique (user_id, sha256)
);

create table card_extraction_jobs (
  id            bigint generated always as identity primary key,
  user_id       bigint      not null references users(id) on delete cascade,
  source_id     bigint      not null references card_sources(id) on delete cascade,
  status        varchar(10) not null check (status in ('QUEUED', 'RUNNING', 'DONE', 'FAILED')),
  total_parts   integer     not null,            -- 본문을 5,000자씩 나눈 조각 수 = LLM 호출 수
  done_parts    integer     not null default 0,
  error_message text,
  created_at    timestamptz not null default now(),
  started_at    timestamptz,
  finished_at   timestamptz
);
create index card_extraction_jobs_user_idx on card_extraction_jobs (user_id, created_at desc);

create table experience_cards (
  id               bigint generated always as identity primary key,
  user_id          bigint       not null references users(id) on delete cascade,
  title            varchar(200) not null,
  period           varchar(50),                  -- '2025-03 ~ 2025-06' 글자 그대로
  org              varchar(200),
  role             varchar(200),
  summary          varchar(200),                 -- 60자를 넘으면 경고만 낸다
  situation        text,
  task             text,
  action           text,
  result           text,
  verified         boolean      not null default false,
  verified_at      timestamptz,
  visibility       varchar(10)  not null default 'PRIVATE' check (visibility in ('PRIVATE')),
  source_id        bigint references card_sources(id) on delete set null,
  job_id           bigint references card_extraction_jobs(id) on delete set null,
  extraction_notes jsonb,                        -- 추출 때 생긴 안내 목록. 카드를 확인하면 비운다
  created_at       timestamptz  not null default now(),
  updated_at       timestamptz  not null default now()
);
create index experience_cards_user_idx on experience_cards (user_id, updated_at desc);

create table card_tags (
  card_id bigint       not null references experience_cards(id) on delete cascade,
  tag     varchar(100) not null,                 -- 키워드 사전의 대표 표기
  primary key (card_id, tag)
);
create index card_tags_tag_idx on card_tags (tag);

create table card_usable_for (
  card_id       bigint      not null references experience_cards(id) on delete cascade,
  question_type varchar(10) not null
    check (question_type in ('지원동기', '직무역량', '협업', '문제해결', '성장', '기타')),
  primary key (card_id, question_type)
);

create table card_facts (
  card_id bigint       not null references experience_cards(id) on delete cascade,
  seq     integer      not null,                 -- 화면에 보이는 순서
  body    varchar(500) not null,
  primary key (card_id, seq)
);

-- ── LLM 사용 기록 ────────────────────────────────────────────────────
create table llm_usage (
  id            bigint generated always as identity primary key,
  user_id       bigint references users(id) on delete set null,
  feature       varchar(30) not null,            -- 'EXP_EXTRACT' 등
  model         varchar(50) not null,
  input_tokens  integer     not null,
  output_tokens integer     not null,
  created_at    timestamptz not null default now()
);
create index llm_usage_user_idx on llm_usage (user_id, created_at);
```

### 3.2 설계 이유

- **구글 계정은 `sub`로 식별한다.** 구글 문서는 `sub`가 모든 구글 계정에서 유일하고 재사용되지 않으니 이것을 사용자 키로 쓰라고 하고, `email`은 유일하지 않을 수 있고 바뀔 수 있으니 기본 식별자로 쓰지 말라고 한다. 그래서 `user_identities.provider_user_id`에 `sub`를 넣고, 이메일은 연결할 때 한 번만 쓴다.
- **제공자를 따로 테이블로 뺐다.** 카카오·네이버를 추가할 때 `provider` 제약에 값만 더하면 된다.
- **구글 로그인 콜백의 처리 순서**(가정 3번):
  1. `sub`로 `user_identities`를 찾는다. 있으면 그 계정으로 로그인.
  2. 없고 구글의 `email_verified`가 true면 같은 이메일의 `users`를 찾는다.
     - 계정이 없다 → 새 계정을 만들고(인증 완료, 비밀번호 없음) 연결.
     - 인증을 마친 계정이 있다 → 그 계정에 연결.
     - 인증 전 계정이 있다 → 비밀번호를 지우고 인증 완료로 바꾼 뒤 연결. 다른 사람이 그 이메일로 먼저 가입만 해 둔 경우, 남의 비밀번호가 붙은 계정에 연결되는 것을 막는다.
  3. `email_verified`가 false면 로그인을 거부한다.
- **토큰은 해시로만 보관한다.** DB가 새도 메일 링크를 만들 수 없다. 한 번 쓰면 `used_at`을 채운다.
- **카드 칸은 jobfit 형식 그대로다.** title, period, org, role, tags, summary, star 4칸, facts, usable_for, verified. jobfit의 영문 `id`(exp-…)는 DB의 `id`로 대신한다.
- **`period`는 글자 그대로 둔다.** jobfit이 "2025-03 ~ 2025-06", "2026 ~ 현재"처럼 여러 꼴을 받는다. 기간순 정렬이 필요해지면 날짜 칸을 더한다.
- **문항 유형 값은 한글 그대로다.** jobfit 프롬프트와 테스트가 이 이름을 쓴다.
- **자료 본문을 보관하는 이유.** jobfit은 추출된 카드의 숫자를 자료 원문과 대조해, 원문에 없는 숫자가 든 fact는 빼고 star의 숫자는 `[확인 필요: 숫자]`로 바꾼다. 카드를 확인할 때도 원문을 다시 본다. 사용자가 자료를 지우면 카드는 남고 `source_id`만 빈다.
- **`llm_usage`.** 지금 월 100달러 크레딧을 쓰므로 기능별·사용자별 토큰 수를 처음부터 쌓아 둔다.

### 3.3 확인한 것

임시 PostgreSQL 16에 V1을 실행하고 아래를 SQL로 돌려 봤다.

| 확인 | 결과 |
|---|---|
| 테이블 10개 생성 | 통과 |
| 가입 → 이메일 인증 → 구글 연결 → 자료 → 추출 작업 → 카드·태그·유형·fact 저장 | 통과 |
| 카드 목록(태그 + 문항 유형 + 확인 필요 필터), 태그별 카드 수 | 통과 |
| 대소문자만 다른 이메일, 정해지지 않은 제공자, 문항 유형이 아닌 값, 같은 자료 두 번 | 모두 막힘 |
| 자료 삭제 시 카드는 남고 `source_id`·`job_id`만 빈다 | 통과 |
| 계정 삭제 시 딸린 행이 모두 지워지고 `llm_usage`는 `user_id`만 빈다 | 통과 |

확인하지 않은 것: JPA 매핑, Spring Session 테이블, Supabase 위에서의 실행.

## 4. API

21개다. 주소는 `/api` 아래, 본문은 JSON, 로그인은 세션 쿠키로 확인한다. 바꾸는 요청에는 CSRF 헤더(`X-XSRF-TOKEN`)를 붙인다. 오류는 `{ "code": "...", "message": "..." }` 꼴이다. 모든 API에 공통인 오류 코드는 그룹 설계 4절 머리의 표에 있다. 이 절의 오류는 `EMAIL_NOT_VERIFIED` 말고는 코드 이름이 아직 없다(화면·API 대응 문서 3.4절 19번).

### 4.1 로그인 (8개)

| 메서드·주소 | 하는 일 | 비고 |
|---|---|---|
| `POST /api/auth/signup` | 이메일·비밀번호·표시 이름으로 가입, 가입 확인 메일 발송 | 이미 있는 이메일이면 409. 이메일 존재 여부가 드러난다 |
| `POST /api/auth/verify-email` | 메일의 토큰으로 인증 완료 | 만료·사용된 토큰이면 400 |
| `POST /api/auth/verify-email/resend` | 가입 확인 메일 다시 보내기 | 계정이 없어도 같은 응답 |
| `POST /api/auth/login` | 이메일·비밀번호 로그인 | 인증 전이면 403 `EMAIL_NOT_VERIFIED` |
| `POST /api/auth/logout` | 로그아웃 | |
| `POST /api/auth/password-reset/request` | 재설정 메일 발송 | 계정이 없어도 같은 응답 |
| `POST /api/auth/password-reset/confirm` | 토큰과 새 비밀번호로 변경 | 그 계정의 세션을 모두 끊는다 |
| `GET /api/me` | 내 계정: 이메일, 표시 이름, 비밀번호 유무, 연결된 제공자 | 로그인 안 했으면 401. 2026-11-13에 만들었다. 응답은 `{ id, name, email, hasPassword, providers }`다(그룹 설계 8절 9번) |

구글 로그인은 Spring Security의 기본 경로를 쓴다. 직접 만드는 API가 아니다.

| 주소 | 하는 일 |
|---|---|

| `GET /login/oauth2/code/google` | 구글이 돌아오는 주소. 3.2의 순서대로 처리한 뒤 프런트로 돌려보낸다 |

- **순서표와 다른 점**: 정리 문서의 순서표는 숫자 정규화를 5번(자소서 초안)에 뒀다. 그런데 카드 검사와 추출 정리가 `numbers.py`의 `extract`·`same_value`를 쓴다. 1번과 함께 옮겨야 한다.
- 옮기지 않는 부분: `experiences.py` 뒤쪽의 YAML 파일 고치기, `exp_extract.py`의 파일 스캔과 진행 상태 파일.

## 7. Supabase에 올릴 때의 조건

| 항목 | 내용 |
|---|---|
| 연결 방식 | Spring Boot처럼 계속 떠 있는 서버는 직접 연결(포트 5432)을 쓴다. 직접 연결은 IPv6이고, IPv4만 되는 망에서는 IPv4 추가 기능을 사거나 공유 풀러의 세션 모드(포트 5432)를 쓴다 |
| 쓰지 않을 것 | 공유 풀러의 트랜잭션 모드(포트 6543). prepared statement를 지원하지 않는다. 서버리스용이다 |
| Data API | 리드미는 Spring 서버만 DB에 붙는다. Supabase 문서는 클라이언트 라이브러리·REST·GraphQL을 쓰지 않으면 Data API를 끄라고 한다. 끄면 권한 설정과 관계없이 자동 생성 REST 주소가 응답하지 않는다 |
| public 스키마 | 예전에는 `public`에 만든 테이블이 Data API에 자동으로 열렸다. 2026-10-30부터 기존 프로젝트에도 "새 테이블은 명시적으로 권한을 줘야 열린다"가 적용된다. 전용 스키마 `readme`를 쓰면 이 설정과 무관하다 |
| 무료 플랜 | DB 500MB, 1주일 동안 쓰지 않으면 프로젝트 일시 정지, 자동 백업 없음, 활성 프로젝트 2개까지 |
| Pro 플랜 | 월 25달러부터, 디스크 8GB, 7일치 일일 백업, 일시 정지 없음 |

지금부터 지켜 두면 옮기기 쉬운 것:

- 스키마 변경은 Flyway로만 한다. 옮길 때는 빈 DB에 마이그레이션을 실행하고 데이터를 덤프·복원한다.
- Supabase 전용 기능(Auth, Storage, RLS 정책)에 기대지 않는다. 그러면 다른 Postgres 호스팅으로도 갈 수 있다.
- 서버를 올릴 곳이 IPv6으로 나갈 수 있는지 확인한다. 안 되면 세션 모드 풀러 주소를 쓴다.

사람들과 실제로 쓰기 시작하면 무료 플랜의 일시 정지와 백업 없음이 걸린다.

## 8. 구글 로그인의 조건

- Google Cloud 프로젝트에서 OAuth 클라이언트를 만들고, 리디렉션 주소로 `{서버 주소}/login/oauth2/code/google`을 등록한다. 로컬과 운영 주소를 각각 넣는다.
- 요청 범위는 `openid`, `email`, `profile`만 쓴다.
- 구글 문서 기준으로, Testing 상태의 앱은 테스트 사용자 100명 제한이 있지만 기본 신원 범위만 요청하는 앱은 허용 목록에 없는 사용자도 접근할 수 있다는 예외가 표에 적혀 있다. 인증(verification)은 민감·제한 범위를 요청하는 공개 앱에 필요하다고 되어 있다.
- 브랜드 인증을 받기 전에는 동의 화면에 앱 이름과 로고가 표시되지 않는다.
- 기본 범위만 쓰는 앱이 운영 상태에서 인증 없이 되는지는 문서가 명시하지 않았다. 실제 콘솔에서 확인이 필요하다.

## 9. 새로 생긴 결정

| 항목 | 선택지 |
|---|---|
| 메일 발송 수단 | 가입 확인·재설정 메일을 보낼 SMTP 계정 또는 메일 발송 서비스. 코드는 어느 쪽이든 Spring의 JavaMailSender로 같다. 메일 자동화의 수신과 같은 도메인을 쓸지도 함께 정한다 |
