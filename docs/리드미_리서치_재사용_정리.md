### 원하는 동작 (세부는 미정)

- URL을 넣으면 LLM이 공고를 분석해 정해 둔 칸을 자동으로 채운다.
- 칸은 필수값과 부가정보로 나누고, 부가정보는 비어 있어도 된다.
- 한솥밥의 "어떤 문서를 넣어도 시스템 칸에 맞춰 넣어 주는 기능"을 그대로 쓴다.
- 백엔드 서버를 Python으로 두고 싶지 않다.

### 정한 것에 따라 생기는 일

- 수익화 가능성이 있으므로 유료화 금지인 사람인 API, 상업적 이용금지인 워크넷 채용정보는 약관과 충돌한다. 사용자 입력 방식과는 충돌하지 않는다.
- 기존 경험카드는 포트폴리오와 이력서만으로 만든 것이라 새 사전의 낱말 태그가 없다. 카드 태그를 다시 붙이는 전처리가 필요하다. jobfit에는 기존 카드의 태그를 다시 붙이는 명령이 없다(`exp extract --force`는 이미 있는 카드와 같은 경험을 건너뛴다).
- 공기업·대학 전산직 공고는 공고문이 첨부 파일인 경우가 많다. 파일 업로드 경로가 중요해진다.
- jobfit의 블라인드 표현 검사와 지원서 입력표는 공기업 지원에 바로 쓰인다.
- 그룹 우선이므로 초기에 쓸 그룹을 먼저 확보해야 한다.

### 그룹 공고 (2026-11-13에 정함)

화면을 그리기 전에 정해야 했던 네 가지다.

**1. 공고를 올리는 사람**

- 그룹 멤버 누구나 그룹에 공고를 올린다. 그룹장이 즐겨찾기해야 공유되는 방식은 쓰지 않는다.
- 그룹에서 공고를 내리는 것은 올린 사람과 그룹장만 한다.
- 이미 그룹에 있는 공고를 다시 올리면 새로 만들지 않고 기존 공고로 안내한다.

**2. 관심 표시**

- 관심은 켜고 끄는 표시 하나다.
- 그룹 공고에서 관심을 켜면 그 그룹 멤버에게 내 이름이 보이고, 그 공고가 내 공고 목록에 들어간다(결정 = 미정).
- 관심은 그룹별로 기록한다. 같은 공고가 내가 속한 두 그룹에 있어도 관심을 켠 그룹에만 보인다.
- "지원 예정" 값은 두지 않는다. 관심이 그 뜻을 맡는다.
- 지원 상태의 원본은 내 지원 관리의 값이다. 그룹에는 내가 관심을 켠 공고에 한해, 내가 그 그룹에 정한 공개 범위만큼 보인다.
- 공개 범위는 그룹마다 따로 고르고, 기본값은 "지원 여부까지"다.

| 공개 범위 | 그룹에 보이는 것 |
|---|---|
| 관심만 | 관심 |
| 지원 여부까지(기본값) | 관심, 지원함 |
| 단계·결과까지 | 관심, 지원함, 서류·필기·면접 단계, 합격·불합격 |

**3. 메모**

- 공용 메모 칸은 두지 않고 멤버별 댓글로 한다.
- 댓글은 "그룹 × 공고"에 달린다. 같은 공고가 다른 그룹에 있어도 그 그룹의 댓글은 보이지 않는다.
- 쓴 사람만 수정·삭제한다. 그룹장은 삭제만 한다.
- 글자와 링크만 받는다. 파일 첨부는 없다.
- 나만 보는 메모는 내 지원 관리에 따로 둔다.
- 댓글이 쌓여 핵심이 묻히면 "댓글 하나를 맨 위에 고정"을 나중에 더한다.

**4. 그룹 공고 목록**

칸(데스크톱은 한 줄, 모바일은 카드):

| 칸 | 내용 |
|---|---|
| 마감 | D-day와 날짜. 상시 채용은 "상시", 못 읽었으면 "마감일 확인 필요" |
| 회사명 · 공고명 | 누르면 공고 상세 |
| 관심 멤버 | 이름 나열. 지원한 사람은 표시를 구분한다(공개 범위가 "지원 여부까지" 이상인 멤버만) |
| 내 상태 | 관심 켜기·끄기. 지원했으면 내 상태 값 |
| 댓글 수 | |
| 올린 사람 · 올린 날 | 보조 정보. 올린 지 3일 이내면 "새 공고" 표시 |

- 모바일 카드는 회사명과 D-day, 공고명, 관심 멤버와 댓글 수 순으로 놓는다. 올린 사람은 상세에서 보여 준다.
- 정렬: 기본은 마감 임박순이다. 최근 올린 순, 관심 많은 순으로 바꿀 수 있다.
- 필터: 진행 중 / 마감됨(기본은 진행 중), 내 관심만, 멤버 선택(그 멤버가 관심을 켠 공고), 회사명·공고명 검색.

마감일이 없는 공고의 위치:

| 경우 | 위치 |
|---|---|
| 마감일을 못 읽음 | 목록 맨 위 "마감일 확인 필요" 묶음. 멤버 누구나 날짜를 넣으면 제자리로 간다 |
| 상시·수시 채용 | 날짜 있는 공고 아래 "상시 채용" 묶음, 최근 올린 순 |
| 마감 지남 | 기본 목록에서 빠지고 "마감됨"에서 최근 마감순 |

- 마감은 지났지만 필기·면접이 진행 중인 공고를 따로 보여 주는 구분은 지금 넣지 않는다. "진행 중 / 마감됨" 둘로 시작한다.

**이 결정이 기대는 것과 남은 세부**

- 2번의 공개 범위 표는 지원 상태 값을 결정·단계·결과로 나누는 구조(7절 제안)를 전제로 썼다. 그 구조는 아직 제안이다.
- 관심을 껐을 때 그 공고를 내 공고 목록에 남길지는 정하지 않았다(제안: 남긴다. 지원 기록이 지워지지 않게).
- 내 결정을 "지원안함"으로 바꿨을 때 관심을 자동으로 끌지는 정하지 않았다(제안: 끌지 물어본다).
- "새 공고"에 올린 지 3일째를 넣을지는 정하지 않았다. 코드는 넣고(11.10에 올린 공고가 11.13에 새 공고다), 디자인 예시는 넣지 않는다.
- 그룹 공고의 테이블과 API 설계는 아직 없다. 화면이 기대는 응답 모양은 `frontend/src/features/group-posts/types.ts`에 있다.

| 스터디 | 링커리어 | 모집 글만 올리고 운영은 오픈채팅 |
| | SwithUs, 픽스터디 | 모집, 일정, 출석, 과제 인증 |

빈자리: 그룹 안에서 공고와 경험카드를 연결해 주는 서비스는 찾지 못했다.

### 공고 데이터 확보 방식

| 방식 | 제약 |
|---|---|
| 사용자 입력 (선택함) | 법적 부담이 가장 낮다. 서비스 안에서 공고 탐색은 안 된다 |
| 크롬 확장 | 확장 개발과 스토어 심사가 추가된다 |
| 사람인 API | 일 500건. 서비스 유료화와 이용 대가 수취 금지 |
| 고용24 API | 기업회원 전용, 담당자 심사. 워크넷 채용정보는 출처표시·상업적 이용금지·변경금지 |
| 공공기관 채용정보 조회서비스 | 개발계정 1,000건, 운영 단계는 심의 승인 |
| 로켓펀치 Open API | 분당 60회·일 5,000회, 1.0 beta. 이용약관 미확인 |
| 서버 크롤링 | 잡코리아 대 사람인(서울고법 2016나2019365): 데이터베이스권 침해, 배상 2억 5,000만 원, 대법원 확정 |

### 그 밖의 제약

- 직업정보제공사업 신고 대상인지 출시 전 확인이 필요하다. 링크 입력 방식인 티오도 신고번호를 표기한다.
- 노션 API: 연결당 분당 180회(평균 초당 3회), 요청당 블록 1,000개·500KB. Free 워크스페이스는 2026-09-08부터 블록 한도가 적용된다.
- 구글 시트 API: 프로젝트당 분당 300회, 사용자당 분당 60회.
- 그룹 간 관심 표시는 그룹 수가 쌓여야 의미가 생긴다.
- 같은 공고에 지원하는 그룹원은 경쟁자이기도 해서 카드별 공개 범위가 필요하다.

### 키워드 사전 확장본 — `claude/사전/`

jobfit 사전 원본은 한 글자도 고치지 않고 아래에 덧붙였다. 형식이 같아서 jobfit 프로젝트 루트의 `data/` 폴더에 넣으면 지금 jobfit에서도 쓸 수 있다.

| 파일 | 내용 | 원본 → 확장본 |
|---|---|---|
| `keywords.txt` | 대표 표기 | 117 → 227 |
| `synonyms.yaml` | 대표 표기별 다른 표기 | 표기 합계 225 → 554 |
| `implies.yaml` | 포함 관계 (MES → 스마트팩토리, PL/SQL → Oracle 등) | 42 → 93 |
| `certificates.yaml` | 자격증 12종. jobfit은 읽지 않는다 | 새 파일 |

추가한 영역: 스마트팩토리·MES 39개, 고장예측·데이터 분석 35개, 공공·대학 전산 36개.

검증: 확장본을 jobfit에 넣고 테스트 269건이 모두 통과했다. 표본 공고 문장 4개에서 낱말이 뽑히는 것과, 걸리면 안 되는 문장 9개가 안 걸리는 것을 확인했다.

일부러 뺀 것:

- **자격증 이름**: 자격증은 경험카드가 아니라 지원서 정보에 있는 값이다. 키워드로 넣으면 "정보처리기사 우대"가 카드 미충족으로 세어져 매칭 점수가 내려간다. 그래서 `certificates.yaml`로 분리했다.
- **SQL 튜닝**: 넣으면 "SQL 튜닝" 요건이 SQL로 세어지던 기존 동작이 바뀐다.
- **다른 뜻과 겹치는 표기**: R(R&D), GEM(Ruby gem), WAS(영어 was), F/W(펌웨어와 방화벽), Apache 홀로(Apache Kafka), 전처리 홀로(제조의 전처리 공정), 두 글자 약어 FA·SM·AD·QA.
- **NCS, 토익, 한국사**: 전형과 어학 이름이지 역량 낱말이 아니다.

알려진 한계:

- 자격증 이름 안의 낱말이 역량 낱말로 읽힌다(정보보안기사 → 정보보안, 네트워크관리사 → 네트워크). 리드미에서는 자격증 사전을 먼저 훑어 가린 뒤 키워드를 찾으면 된다.
- 낱말 목록은 직군 지식으로 고른 것이다. 실제 공고 표본으로 빠진 낱말을 확인하지는 않았다.

| 순서 | 모듈 | 쓰이는 기능 |
|---|---|---|
| 1 | 키워드 사전, 경험카드 형식과 검사 | 경험카드 (로그인 다음에 만들 것) |

- 정규식 차이: 이름 붙은 그룹 문법이 다르다(`(?P<이름>…)` → `(?<이름>…)`).

### 그대로는 안 되는 부분

- jobfit은 사용자 한 명 전제다. 상태가 로컬 파일이라 DB, 그룹, 권한은 새로 만든다.
- jobfit의 CLI, 엑셀 입출력, 프롬프트 복사·붙여넣기 흐름은 쓰지 않는다.
- jobfit은 사용자 PC에서 공고를 받는다. 서버에서 받으면 요청량과 IP 조건이 달라진다.
- URL(HTML) 위치 표식 파서, 이미지형 공고, 구형 HWP는 두 프로젝트 모두 없다.
- 공고키는 같은 사이트 안에서만 맞다. 사람인과 잡코리아에 따로 올라온 같은 공고는 못 묶는다.

## 5. LLM 사용

### LLM을 쓰는 기능

| 기능 | 호출 빈도 | 무엇에 비례하나 |
|---|---|---|
| 공고 분석(필수·우대·업무·키워드·문항) | 공고당 1회 | 공고 수 |
| 첨부 파일·이미지 공고 칸 채우기 | 규칙으로 못 읽은 공고만 1회 | 공고 수 |
| 경험카드 추출 | 자료 5,000자 조각당 1회, 가입 때 한 번 | 사용자 수 |
| 문체 분석, 지원서 정보 추출 | 사용자당 각 1회 정도 | 사용자 수 |
| 자소서 초안 | 사용자와 공고 조합마다 1회 | 사용자 수 × 지원 공고 수 |
| 초안 수정 | 검사에 걸린 경우만 0~1회 | 사용자 수 × 지원 공고 수 |

필수값 읽기, 같은 공고 판별, 매칭 점수, 문항별 카드 배정, 초안 검사, 지원 현황은 LLM을 쓰지 않는다.

고칠 곳: jobfit의 공고 분석 프롬프트에는 개인 경험 태그가 들어간다. 그대로 가져오면 같은 공고를 사용자마다 다시 분석한다. 태그 대신 사전의 대표 표기를 넣으면 공고당 1회로 끝나고 그룹이 결과를 공유한다.

### 5명 그룹 한 달 비용 어림

| 모델 | 한 달 비용 | 생각 토큰까지 넉넉히 잡은 경우 |
|---|---|---|
| Haiku 5.5 | 약 0.5달러 | 약 1달러 |
| Sonnet 5.5 | 약 11달러 | 약 23달러 |
| Opus 5.5 | 약 21달러 | 약 46달러 |

가정: 주 10건 공고 공유, 1인당 주 4건 지원, 한 달 212회 호출. 입력은 jobfit 프롬프트 상한(6,000~8,000자)을 꽉 채운 것으로, 한글 1자는 1.5토큰으로 잡았다(실제 비율은 미확인). 단가는 백만 토큰당 입력/출력이 Haiku 5.5 0.10/0.50달러, Sonnet 5.5 2/10달러, Opus 5.5 4/20달러(2026-11-12 가격 문서). 이미지·스캔 공고와 개발 중 테스트 호출은 넣지 않았다. 월 100달러 크레딧의 사용 조건(이월, 모델 제한)은 확인하지 못했다.

### 사용자 쪽 키와 구독

- 사용자가 자기 API 키를 넣어 쓰게 하는 것은 가능하다. Anthropic 약관에서 API 키 접근은 허용된 방식이다.
- 구독(Free·Pro·Max) 로그인을 다른 서비스에서 쓰는 것은 금지돼 있다(2026년 2월 약관 명확화). 구독 계정에서는 다른 서비스에 넣을 API 키가 나오지 않는다.
- Pro 구독에는 API 사용이 포함되지 않는다. Max, Ultra, Team에는 매달 API 크레딧이 포함된다.
- 구독만 있는 사용자가 자기 구독으로 쓰는 길은 둘이다. 붙여넣기(jobfit에 구현돼 있음)와 커넥터(리드미가 MCP 서버를 제공, Claude 커스텀 커넥터는 모든 플랜에서 가능하고 Free는 1개).
- 키를 받는다면 보관 위치를 정해야 한다: 서버에 암호화 저장 / 브라우저에만 두고 직접 호출 / 요청마다 보내고 저장하지 않음.

## 6. 메일 자동화

사용자가 채용 관련 메일을 리드미의 자기 수신 주소로 보내면, 리드미가 내용을 추려 그 계정의 공고 관리와 일정 관리에 반영한다. 리드미는 사용자 메일함에 접근하지 않는다.

### 입력 경로

| 경로 | 사용자가 할 일 | LLM 비용 | 약점 |
|---|---|---|---|
| 자동 전달 규칙 (기본) | 메일 서비스에 규칙을 한 번 설정. 예: Gmail 필터로 채용 낱말이 든 메일을 리드미 주소로 전달 | 내 키. Haiku 기준 메일 한 통에 0.1센트 미만 | 필터가 넓으면 무관한 메일도 넘어온다. 채용 메일이 아니면 저장하지 않고 버린다. Gmail 자동 전달은 확인 코드 절차가 있다 |
| LLM 예약작업 (선택) | Claude에 Gmail 커넥터 연결, 발송 승인 해제, 예약작업 작성 | 사용자 구독 | 예약 실행에서 승인 없이 발송되는지 미확인. ChatGPT는 예약 실행에서 Gmail 커넥터 호출 실패 보고가 있다(2026-08~10) |
| 직접 실행 | 저장해 둔 지시문을 하루 한 번 직접 실행 | 사용자 구독 | 반자동 |
| 리드미 커넥터 + 예약작업 | Claude에 리드미 커넥터 추가 | 사용자 구독 | MCP 서버를 만들어야 한다. 예약 실행에서 커넥터 쓰기가 되는지 미확인 |
| PC에서 예약 실행 | Claude Code나 Codex를 작업 스케줄러로 실행 | 사용자 구독 | 개발 직군만 가능, PC가 켜져 있어야 한다 |

예약작업이 안 될 때의 순서: 직접 실행 → 리드미 커넥터 → PC 예약 실행.

예약작업 경로의 장점은 사용자 쪽에서 관련 메일만 추려 보내므로 리드미에 필요한 내용만 도착한다는 것이다.

### 꼭 넣을 것

- 사용자별 수신 주소. 보낸 사람 주소는 위조할 수 있으므로 추측할 수 없는 주소를 주고, 등록된 발신 주소인지도 확인한다.
- 메일 내용은 자료로만 처리한다. 메일 안의 지시문은 따르지 않고, 상태 값은 정해진 목록에서만 고른다.
- 공고 등록은 자동, 상태 변경(불합격 등)은 "확인 필요"로 올리고 사용자가 누르면 반영한다.
- 원문은 최소로 보관한다. 추출한 칸만 저장한다.
- 예약작업 지시문에는 고정 양식(회사명, 공고명, 상태, 일정, 근거 메일 날짜)을 넣고, 수신 주소를 리드미 주소로 한정한다.

### 시험할 것 (본인 Max 계정)

1. Gmail 커넥터 발송 승인을 풀고, 채용 메일을 요약해 다른 주소로 보내는 예약작업을 만든다. 사람이 없을 때 메일이 도착하는지 본다.
2. 채용 메일을 요약해 Notion 페이지에 적는 예약작업을 만든다. 사람이 없을 때 페이지가 생기면 커넥터 방식이 가능하다.

### 지원 상태 값 제안: 단계와 결과를 분리

| 칸 | 값 |
|---|---|
| 결정 | 미정, 보류, 지원안함, 지원함 |
| 단계 | 서류, 필기, 1차 면접, 2차 면접, 최종 |
| 결과 | 진행 중, 합격, 불합격 |

- 필기 단계는 공기업의 NCS·전공 필기와 사기업의 코딩테스트·과제·인적성을 함께 담는다. 세부 종류는 메모 칸에 적는다.
- 한 줄 목록에 "필기합격", "1차면접합격"처럼 값을 계속 늘리는 것보다 값이 적고, 어느 단계에서 떨어졌는지 집계할 수 있다.
- jobfit 값과의 대응: 지원완료 = 지원함 + 서류 + 진행 중, 서류합격 = 서류 + 합격, 탈락 = 해당 단계 + 불합격, 최종합격 = 최종 + 합격.

### 구형 HWP 읽는 방법

| 방법 | 내용 | 조건 |
|---|---|---|
| hwplib | Java 라이브러리. HWP를 객체로 읽고 텍스트 추출 예제가 있다. Maven `kr.dogfoot:hwplib` 1.1.9 | Apache-2.0. 암호 걸린 파일과 PDF·HTML 변환은 미지원 |
| pyhwp | Python. HWP 버전 5 파서, 텍스트·ODT 변환은 실험적 | AGPLv3. 서비스에 쓰면 소스 공개 조건을 검토해야 한다 |
| LibreOffice + H2Orestart | HWP·HWPX를 열어 서버에서 PDF로 변환. v0.8.0(2026-10-18) | GPL. LibreOffice와 Java 실행 환경 필요. 변환 뒤 PDF 파서로 읽는다 |

스택이 Java면 hwplib가 서버 안에서 바로 돈다. HWPX는 한솥밥 파서나 `neolord0/hwpxlib`로 읽는다.
