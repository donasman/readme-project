## 2. 가정

| # | 항목 | 초안의 값 | 다른 선택지 | 바뀌는 곳 |
|---|---|---|---|---|
| L1 | 인증 담당 | **확정**: Spring Security. Supabase는 DB로만 쓴다 | Supabase Auth(구글·이메일 가입, 인증 메일 포함) | 계정 테이블 3개와 인증 API 전부 |
| L2 | 로그인 유지 | **확정**: 서버 세션 쿠키(Spring Session JDBC) | JWT(access + refresh) | 세션 테이블, 프런트 요청 방식, CSRF 처리 |
| L3 | 계정 연결 | 구글 이메일과 같은 이메일의 계정이 있으면 한 계정으로 연결(3.2) | 항상 별도 계정 / 로그인한 상태에서만 직접 연결 | 구글 콜백 로직. 테이블은 같다 |
| L4 | 인증 전 계정 | 이메일 인증 전에는 로그인 불가 | 로그인은 되고 기능만 제한 | 로그인 API, 프런트 안내 |
| L5 | 토큰 유효 시간 | 가입 확인 24시간, 비밀번호 재설정 1시간 | 다른 값 | 설정값 |

L1과 L2는 2026-11-12에 확정했다. L3~L5는 아직 가정이다. L4와 L5는 2026-11-14에, L3은 2026-11-15에 초안의 값대로 만들었다(4.1). 옛 가정 5(전용 스키마 `readme`)는 구조 문서 7절로 옮겼다.

**L1을 Spring Security로 정한 이유**

- Supabase Auth를 쓰면 첫날부터 Supabase가 필요하다. "지금은 Postgres, Supabase는 나중에 생각"이라는 순서와 맞지 않는다.
- 계정이 Supabase의 `auth.users`에 생기고 리드미 데이터는 Spring이 관리하는 테이블에 있어, 사용자 저장소가 둘이 된다. 탈퇴·그룹 초대처럼 계정을 건드리는 기능마다 Spring이 Supabase 관리 API를 불러야 한다.
- Supabase Auth가 덜어 주는 것 중 메일 발송은 실제로는 덜어지지 않는다. 기본 메일 서버는 팀 구성원 주소로만 보내고 시간당 2통 제한이며 운영용이 아니라고 문서에 적혀 있다. 어느 쪽이든 발송 수단을 따로 붙여야 한다.
- 남는 차이는 가입·인증·재설정 API 7개를 직접 만드느냐인데, Spring Security가 비밀번호 해시, 구글 로그인, 세션, CSRF를 이미 제공한다.
- 잃는 것: Supabase Auth의 요청 횟수 제한, 유출 비밀번호 검사, 2단계 인증 같은 기능은 필요해지면 직접 붙여야 한다.

**L2를 세션 쿠키로 정한 이유**

- 접속하는 쪽이 React 웹 화면 하나다. JWT가 유리한 경우(모바일 앱, 외부 개발자용 API, 서버 여러 대가 서로 호출)가 지금 없다.
- Spring Security의 구글 로그인은 기본이 세션 방식이다. JWT로 가면 구글 로그인 중간 상태 보관, 토큰 발급, refresh 토큰 보관·교체·폐기를 직접 만들어야 한다. 직접 만드는 보안 코드가 늘어난다.
- 로그아웃, 비밀번호 재설정, 탈퇴, 그룹 강퇴가 즉시 반영된다. 세션 행을 지우면 끝이다. JWT는 만료 전까지 유효해서 차단 목록을 따로 둬야 한다.
- 쿠키를 `HttpOnly`로 두면 화면의 스크립트가 로그인 정보를 읽을 수 없다.
- 세션을 DB에 두므로(Spring Session JDBC) 서버를 다시 배포해도 로그인이 풀리지 않는다.
- 조건: 프런트와 서버가 같은 사이트 주소 아래 있어야 한다(`리드미_백엔드_구조.md` 5절). 메일 자동화에 쓸 도메인이 어차피 필요하므로 그 도메인 아래 두면 된다. 개발 때는 Vite 프록시로 `/api`를 서버에 넘긴다.
- 나중에 모바일 앱이나 리드미 커넥터가 생기면 그쪽에만 토큰 인증을 추가한다. 웹의 세션은 그대로 둔다.

## 3. 테이블

| 테이블 | 내용 |
|---|---|
| `users` | 계정. 이메일, 인증 시각, 비밀번호 해시(구글로만 가입하면 비어 있음), 표시 이름 |
| `user_identities` | 계정에 연결된 소셜 로그인. 지금은 `GOOGLE`만 |
| `email_tokens` | 가입 확인·비밀번호 재설정 메일의 토큰(해시로 보관) |
| `spring_session`, `spring_session_attributes` | 로그인 세션. spring-session-jdbc에 들어 있는 `schema-postgresql.sql`을 Flyway V2로 넣는다 |

### 3.1 생성 SQL

`V1__init.sql`의 앞부분이다. V1 한 파일에 로그인과 경험카드 테이블이 함께 있고, 뒷부분은 경험카드 문서 3.1에 있다. 아래는 마이그레이션 파일과 글자가 같다(파일 첫 줄의 `-- 리드미 V1: 로그인 · 경험카드`만 뺐다). 고칠 일이 생기면 마이그레이션 파일이 원본이다.

```sql
-- JDBC 주소에 currentSchema=readme 를 붙여 쓴다. Flyway, JPA, Spring Session 이 모두 이 스키마를 본다.
create schema if not exists readme;
set search_path to readme;

-- ── 계정 ─────────────────────────────────────────────────────────────
create table users (
  id                bigint generated always as identity primary key,
  email             varchar(320) not null,
  email_verified_at timestamptz,                 -- null 이면 아직 인증 전
  password_hash     varchar(100),                -- 구글로만 가입한 계정은 null
  display_name      varchar(50)  not null,
  created_at        timestamptz  not null default now(),
  updated_at        timestamptz  not null default now(),
  last_login_at     timestamptz
);
create unique index users_email_key on users (lower(email));

create table user_identities (
  id               bigint generated always as identity primary key,
  user_id          bigint       not null references users(id) on delete cascade,
  provider         varchar(20)  not null check (provider in ('GOOGLE')),
  provider_user_id varchar(255) not null,        -- 구글 ID 토큰의 sub
  provider_email   varchar(320),                 -- 연결할 때 구글이 준 이메일(참고용)
  created_at       timestamptz  not null default now(),
  unique (provider, provider_user_id),
  unique (user_id, provider)
);

create table email_tokens (
  id         bigint generated always as identity primary key,
  user_id    bigint      not null references users(id) on delete cascade,
  purpose    varchar(20) not null check (purpose in ('VERIFY_EMAIL', 'RESET_PASSWORD')),
  token_hash char(64)    not null unique,        -- 토큰 원문은 메일에만 있다. DB에는 SHA-256
  expires_at timestamptz not null,
  used_at    timestamptz,
  created_at timestamptz not null default now()
);
create index email_tokens_user_idx on email_tokens (user_id, purpose);
```

### 3.2 설계 이유

- **구글 계정은 `sub`로 식별한다.** 구글 문서는 `sub`가 모든 구글 계정에서 유일하고 재사용되지 않으니 이것을 사용자 키로 쓰라고 하고, `email`은 유일하지 않을 수 있고 바뀔 수 있으니 기본 식별자로 쓰지 말라고 한다. 그래서 `user_identities.provider_user_id`에 `sub`를 넣고, 이메일은 연결할 때 한 번만 쓴다.
- **제공자를 따로 테이블로 뺐다.** 카카오·네이버를 추가할 때 `provider` 제약에 값만 더하면 된다.
- **구글 로그인 콜백의 처리 순서**(L3):
  1. `sub`로 `user_identities`를 찾는다. 있으면 그 계정으로 로그인.
  2. 없고 구글의 `email_verified`가 true면 같은 이메일의 `users`를 찾는다.
     - 계정이 없다 → 새 계정을 만들고(인증 완료, 비밀번호 없음) 연결.
     - 인증을 마친 계정이 있다 → 그 계정에 연결.
     - 인증 전 계정이 있다 → 비밀번호를 지우고 인증 완료로 바꾼 뒤 연결. 다른 사람이 그 이메일로 먼저 가입만 해 둔 경우, 남의 비밀번호가 붙은 계정에 연결되는 것을 막는다.
  3. `email_verified`가 false면 로그인을 거부한다.
- **토큰은 해시로만 보관한다.** DB가 새도 메일 링크를 만들 수 없다. 한 번 쓰면 `used_at`을 채운다.

임시 PostgreSQL 16에 V1을 실행하고 아래를 SQL로 돌려 봤다. V1은 경험카드 테이블과 함께 확인했다.

## 4. API

공통 규칙(주소, 본문, 세션 쿠키, CSRF, 오류 꼴)과 공통 오류 코드는 구조 문서 5절에 있다.

| 메서드·주소 | 하는 일 | 비고 |
|---|---|---|
| `POST /api/auth/signup` | 이메일·비밀번호·표시 이름으로 가입, 가입 확인 메일 발송 | 인증을 마친 계정이 그 이메일을 쓰면 409 `EMAIL_TAKEN`. 이메일 존재 여부가 드러난다. 인증 전 계정이면 덮어쓴다(4.1) |
| `POST /api/auth/verify-email` | 메일의 토큰으로 인증 완료 | 지났거나 쓴 토큰이면 410 `LINK_EXPIRED`(4.1) |
| `POST /api/auth/verify-email/resend` | 가입 확인 메일 다시 보내기 | 계정이 없어도 같은 응답. 1분에 한 번, 24시간에 5번까지 보낸다(4.1) |
| `POST /api/auth/login` | 이메일·비밀번호 로그인 | 틀리면 401 `INVALID_CREDENTIALS`. 인증 전이면 403 `EMAIL_NOT_VERIFIED`. 15분 안에 10번 실패하면 429 `TOO_MANY_ATTEMPTS`(4.1) |
| `POST /api/auth/logout` | 로그아웃 | |
| `POST /api/auth/password-reset/request` | 재설정 메일 발송 | 계정이 없어도 같은 응답. 1분에 한 번, 24시간에 5번까지 보낸다(4.1) |
| `POST /api/auth/password-reset/check` | 재설정 링크를 아직 쓸 수 있는지 | 2026-11-14 더함(4.1). 쓸 수 없으면 410 `LINK_EXPIRED` |
| `POST /api/auth/password-reset/confirm` | 토큰과 새 비밀번호로 변경 | 그 계정의 세션을 모두 끊는다 |
| `GET /api/me` | 내 계정: 이메일, 표시 이름, 비밀번호 유무, 연결된 제공자 | 로그인 안 했으면 401. 2026-11-13에 만들었다. 응답은 `{ id, name, email, hasPassword, providers, google }`다(7절 1번). `google`은 2026-11-15에 더했다(7절 9번) |
| `PUT /api/me` | 표시 이름 바꾸기 | `{ "name" }`. 앞뒤 공백을 지우고 1~50자. 바뀐 내 계정을 `GET /api/me`와 같은 모양으로 돌려준다(4.1) |
| `PUT /api/me/password` | 로그인한 채로 비밀번호 바꾸기 | `{ "currentPassword", "newPassword" }`. 지금 비밀번호가 틀리면 400 `WRONG_PASSWORD`, 비밀번호가 없는 계정은 409 `NO_PASSWORD`. 이 세션은 두고 다른 세션을 모두 끊는다. 204(4.1) |
| `GET /api/me/withdrawal` | 탈퇴하면 지워질 것의 수와 내가 그룹장인 그룹 | 그룹마다 이어받을 사람을 싣는다. 혼자인 그룹은 `null`이고 탈퇴하면 지워진다(4.1) |
| `POST /api/me/withdraw` | 탈퇴 | `{ "password" }`, 비밀번호가 없는 계정은 `{ "email" }`로 확인한다. 틀리면 400 `WRONG_PASSWORD`·`WRONG_EMAIL`. 그룹장을 넘기고 계정을 지우고 세션을 모두 끊는다. 204(4.1) |

`GET /api/me` 말고는 2026-11-14에 만들었다(`auth/AuthController`, 로그아웃은 `SecurityConfig`).

`/api/me`의 고치기와 탈퇴 4개는 2026-11-15에 만들었다(`auth/MeController`, `MeService`, `WithdrawalQueries`).

구글 로그인은 Spring Security의 기본 경로를 쓴다. 직접 만드는 API가 아니다.

| 주소 | 하는 일 |
|---|---|
| `GET /oauth2/authorization/google` | 구글 로그인 화면으로 보낸다. 로그인 화면의 "구글로 계속하기"가 여는 주소 |
| `GET /login/oauth2/code/google` | 구글이 돌아오는 주소. 3.2의 순서대로 처리한 뒤 프런트로 돌려보낸다 |

2026-11-15에 만들었다(`SecurityConfig`의 `oauth2Login`, `auth/GoogleLoginHandler`). 구글 클라이언트 값이 없으면 두 주소는 404 `NOT_FOUND`다(4.1).

### 4.1 만들면서 정한 것

2026-11-14에 정한 것(화면·API 대응 문서 3절 2번, 19번, 20번과 이 문서 8절의 비밀번호 규칙):

- **비밀번호 규칙**: 8자 이상, UTF-8로 72바이트 이하, 조합 규칙은 없다. 어기면 400 `INVALID_INPUT`이다. 72바이트는 비밀번호 해시(BCrypt)가 쓰는 길이다(영문 72자, 한글 24자). 로그인에서는 규칙을 보지 않고, 72바이트를 넘으면 틀린 비밀번호와 같은 401이다.
- **인증 전 계정의 이메일로 다시 가입**: 409가 아니라, 새로 넣은 이름과 비밀번호로 덮어쓰고 전에 보낸 링크를 쓸 수 없게 한 뒤 새 확인 메일을 보낸다. 남이 내 이메일로 가입만 해 두어도 내가 가입할 수 있다. 인증을 마친 계정만 409 `EMAIL_TAKEN`이다. 메일 제한에 걸리면 덮어쓰기만 한다(아래 2026-11-15).
- **재설정이 인증도 마친다**: 비밀번호 재설정을 마치면 인증 전 계정도 인증을 마친 것으로 본다. 재설정 메일을 받았다는 것이 그 이메일의 주인이라는 뜻이라서다.
- **재설정 링크 미리 확인**: `POST /api/auth/password-reset/check { "token": … }`. 쓸 수 있으면 204, 아니면 410 `LINK_EXPIRED`. 링크를 쓰지는 않는다. 토큰은 서버 접속 기록에 남지 않게 주소가 아니라 본문에 넣는다.
- **로그인 뒤 돌아갈 곳**(구글 로그인을 만들 때): 돌아갈 화면은 프런트가 브라우저(localStorage)에 들고 있는다. 서버는 구글 로그인을 마치면 언제나 프런트의 정해진 주소 하나로, 실패하면 `/login?error=google`로 보낸다. 서버는 돌아갈 주소를 받지 않는다.
- **임시 로그인과 예시 데이터**: 임시 로그인을 걷어내고, dev 예시 사용자는 개발용 비밀번호로 실제 로그인을 한다(구조 문서 6.2).

만들면서 채운 빈칸:

- 돌려줄 값이 없는 요청(가입, 인증, 다시 보내기, 로그아웃, 재설정 요청·확인·바꾸기)은 204다. 로그인은 200과 `GET /api/me`와 같은 내 계정이다.
- 링크를 새로 보내면 그 사람에게 보낸 같은 종류의 쓰지 않은 링크를 쓸 수 없게 한다. 메일함의 옛 링크는 410이 된다. 재설정을 마치면 그 사람의 다른 재설정 링크도 쓸 수 없게 한다. 처음에는 행을 지웠고, 2026-11-15부터는 `used_at`을 채우고 행을 남긴다(아래).
- 인증을 마친 계정에는 확인 메일을 다시 보내지 않는다(응답은 같다).
- 구글로만 가입해 비밀번호가 없는 계정도 재설정 메일을 받는다. 재설정을 마치면 비밀번호가 생겨 이메일로도 로그인한다.
- 로그아웃은 세션 행과 쿠키를 지우고 204를 준다. 로그인하지 않았어도 204다. 다음 로그인에 쓸 새 `XSRF-TOKEN` 쿠키를 함께 준다.
- 이메일과 표시 이름은 앞뒤 공백을 지운다. 이메일은 대소문자를 가리지 않고 찾고, 가입할 때 넣은 그대로 두고 그 주소로 메일을 보낸다.
- 없는 이메일로 로그인할 때도 비밀번호 해시를 한 번 견준다. 계정이 있을 때와 응답 시간이 비슷하다.
- 메일은 DB 변경이 커밋된 뒤에 보낸다. 보내지 못하면 오류를 내지 않고 기록만 남긴다(토큰과 이메일은 남기지 않는다). 계정은 저장되었으므로 "다시 받기"로 다시 보낸다.
- 메일의 보내는 사람은 `app.mail-from`(운영은 환경 변수 `MAIL_FROM`)이다.
- 메일은 요청 안에서 바로 보낸다. 계정이 있을 때만 메일을 보내므로 다시 보내기와 재설정 요청은 계정이 있을 때 조금 늦게 답한다. 가입이 409로 이메일 존재를 이미 알려 주므로 그대로 둔다.

2026-11-15에 정한 것(요청 횟수 제한):

- **링크 메일 제한**: 같은 사람에게 같은 종류(가입 확인, 재설정)의 링크는 1분에 한 번, 최근 24시간에 5번까지 보낸다. 가입, 확인 메일 다시 보내기, 재설정 요청이 모두 같은 곳(`AccountService.sendLink`)을 지나므로 셋에 다 걸린다. 가입 확인과 재설정은 따로 센다.
- 제한에 걸리면 새 링크를 만들지 않고 메일도 보내지 않는다. 전에 보낸 링크는 그대로 쓸 수 있다. 응답은 똑같이 204다. 계정이 있는지도, 제한에 걸렸는지도 응답으로 드러나지 않는다.
- 인증 전 계정에 1분 안에 다시 가입하면 이름과 비밀번호는 바꾸고 메일은 보내지 않는다. 처음 메일의 링크로 인증을 마치고, 로그인은 바꾼 비밀번호로 한다.
- 횟수는 `email_tokens.created_at`으로 센다. 마이그레이션은 없다. 쓴 링크와 쓸 수 없게 한 링크도 센다. 그래서 옛 링크를 지우지 않고 `used_at`을 채운다. 행은 지우지 않는다. 쌓이면 하루 지난 행을 지우는 일을 따로 둔다.
- 같이 들어온 요청들은 모두 횟수 검사를 지날 수 있다. 연결 풀이 5라서 한 번에 많아야 5통이다. 문제가 되면 세기 전에 사용자 행을 잠근다.
- 남이 내 주소로 재설정을 5번 요청하면 나는 24시간 동안 새 재설정 메일을 받지 못한다. 마지막에 온 링크는 1시간 동안 쓸 수 있다. 남의 주소로 메일을 계속 보내지 못하게 하는 값으로 받아들인다.
- **로그인 실패 제한**: 이메일마다 15분 안에 10번 로그인하지 못하면 그 이메일의 로그인을 429 `TOO_MANY_ATTEMPTS`로 막는다. 이메일은 앞뒤 공백을 지우고 소문자로 맞춘 글자로 세고, 계정도 그 글자로 찾는다. 따로 하면 "İ"처럼 자바와 PostgreSQL이 다르게 낮추는 글자로 같은 계정에 세는 칸을 새로 만들 수 있다(i가 n개인 주소는 칸이 2ⁿ개). 대신 그런 글자가 든 주소로 가입한 계정은 그 글자 그대로는 로그인하지 못할 수 있다. 드문 경우라 그대로 둔다.
- 비밀번호를 보기 전에 막으므로 막힌 동안에는 맞는 비밀번호도 429다. 15분 안의 실패가 10번 아래로 줄면 풀린다. 막힌 시도는 세지 않는다. 로그인에 성공하면 센 것을 지운다.
- 계정이 없는 이메일도 똑같이 센다. 막혔다는 것이 계정이 있다는 뜻이 아니다.
- 비밀번호를 재설정하면 그 계정의 이메일에서 센 것도 지운다. 10번 틀린 사람은 대개 재설정하는 사람이라, 새 비밀번호로 바로 들어오게 한다.
- 시도는 비밀번호를 견주기 전에 세고, 성공하면 지운다. 같이 들어온 요청들이 모두 검사를 지나 10번을 넘기지 못하게 하려는 것이다. 그래서 비밀번호는 맞지만 인증 전(403)인 시도도 실패로 센다.
- 센 것은 서버 메모리(`auth/LoginThrottle`)에 둔다. 서버를 다시 띄우면 지워지고, 서버가 여러 대면 따로 센다. 서버가 여러 대가 되면 DB나 Redis로 옮긴다. 아무 이메일이나 넣어 메모리를 채우지 못하게 두 가지로 묶는다. 15분마다 지난 실패만 남은 이메일을 지우고, 이메일은 10만 개(50MB쯤)까지만 든다. 넘으면 가장 먼저 들어온 이메일부터 버린다. 그래서 새 이메일을 아주 많이 넣으면 다른 이메일에서 센 것이 15분보다 빨리 빠질 수 있다.
- 로그인의 이메일은 320자(`users.email` 칸의 길이)까지 받는다. 넘으면 400 `INVALID_INPUT`이다. 메모리에 드는 이메일의 길이를 묶으려는 것이다.
- 세션 유지 기간은 바꾸지 않았다. 마지막 사용 후 14일, 쿠키 365일 그대로다(구조 문서 5.1).

2026-11-15 구글 로그인을 만들며 정한 것:

- **주소**: 4절 표의 Spring Security 기본 경로 그대로다. `/api` 아래가 아닌 것은 fetch로 부르는 API가 아니라 브라우저가 이동하는 주소라서다. `SecurityConfig`는 이 두 주소만 로그인 없이 연다. 구글로 가는 요청과 돌아오는 요청은 GET이라 CSRF 검사를 받지 않고, 대신 Spring이 세션에 둔 `state`와 OIDC `nonce`로 맞춰 본다. 다른 API의 CSRF 검사는 그대로다.
- **켜고 끄기**: 구글 클라이언트 값(`spring.security.oauth2.client.registration.google`)이 있을 때만 켠다. 없으면 서버는 전처럼 뜨고 두 주소는 404 `NOT_FOUND`다. 개발은 `backend/application-local.yml`, 운영은 환경 변수 `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`이다(6.1). 운영은 다른 운영 값처럼 이 값이 빠지면 서버가 뜨지 않는다.
- **`application-local.yml`은 dev 프로필만 읽는다**: 전에는 모든 프로필이 읽었다. 내 PC에 구글 값을 넣어도 test 프로필만 켜는 테스트의 결과가 바뀌지 않게 `application-dev.yml`로 옮겼다. test와 dev를 함께 켜는 `dev/DevProfileTests`는 이 파일을 읽으므로, 내 PC에 구글 값이 있으면 그 테스트에서는 구글 로그인이 켜진다.
- **계정 찾기·연결·만들기**(3.2의 순서, `AccountService.loginWithGoogle`):
  - `sub`가 연결된 계정이 있으면 그 계정이다. 이때는 구글의 이메일과 `email_verified`를 보지 않는다.
  - 연결된 계정이 없으면 `email_verified`가 true일 때만 같은 이메일(대소문자 무시)의 계정을 찾는다. false면 연결도, 새 계정도 없이 거부한다.
  - 계정이 없으면 인증을 마친, 비밀번호 없는 계정을 만든다. 이름은 구글의 `name`이고, 없으면 이메일의 `@` 앞이다. 50자를 넘으면 자른다.
  - 인증을 마친 계정이면 연결한다. 이름과 비밀번호는 그대로 둔다.
  - 인증 전 계정이면 3.2대로 비밀번호를 지우고 인증을 마친 뒤 연결한다. 3.2에 없던 것을 이렇게 채웠다: 이름도 구글의 것으로 바꾼다(인증 전 계정에 다시 가입하면 이름을 덮어쓰는 것과 같다). 보낸 가입 확인 링크를 쓸 수 없게 한다(행은 남긴다. 메일 제한이 행으로 센다). 인증 전 계정은 로그인할 수 없어 세션이 없으므로 세션은 끊지 않는다.
  - 그 계정에 다른 구글 계정이 이미 연결되어 있으면 거부한다(`user_identities`의 `unique (user_id, provider)`). 연결을 바꾸지 않는다.
  - `provider_email`에는 연결할 때 구글이 준 이메일을 넣고 그 뒤로 고치지 않는다. 로그인할 때마다 `last_login_at`을 남긴다.
- **정한 규칙의 한계**: Gmail이 아닌 주소에서 구글의 `email_verified`는 그 구글 계정을 만들 때 주소를 확인했다는 뜻일 뿐이다. 그 주소가 나중에 다른 사람에게 넘어가면(예: 회사 메일함을 다른 사람이 물려받음) 옛 구글 계정이 여기서 새 주인의 계정에 연결될 수 있다.
- **세션**: 계정을 정한 뒤 이메일 로그인과 같은 `LoginSession.start`를 부른다. 세션에는 구글의 토큰이 아니라 `LoginUser`가 남고 주인 이름은 사용자 id다. 그래서 `@CurrentUser`, `GET /api/me`, 재설정 때 세션 끊기가 그대로 된다. Spring의 구글 필터가 먼저 세션에 넣은 구글 로그인 정보는 이것으로 덮인다. 거부하거나 오류가 나면 세션을 지운다. 성공하면 새 `XSRF-TOKEN` 쿠키를 준다.
- **돌려보내는 곳**: 성공은 `{app.frontend-origin}/`(홈), 실패는 `{app.frontend-origin}/login?error=google`이다. 실패는 동의 거부, 구글의 오류, `state`가 맞지 않음, 위의 거부, 서버 오류를 모두 포함하고 이유를 나누지 않는다.
- **기록**: 토큰과 이메일을 남기지 않는다. 거부와 실패는 이유(구글의 오류 코드, 예외 이름, 사용자 id)만 남긴다.
- **알고 둔 것**: Spring이 구글의 access token을 구글 계정마다 메모리에 하나씩 둔다. 쓰지 않고, 서버를 다시 띄우면 사라진다(`SecurityConfig`의 shortcut 주석). 구글로 가기 시작하면 `state`를 두려고 세션 행이 생긴다. 끝내지 않고 떠나면 그 행은 유휴 제한(14일) 뒤에 지워진다.

규칙에 맞지 않는 비밀번호, 빈 칸, 이메일 꼴이 아닌 값은 공통 400 `INVALID_INPUT`이다(구조 문서 5.2).

2026-11-15에 정한 것(내 계정 고치기와 탈퇴. 화면·API 대응 문서 3절 17번·18번, 그룹 문서 9절):

- **표시 이름 바꾸기**: `PUT /api/me { "name": … }`. 앞뒤 공백을 지우고 1~50자(`users.display_name` 칸의 길이)다. 어기면 400 `INVALID_INPUT`이다. 바뀐 내 계정을 `GET /api/me`와 같은 모양으로 돌려준다. 그룹의 공개 범위 바꾸기처럼 바꾼 것을 돌려준다.
- **로그인한 채로 비밀번호 바꾸기**: `PUT /api/me/password { "currentPassword": …, "newPassword": … }`. 새 비밀번호는 위의 비밀번호 규칙을 따른다. 지금 비밀번호가 틀리면 400 `WRONG_PASSWORD`다. 401이 아닌 것은 프런트가 401을 "로그인하지 않았다"로 보기 때문이다.
- 지금 비밀번호는 규칙도 빈칸도 보지 않는다. 비었거나 72바이트를 넘으면 틀린 것과 같다.
- 비밀번호가 없는 계정(구글로만 가입)은 지금 비밀번호 칸에 무엇을 넣었든 409 `NO_PASSWORD`다. 비밀번호는 재설정 메일로 만든다. 재설정은 이런 계정에도 메일을 보낸다(위).
- 바꾸면 204다. 이 브라우저의 세션은 두고 그 사람의 다른 세션을 모두 지운다. 재설정처럼 커밋 뒤에 지운다. 이 세션의 id는 바꾸지 않는다.
- 비밀번호를 바꿔도 메일함의 재설정 링크(1시간)는 그대로 쓸 수 있다. 재설정 링크를 다루는 코드는 건드리지 않았다.
- **틀린 횟수는 세지 않는다**: 비밀번호 바꾸기와 탈퇴 확인에서 비밀번호를 틀려도 세지 않는다. 세션을 가진 사람은 계속 맞혀 볼 수 있다(`MeService`의 shortcut 주석). 세션을 먼저 훔쳐야 하는 일이라 그대로 둔다. 문제가 되면 로그인처럼 사람마다 센다.
- **탈퇴 미리 보기**: `GET /api/me/withdrawal`. 설정 화면의 `WithdrawInfo`와 같은 모양에 `leads[].id`와 `leads[].successor`를 더했다(7절 13번).
  - `cards`, `sources`: 내 경험카드(`experience_cards`)와 내가 올린 자료(`card_sources`)의 수.
  - `postings`: 내 공고(`user_postings`) 행의 수. 관심만 켜고 상태를 정하지 않은 공고도 센다.
  - `groups`: 내가 멤버인 그룹의 수. 그룹장인 그룹도 센다.
  - `leads`: 내가 그룹장인 그룹. 들어간 순서다. `others`는 나 말고 멤버 수, `successor`는 그룹장을 이어받을 사람(`{ id, name }`)이다. 혼자인 그룹은 `successor`가 `null`이고, 탈퇴하면 그룹이 지워진다.

  ```json
  {
    "cards": 6, "sources": 3, "postings": 9, "groups": 3,
    "leads": [
      { "id": 1, "name": "백엔드 스터디", "others": 2, "successor": { "id": 2, "name": "가람" } },
      { "id": 4, "name": "혼자 그룹", "others": 0, "successor": null }
    ]
  }
  ```

- **탈퇴의 확인**: `POST /api/me/withdraw`. 비밀번호가 있는 계정은 `{ "password": … }`로 확인하고, 틀리면 400 `WRONG_PASSWORD`다. 비밀번호가 없는 계정(구글로만 가입)은 `{ "email": … }`로 확인한다. 앞뒤 공백을 지우고 대소문자를 가리지 않고 계정의 이메일과 같아야 한다. 다르면 400 `WRONG_EMAIL`이다. 비밀번호 계정이 이메일만 보내면 `WRONG_PASSWORD`, 비밀번호 없는 계정이 비밀번호만 보내면 `WRONG_EMAIL`이다. 확인하지 못하면 아무것도 지우지 않는다.
- 확인의 코드를 둘로 나눈 것은 화면이 틀린 칸 아래에 알리게 하려는 것이다. 메시지도 칸에 맞게 다르다.
- **탈퇴의 순서**: 한 트랜잭션에서 (1) 그룹장인 그룹을 넘기고(그룹 문서 4절의 2026-11-15) (2) `users` 행을 지운다. 나머지는 외래 키가 지우거나 비운다(아래 표). 성공하면 204다.
- 커밋 뒤에 그 사람의 세션을 모두 지운다. 요청을 보낸 세션도 끝내고 응답에서 세션 쿠키를 지운다. 응답을 받은 브라우저는 로그인하지 않은 상태이고 `GET /api/me`가 401이다. `XSRF-TOKEN` 쿠키는 세션과 무관해 그대로 둔다.
- 지운 계정은 되살리지 않는다. 같은 이메일로 새로 가입할 수 있다.

탈퇴할 때 `users`를 가리키는 외래 키(V1, V3 전부, 2026-11-15 확인)가 하는 일이다. 지우기를 막는 외래 키는 없다. 그룹·공고 문서 3.3에서 SQL로 확인한 것과 같고, `auth/WithdrawTests`가 본다.

| 테이블.칸 | on delete | 결과 |
|---|---|---|
| `user_identities.user_id`, `email_tokens.user_id` | cascade | 구글 연결과 메일 링크가 지워진다 |
| `card_sources.user_id`, `card_extraction_jobs.user_id`, `experience_cards.user_id` | cascade | 자료, 추출 작업, 카드가 지워진다. 카드의 태그·쓰임·사실은 카드를 따라 지워진다 |
| `llm_usage.user_id` | set null | 사용 기록은 남고 사람만 빈다 |
| `group_members.user_id` | cascade | 멤버 자격이 지워지고 그 그룹의 내 관심(`group_post_interests`)이 따라 지워진다. 그룹장인 그룹은 그 전에 넘긴다 |
| `user_postings.user_id` | cascade | 내 공고와 지원 상태가 지워진다 |
| `groups.created_by`, `group_invites.created_by` | set null | 그룹과 내가 만든 초대 링크는 남는다. 초대 링크는 만료 전까지 그대로 쓸 수 있다 |
| `postings.created_by`, `postings.deadline_set_by` | set null | 공고 본체는 남는다 |
| `group_posts.posted_by`, `group_posts.taken_down_by` | set null | 그룹에 올린 공고는 남고 올린 사람·내린 사람만 빈다 |
| `group_post_comments.author_id` | set null | 댓글은 남고 쓴 사람만 빈다 |

세션 행(`spring_session`)은 외래 키가 없다(주인 이름이 사용자 id의 글자다). 그래서 서버가 지운다.

## 5. 화면과 API

|---|---|
| 로그인 | `POST /api/auth/login`, `GET /oauth2/authorization/google`, `GET /api/me` |
| 회원가입 | `POST /api/auth/signup` |

## 6. 구글 로그인의 조건

- Google Cloud 프로젝트에서 OAuth 클라이언트를 만들고, 리디렉션 주소로 `{서버 주소}/login/oauth2/code/google`을 등록한다. 로컬과 운영 주소를 각각 넣는다.
- 요청 범위는 `openid`, `email`, `profile`만 쓴다.
- 구글 문서 기준으로, Testing 상태의 앱은 테스트 사용자 100명 제한이 있지만 기본 신원 범위만 요청하는 앱은 허용 목록에 없는 사용자도 접근할 수 있다는 예외가 표에 적혀 있다. 인증(verification)은 민감·제한 범위를 요청하는 공개 앱에 필요하다고 되어 있다.
- 브랜드 인증을 받기 전에는 동의 화면에 앱 이름과 로고가 표시되지 않는다.
- 기본 범위만 쓰는 앱이 운영 상태에서 인증 없이 되는지는 문서가 명시하지 않았다. 실제 콘솔에서 확인이 필요하다.

### 6.1 클라이언트 만들기와 값 넣기

2026-11-15에 확인한 Google Cloud 콘솔의 메뉴 이름(Google Auth Platform)이다. 클라이언트 하나에 개발과 운영의 돌아올 주소를 함께 넣어도 된다.

1. Google Cloud 콘솔에서 프로젝트를 고르거나 만든다.
2. 메뉴 > Google Auth Platform으로 간다. "not configured yet"이 보이면 **Get started**를 누르고 앱 이름(리드미), 사용자 지원 이메일, Audience(**External**), 연락처 이메일을 넣어 만든다.
3. **Data Access**에서 범위는 `openid`, `.../auth/userinfo.email`, `.../auth/userinfo.profile`만 둔다. 모두 민감하지 않은 범위다. 서버가 구글로 보낼 때 `openid email profile`을 요청하므로 여기서 더하지 않아도 동작한다.
4. **Audience**는 처음에 Testing 상태다. **Test users**에 내 구글 계정과 같이 써 볼 사람의 계정을 더한다. 위의 예외(기본 범위만 쓰면 목록 밖의 사용자도 된다)는 아직 확인하지 않았다.
5. **Clients** > **Create client**에서 Application type을 **Web application**으로 고르고 이름(예: `readme`)을 넣는다.
   - **Authorized JavaScript origins**: 비워 둔다. 서버가 구글로 보내고 받는 방식이라 브라우저의 스크립트가 구글을 부르지 않는다.
   - **Authorized redirect URIs**:
     - 개발: `http://localhost:8080/login/oauth2/code/google`
     - 운영(도메인이 정해지면 더한다): `https://api.<도메인>/login/oauth2/code/google`
   - 서버는 돌아올 주소를 받은 요청의 주소로 만든다. 개발은 브라우저가 서버(8080)로 바로 가므로 위의 주소가 된다. 운영은 Cloudflare와 Caddy 뒤라서 `server.forward-headers-strategy: framework`(`application-prod.yml`)가 `https://api.<도메인>`으로 만든다.
   - 글자가 하나라도 다르면(`http`·`https`, 포트, 끝의 `/`) 구글이 `redirect_uri_mismatch`를 낸다. 고친 값이 적용되기까지 몇 분에서 몇 시간 걸릴 수 있다.
6. **Create**를 누르면 클라이언트 ID와 보안 비밀이 나온다. 보안 비밀은 만들 때 한 번만 전부 보이므로 바로 복사하거나 JSON으로 받아 둔다. 잃어버리면 새로 만든다.
7. 값을 넣는다.
   - 개발: `backend/application-local.yml`을 만든다. git에 올라가지 않고 dev 프로필만 읽는다(test 프로필만 켜는 테스트는 읽지 않고, test와 dev를 함께 켜는 `dev/DevProfileTests`는 읽는다).

     ```yaml
     spring:
       security:
         oauth2:
           client:
             registration:
               google:
                 client-id: <클라이언트 ID>.apps.googleusercontent.com
                 client-secret: <보안 비밀>
                 scope: openid, email, profile
     ```

   - 운영: 서버의 환경 변수 파일(`/etc/readme/readme.env`)에 `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`을 넣는다(`backend/.env.example`). 운영은 이 값이 없으면 서버가 뜨지 않는다.
8. 개발에서 확인: 서버를 다시 띄우고(`.\gradlew bootRun`) 브라우저로 `http://localhost:8080/oauth2/authorization/google`을 연다. 구글 로그인을 마치면 `http://localhost:5173/`로 돌아온다(프런트가 꺼져 있으면 그 화면만 열리지 않는다). 같은 브라우저로 `http://localhost:8080/api/me`를 열면 `providers`에 `google`이 있는 내 계정이 보인다.

## 7. 프런트와 맞출 것

1. (2026-11-13 서버를 만들며 더함) `GET /api/me`는 `Viewer`의 `id`, `name`에 `email`, `hasPassword`, `providers`(예: `["google"]`)를 더해 준다. 프런트는 둘만 쓰면 된다.
2. 프런트의 가입·인증·재설정 화면이 기대는 것(`EMAIL_TAKEN`, 토큰 확인, 메일 링크의 프런트 주소)은 화면·API 대응 문서 4절에 있다. 2026-11-14에 서버가 그대로 맞췄다. 아래는 그때 더한 것이다.
3. 지났거나 쓴 링크는 410 `LINK_EXPIRED`다. 프런트의 `"expired"`가 이것이다(`verifyEmail`, `resetPassword`). `checkResetToken`은 `POST /api/auth/password-reset/check`에 `{ "token": … }`을 보내 204면 `true`, 410이면 `false`다.
4. 가입 확인은 `POST /api/auth/verify-email { "token": … }`이다. 가짜 서버의 주석에 있는 `GET /api/auth/verify?token=`이 아니다.
5. 로그인의 틀린 비밀번호는 401 `INVALID_CREDENTIALS`다. 401을 한꺼번에 "로그인 화면으로 보내기"로 처리한다면, 로그인 요청에서는 `code`를 보고 칸 아래에 알린다.
6. 돌려줄 값이 없는 요청은 204다. 로그인은 `GET /api/me`와 같은 내 계정을 돌려준다.
7. 바꾸는 요청에 넣을 `XSRF-TOKEN` 쿠키는 쿠키가 없는 요청의 응답에 실린다. 화면을 처음 열 때 부르는 `GET /api/me`(로그인 전이면 401)가 쿠키를 받는다. 로그인과 로그아웃은 새 쿠키를 주므로 그 뒤에는 쿠키를 다시 읽어 헤더에 넣는다.
8. 비밀번호 칸의 규칙은 서버와 같다: 8자 이상(화면의 "8자 이상"과 같다), 72바이트 이하. 한글 25자 이상은 서버가 400을 준다.
9. (2026-11-15 더함) 로그인이 429 `TOO_MANY_ATTEMPTS`면 그 이메일로 15분 안에 10번 실패한 것이다. 응답의 `message`를 로그인 칸 아래에 보여 준다. 막힌 동안에는 비밀번호가 맞아도 이 응답이다. 확인 메일 다시 보내기와 재설정 요청 화면은 바꿀 것이 없다. 메일 제한(1분에 한 번, 24시간에 5번)에 걸려도 204이고 메일만 가지 않는다.
10. (2026-11-15 구글 로그인을 만들며 더함) 로그인·회원가입 화면의 "구글로 계속하기"는 fetch가 아니라 페이지 이동으로 서버의 `GET /oauth2/authorization/google`을 연다. 서버 주소를 붙인다: 개발 `http://localhost:8080/oauth2/authorization/google`, 운영 `https://api.<도메인>/oauth2/authorization/google`. 개발에서 Vite 프록시로 넘기지 않는다. 구글에 등록한 돌아올 주소가 서버(8080)의 것이라서다(6.1). 이동하기 전에 돌아갈 화면을 localStorage에 둔다(4.1).
11. 성공하면 서버가 `{프런트 주소}/`(홈)로 보낸다. 세션 쿠키와 새 `XSRF-TOKEN` 쿠키가 실려 있으므로 그 뒤 요청은 쿠키를 다시 읽어 헤더에 넣는다. localStorage에 돌아갈 화면이 있으면 홈에서 그리로 옮긴다.
12. 실패하면 서버가 `{프런트 주소}/login?error=google`로 보낸다. 로그인 화면은 이 값이 있으면 안내를 보인다(예: "구글로 로그인하지 못했습니다. 다시 시도해 주세요"). 이유(동의 거부, 구글이 확인하지 않은 이메일, 다른 구글 계정이 이미 연결된 계정, 오류)는 나누지 않는다.
13. 구글 클라이언트 값이 없는 서버에서는 두 주소가 404다. 구글 로그인이 켜졌는지 알려 주는 API는 없다.
14. 인증 전 계정의 이메일로 구글 로그인을 하면 그 계정의 비밀번호가 지워지고 이름이 구글의 것으로 바뀐다(4.1). `GET /api/me`의 `hasPassword`가 false, `providers`가 `["google"]`이 된다.
15. (2026-11-15 내 계정 고치기와 탈퇴를 만들며 더함) `GET /api/me`에 `google`을 더했다. 연결한 구글 계정이 있으면 `{ "email": … }`(연결할 때 구글이 준 이메일), 없으면 `null`이다. 설정 화면의 `AccountInfo.google`과 같은 모양이라 그대로 쓰면 된다. `providers`는 전처럼 `["google"]` 꼴의 이름 목록이다. 그 안에 이메일을 넣지 않고 칸을 따로 둔 것은 이름 목록에 기대는 곳(구글 로그인 테스트)을 깨지 않으려는 것이다. `user_identities.provider_email`이 빈 행이면 `{ "email": null }`일 수 있다. 구글 로그인이 만드는 행은 늘 채운다.
16. `AccountInfo.emailVerified`는 `GET /api/me`에 없다. 로그인한 계정은 모두 인증을 마쳤다(L4. 구글로 만든 계정도 인증을 마친 채로 생긴다). 프런트는 `true`로 두면 된다.
17. 표시 이름 바꾸기는 `PUT /api/me { "name": … }`이고 바뀐 내 계정을 돌려준다. 서버는 50자까지 받는다. 프런트의 `NAME_MAX_LENGTH`(20)는 서버보다 짧아 그대로 둬도 된다.
18. 비밀번호 바꾸기는 `PUT /api/me/password { "currentPassword", "newPassword" }`이고 204다. 틀린 지금 비밀번호는 400 `WRONG_PASSWORD`(401이 아니다), 비밀번호가 없는 계정은 409 `NO_PASSWORD`다. 지금 내 정보 화면의 "비밀번호 바꾸기"는 재설정 화면으로 가는 링크다. 이 API를 쓸지, 비밀번호가 없는 계정(`hasPassword`가 false)은 재설정으로 보낼지는 프런트가 정한다. 바꾸면 이 브라우저는 로그인한 채로 있고 다른 기기는 로그아웃된다.
19. 탈퇴 미리 보기는 `GET /api/me/withdrawal`이다. `WithdrawInfo`와 같고 `leads[]`에 `id`와 `successor`(`{ id, name }` 또는 `null`)가 더 있다. 탈퇴 화면의 "그룹장 없이 남습니다" 안내는 바뀌어야 한다: `successor`가 있으면 그 사람이 그룹장이 되고, `null`이면 그룹이 지워진다. 그룹의 `key`는 이름 대신 `id`를 쓰면 된다(이름은 겹칠 수 있다).
20. 탈퇴는 `POST /api/me/withdraw`이고 204다. 비밀번호가 있으면 `{ "password" }`, 없으면(`hasPassword`가 false) 계정의 이메일을 `{ "email" }`로 보낸다. 틀리면 400 `WRONG_PASSWORD` 또는 `WRONG_EMAIL`이다. 지금 화면에는 비밀번호 칸만 있어 비밀번호가 없는 계정은 탈퇴할 수 없다. 성공하면 서버가 세션과 세션 쿠키를 지우므로 응답 뒤에는 로그인하지 않은 상태다.
