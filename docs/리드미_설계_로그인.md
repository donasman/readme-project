## 2. 가정

| # | 항목 | 초안의 값 | 다른 선택지 | 바뀌는 곳 |
|---|---|---|---|---|
| L1 | 인증 담당 | **확정**: Spring Security. Supabase는 DB로만 쓴다 | Supabase Auth(구글·이메일 가입, 인증 메일 포함) | 계정 테이블 3개와 인증 API 전부 |
| L2 | 로그인 유지 | **확정**: 서버 세션 쿠키(Spring Session JDBC) | JWT(access + refresh) | 세션 테이블, 프런트 요청 방식, CSRF 처리 |
| L3 | 계정 연결 | 구글 이메일과 같은 이메일의 계정이 있으면 한 계정으로 연결(3.2) | 항상 별도 계정 / 로그인한 상태에서만 직접 연결 | 구글 콜백 로직. 테이블은 같다 |
| L4 | 인증 전 계정 | 이메일 인증 전에는 로그인 불가 | 로그인은 되고 기능만 제한 | 로그인 API, 프런트 안내 |
| L5 | 토큰 유효 시간 | 가입 확인 24시간, 비밀번호 재설정 1시간 | 다른 값 | 설정값 |

L1과 L2는 2026-11-12에 확정했다. L3~L5는 아직 가정이다. L4와 L5는 2026-11-14에 초안의 값대로 만들었고, L3은 구글 로그인을 만들 때 쓴다. 옛 가정 5(전용 스키마 `readme`)는 구조 문서 7절로 옮겼다.

**L1을 Spring Security로 정한 이유**

- Supabase Auth를 쓰면 첫날부터 Supabase가 필요하다. "지금은 Postgres, Supabase는 나중에 생각"이라는 순서와 맞지 않는다.
- 계정이 Supabase의 `auth.users`에 생기고 리드미 데이터는 Spring이 관리하는 테이블에 있어, 사용자 저장소가 둘이 된다. 탈퇴·그룹 초대처럼 계정을 건드리는 기능마다 Spring이 Supabase 관리 API를 불러야 한다.
- Supabase Auth가 덜어 주는 것 중 메일 발송은 실제로는 덜어지지 않는다. 기본 메일 서버는 팀 구성원 주소로만 보내고 시간당 2통 제한이며 운영용이 아니라고 문서에 적혀 있다. 어느 쪽이든 발송 수단을 따로 붙여야 한다.
- 남는 차이는 가입·인증·재설정 API 7개를 직접 만드느냐인데, Spring Security가 비밀번호 해시, 구글 로그인, 세션, CSRF를 이미 제공한다.
- 잃는 것: Supabase Auth의 요청 횟수 제한, 유출 비밀번호 검사, 2단계 인증 같은 기능은 필요해지면 직접 붙여야 한다.

**L2를 세션 쿠키로 정한 이유**

- 접속하는 쪽이 React 웹 화면 하나다. JWT가 유리한 경우(모바일 앱, 외부 개발자용 API, 서버 여러 대가 서로 호출)가 지금 없다.
- Spring Security의 구글 로그인은 기본이 세션 방식이다. JWT로 가면 구글 로그인 중간 상태 보관, 토큰 발급, refresh 토큰 보관·교체·폐기를 직접 만들어야 한다. 직접 만드는 보안 코드가 늘어난다.
- 로그아웃, 비밀번호 재설정, 탈퇴, 그룹 강퇴가 즉시 반영된다. 세션 행을 지우면 끝이다. JWT는 만료 전까지 유효해서 차단 목록을 따로 둬야 한다.
- 쿠키를 `HttpOnly`로 두면 화면의 스크립트가 로그인 정보를 읽을 수 없다.
- 세션을 DB에 두므로(Spring Session JDBC) 서버를 다시 배포해도 로그인이 풀리지 않는다.
- 조건: 프런트와 서버가 같은 사이트 주소 아래 있어야 한다(`리드미_백엔드_구조.md` 5절). 메일 자동화에 쓸 도메인이 어차피 필요하므로 그 도메인 아래 두면 된다. 개발 때는 Vite 프록시로 `/api`를 서버에 넘긴다.
- 나중에 모바일 앱이나 리드미 커넥터가 생기면 그쪽에만 토큰 인증을 추가한다. 웹의 세션은 그대로 둔다.

## 3. 테이블

| 테이블 | 내용 |
|---|---|
| `users` | 계정. 이메일, 인증 시각, 비밀번호 해시(구글로만 가입하면 비어 있음), 표시 이름 |
| `user_identities` | 계정에 연결된 소셜 로그인. 지금은 `GOOGLE`만 |
| `email_tokens` | 가입 확인·비밀번호 재설정 메일의 토큰(해시로 보관) |
| `spring_session`, `spring_session_attributes` | 로그인 세션. spring-session-jdbc에 들어 있는 `schema-postgresql.sql`을 Flyway V2로 넣는다 |

### 3.1 생성 SQL

`V1__init.sql`의 앞부분이다. V1 한 파일에 로그인과 경험카드 테이블이 함께 있고, 뒷부분은 경험카드 문서 3.1에 있다. 아래는 마이그레이션 파일과 글자가 같다(파일 첫 줄의 `-- 리드미 V1: 로그인 · 경험카드`만 뺐다). 고칠 일이 생기면 마이그레이션 파일이 원본이다.

```sql
-- JDBC 주소에 currentSchema=readme 를 붙여 쓴다. Flyway, JPA, Spring Session 이 모두 이 스키마를 본다.
create schema if not exists readme;
set search_path to readme;

-- ── 계정 ─────────────────────────────────────────────────────────────
create table users (
  id                bigint generated always as identity primary key,
  email             varchar(320) not null,
  email_verified_at timestamptz,                 -- null 이면 아직 인증 전
  password_hash     varchar(100),                -- 구글로만 가입한 계정은 null
  display_name      varchar(50)  not null,
  created_at        timestamptz  not null default now(),
  updated_at        timestamptz  not null default now(),
  last_login_at     timestamptz
);
create unique index users_email_key on users (lower(email));

create table user_identities (
  id               bigint generated always as identity primary key,
  user_id          bigint       not null references users(id) on delete cascade,
  provider         varchar(20)  not null check (provider in ('GOOGLE')),
  provider_user_id varchar(255) not null,        -- 구글 ID 토큰의 sub
  provider_email   varchar(320),                 -- 연결할 때 구글이 준 이메일(참고용)
  created_at       timestamptz  not null default now(),
  unique (provider, provider_user_id),
  unique (user_id, provider)
);

create table email_tokens (
  id         bigint generated always as identity primary key,
  user_id    bigint      not null references users(id) on delete cascade,
  purpose    varchar(20) not null check (purpose in ('VERIFY_EMAIL', 'RESET_PASSWORD')),
  token_hash char(64)    not null unique,        -- 토큰 원문은 메일에만 있다. DB에는 SHA-256
  expires_at timestamptz not null,
  used_at    timestamptz,
  created_at timestamptz not null default now()
);
create index email_tokens_user_idx on email_tokens (user_id, purpose);
```

### 3.2 설계 이유

- **구글 계정은 `sub`로 식별한다.** 구글 문서는 `sub`가 모든 구글 계정에서 유일하고 재사용되지 않으니 이것을 사용자 키로 쓰라고 하고, `email`은 유일하지 않을 수 있고 바뀔 수 있으니 기본 식별자로 쓰지 말라고 한다. 그래서 `user_identities.provider_user_id`에 `sub`를 넣고, 이메일은 연결할 때 한 번만 쓴다.
- **제공자를 따로 테이블로 뺐다.** 카카오·네이버를 추가할 때 `provider` 제약에 값만 더하면 된다.
- **구글 로그인 콜백의 처리 순서**(L3):
  1. `sub`로 `user_identities`를 찾는다. 있으면 그 계정으로 로그인.
  2. 없고 구글의 `email_verified`가 true면 같은 이메일의 `users`를 찾는다.
     - 계정이 없다 → 새 계정을 만들고(인증 완료, 비밀번호 없음) 연결.
     - 인증을 마친 계정이 있다 → 그 계정에 연결.
     - 인증 전 계정이 있다 → 비밀번호를 지우고 인증 완료로 바꾼 뒤 연결. 다른 사람이 그 이메일로 먼저 가입만 해 둔 경우, 남의 비밀번호가 붙은 계정에 연결되는 것을 막는다.
  3. `email_verified`가 false면 로그인을 거부한다.
- **토큰은 해시로만 보관한다.** DB가 새도 메일 링크를 만들 수 없다. 한 번 쓰면 `used_at`을 채운다.

임시 PostgreSQL 16에 V1을 실행하고 아래를 SQL로 돌려 봤다. V1은 경험카드 테이블과 함께 확인했다.

## 4. API

공통 규칙(주소, 본문, 세션 쿠키, CSRF, 오류 꼴)과 공통 오류 코드는 구조 문서 5절에 있다.

| 메서드·주소 | 하는 일 | 비고 |
|---|---|---|
| `POST /api/auth/signup` | 이메일·비밀번호·표시 이름으로 가입, 가입 확인 메일 발송 | 인증을 마친 계정이 그 이메일을 쓰면 409 `EMAIL_TAKEN`. 이메일 존재 여부가 드러난다. 인증 전 계정이면 덮어쓴다(4.1) |
| `POST /api/auth/verify-email` | 메일의 토큰으로 인증 완료 | 지났거나 쓴 토큰이면 410 `LINK_EXPIRED`(4.1) |
| `POST /api/auth/verify-email/resend` | 가입 확인 메일 다시 보내기 | 계정이 없어도 같은 응답 |
| `POST /api/auth/login` | 이메일·비밀번호 로그인 | 틀리면 401 `INVALID_CREDENTIALS`. 인증 전이면 403 `EMAIL_NOT_VERIFIED` |
| `POST /api/auth/logout` | 로그아웃 | |
| `POST /api/auth/password-reset/request` | 재설정 메일 발송 | 계정이 없어도 같은 응답 |
| `POST /api/auth/password-reset/check` | 재설정 링크를 아직 쓸 수 있는지 | 2026-11-14 더함(4.1). 쓸 수 없으면 410 `LINK_EXPIRED` |
| `POST /api/auth/password-reset/confirm` | 토큰과 새 비밀번호로 변경 | 그 계정의 세션을 모두 끊는다 |
| `GET /api/me` | 내 계정: 이메일, 표시 이름, 비밀번호 유무, 연결된 제공자 | 로그인 안 했으면 401. 2026-11-13에 만들었다. 응답은 `{ id, name, email, hasPassword, providers }`다(7절 1번) |

`GET /api/me` 말고는 2026-11-14에 만들었다(`auth/AuthController`, 로그아웃은 `SecurityConfig`).

구글 로그인은 Spring Security의 기본 경로를 쓴다. 직접 만드는 API가 아니다.

| 주소 | 하는 일 |
|---|---|
| `GET /oauth2/authorization/google` | 구글 로그인 화면으로 보낸다. 로그인 화면의 "구글로 계속하기"가 여는 주소 |
| `GET /login/oauth2/code/google` | 구글이 돌아오는 주소. 3.2의 순서대로 처리한 뒤 프런트로 돌려보낸다 |

### 4.1 만들면서 정한 것

2026-11-14에 정한 것(화면·API 대응 문서 3절 2번, 19번, 20번과 이 문서 8절의 비밀번호 규칙):

- **비밀번호 규칙**: 8자 이상, UTF-8로 72바이트 이하, 조합 규칙은 없다. 어기면 400 `INVALID_INPUT`이다. 72바이트는 비밀번호 해시(BCrypt)가 쓰는 길이다(영문 72자, 한글 24자). 로그인에서는 규칙을 보지 않고, 72바이트를 넘으면 틀린 비밀번호와 같은 401이다.
- **인증 전 계정의 이메일로 다시 가입**: 409가 아니라, 새로 넣은 이름과 비밀번호로 덮어쓰고 전에 보낸 링크를 지운 뒤 새 확인 메일을 보낸다. 남이 내 이메일로 가입만 해 두어도 내가 가입할 수 있다. 인증을 마친 계정만 409 `EMAIL_TAKEN`이다.
- **재설정이 인증도 마친다**: 비밀번호 재설정을 마치면 인증 전 계정도 인증을 마친 것으로 본다. 재설정 메일을 받았다는 것이 그 이메일의 주인이라는 뜻이라서다.
- **재설정 링크 미리 확인**: `POST /api/auth/password-reset/check { "token": … }`. 쓸 수 있으면 204, 아니면 410 `LINK_EXPIRED`. 링크를 쓰지는 않는다. 토큰은 서버 접속 기록에 남지 않게 주소가 아니라 본문에 넣는다.
- **로그인 뒤 돌아갈 곳**(구글 로그인을 만들 때): 돌아갈 화면은 프런트가 브라우저(localStorage)에 들고 있는다. 서버는 구글 로그인을 마치면 언제나 프런트의 정해진 주소 하나로, 실패하면 `/login?error=google`로 보낸다. 서버는 돌아갈 주소를 받지 않는다.
- **임시 로그인과 예시 데이터**: 임시 로그인을 걷어내고, dev 예시 사용자는 개발용 비밀번호로 실제 로그인을 한다(구조 문서 6.2).

만들면서 채운 빈칸:

- 돌려줄 값이 없는 요청(가입, 인증, 다시 보내기, 로그아웃, 재설정 요청·확인·바꾸기)은 204다. 로그인은 200과 `GET /api/me`와 같은 내 계정이다.
- 링크를 새로 보내면 그 사람에게 보낸 같은 종류의 쓰지 않은 링크를 지운다. 메일함의 옛 링크는 410이 된다. 재설정을 마치면 그 사람의 다른 재설정 링크도 지운다.
- 인증을 마친 계정에는 확인 메일을 다시 보내지 않는다(응답은 같다).
- 구글로만 가입해 비밀번호가 없는 계정도 재설정 메일을 받는다. 재설정을 마치면 비밀번호가 생겨 이메일로도 로그인한다.
- 로그아웃은 세션 행과 쿠키를 지우고 204를 준다. 로그인하지 않았어도 204다. 다음 로그인에 쓸 새 `XSRF-TOKEN` 쿠키를 함께 준다.
- 이메일과 표시 이름은 앞뒤 공백을 지운다. 이메일은 대소문자를 가리지 않고 찾고, 가입할 때 넣은 그대로 두고 그 주소로 메일을 보낸다.
- 없는 이메일로 로그인할 때도 비밀번호 해시를 한 번 견준다. 계정이 있을 때와 응답 시간이 비슷하다.
- 메일은 DB 변경이 커밋된 뒤에 보낸다. 보내지 못하면 오류를 내지 않고 기록만 남긴다(토큰과 이메일은 남기지 않는다). 계정은 저장되었으므로 "다시 받기"로 다시 보낸다.
- 메일의 보내는 사람은 `app.mail-from`(운영은 환경 변수 `MAIL_FROM`)이다.
- 메일은 요청 안에서 바로 보낸다. 계정이 있을 때만 메일을 보내므로 다시 보내기와 재설정 요청은 계정이 있을 때 조금 늦게 답한다. 가입이 409로 이메일 존재를 이미 알려 주므로 그대로 둔다.

오류 코드(`auth/AuthErrorCode`):

| code | HTTP | 언제 |
|---|---|---|
| `EMAIL_TAKEN` | 409 | 가입: 인증을 마친 계정이 그 이메일을 쓴다 |
| `INVALID_CREDENTIALS` | 401 | 로그인: 계정이 없거나, 비밀번호가 없거나(구글로만 가입), 틀렸다. 셋을 구분하지 않는다 |
| `EMAIL_NOT_VERIFIED` | 403 | 로그인: 비밀번호는 맞지만 인증 전이다(L4) |
| `LINK_EXPIRED` | 410 | 인증, 재설정 미리 확인·바꾸기: 링크가 지났거나, 이미 썼거나, 없다. 셋을 구분하지 않는다. 초대 링크의 410 `INVITE_EXPIRED`와 맞췄다 |

규칙에 맞지 않는 비밀번호, 빈 칸, 이메일 꼴이 아닌 값은 공통 400 `INVALID_INPUT`이다(구조 문서 5.2).

## 5. 화면과 API

| 화면 | 쓰는 API |
|---|---|
| 로그인 | `POST /api/auth/login`, `GET /oauth2/authorization/google`, `GET /api/me` |
| 회원가입 | `POST /api/auth/signup` |
| 이메일 인증 | `POST /api/auth/verify-email`, `POST /api/auth/verify-email/resend` |
| 비밀번호 재설정 | `POST /api/auth/password-reset/request`, `POST /api/auth/password-reset/check`, `POST /api/auth/password-reset/confirm` |

화면별로 보이는 값은 화면·API 대응 문서 2.1절에 있다. 시안이 요구하는데 이 문서에 없는 것: 내 정보 고치기(3절 17번), 탈퇴(18번). 재설정 링크 미리 확인(20번)과 오류 코드 이름(19번)은 2026-11-14에 정해 4절에 넣었다.

## 6. 구글 로그인의 조건

- Google Cloud 프로젝트에서 OAuth 클라이언트를 만들고, 리디렉션 주소로 `{서버 주소}/login/oauth2/code/google`을 등록한다. 로컬과 운영 주소를 각각 넣는다.
- 요청 범위는 `openid`, `email`, `profile`만 쓴다.
- 구글 문서 기준으로, Testing 상태의 앱은 테스트 사용자 100명 제한이 있지만 기본 신원 범위만 요청하는 앱은 허용 목록에 없는 사용자도 접근할 수 있다는 예외가 표에 적혀 있다. 인증(verification)은 민감·제한 범위를 요청하는 공개 앱에 필요하다고 되어 있다.
- 브랜드 인증을 받기 전에는 동의 화면에 앱 이름과 로고가 표시되지 않는다.
- 기본 범위만 쓰는 앱이 운영 상태에서 인증 없이 되는지는 문서가 명시하지 않았다. 실제 콘솔에서 확인이 필요하다.

## 7. 프런트와 맞출 것

1. (2026-11-13 서버를 만들며 더함) `GET /api/me`는 `Viewer`의 `id`, `name`에 `email`, `hasPassword`, `providers`(예: `["google"]`)를 더해 준다. 프런트는 둘만 쓰면 된다.
2. 프런트의 가입·인증·재설정 화면이 기대는 것(`EMAIL_TAKEN`, 토큰 확인, 메일 링크의 프런트 주소)은 화면·API 대응 문서 4절에 있다. 2026-11-14에 서버가 그대로 맞췄다. 아래는 그때 더한 것이다.
3. 지났거나 쓴 링크는 410 `LINK_EXPIRED`다. 프런트의 `"expired"`가 이것이다(`verifyEmail`, `resetPassword`). `checkResetToken`은 `POST /api/auth/password-reset/check`에 `{ "token": … }`을 보내 204면 `true`, 410이면 `false`다.
4. 가입 확인은 `POST /api/auth/verify-email { "token": … }`이다. 가짜 서버의 주석에 있는 `GET /api/auth/verify?token=`이 아니다.
5. 로그인의 틀린 비밀번호는 401 `INVALID_CREDENTIALS`다. 401을 한꺼번에 "로그인 화면으로 보내기"로 처리한다면, 로그인 요청에서는 `code`를 보고 칸 아래에 알린다.
6. 돌려줄 값이 없는 요청은 204다. 로그인은 `GET /api/me`와 같은 내 계정을 돌려준다.
7. 바꾸는 요청에 넣을 `XSRF-TOKEN` 쿠키는 쿠키가 없는 요청의 응답에 실린다. 화면을 처음 열 때 부르는 `GET /api/me`(로그인 전이면 401)가 쿠키를 받는다. 로그인과 로그아웃은 새 쿠키를 주므로 그 뒤에는 쿠키를 다시 읽어 헤더에 넣는다.
8. 비밀번호 칸의 규칙은 서버와 같다: 8자 이상(화면의 "8자 이상"과 같다), 72바이트 이하. 한글 25자 이상은 서버가 400을 준다.

## 8. 새로 생긴 결정

| 항목 | 선택지 |
|---|---|
| 메일 발송 수단 | **정함(2026-11-15)**: 운영은 Amazon SES다(배포 계획 5절). 코드는 Spring의 메일 발송 그대로이고 설정값만 다르다. 개발은 Mailpit이다 |
| 비밀번호 규칙 | **정함(2026-11-14)**: 8자 이상, 72바이트 이하, 조합 규칙 없음(4.1) |
| 세션 유지 기간 | **정함(2026-11-15)**: 지금 값대로 둔다. 마지막 사용 후 14일이면 끊기고(`spring.session.timeout`), 쿠키 수명은 365일이다. 로그인한 지 오래되면 끊는 절대 만료는 두지 않는다. 쿠키 수명은 보안 장치가 아니다(훔친 세션 id는 쿠키 수명과 무관하게 서버의 유휴 제한까지 쓰인다). 로그아웃과 비밀번호 재설정이 세션을 끊는다 |
| L3~L5 | **정함(2026-11-15)**: 모두 초안대로다. L3은 인증된 이메일이면 한 계정으로 연결하고, 구글이 `email_verified`를 참으로 준 경우만이다. L4·L5는 초안대로 만들었다 |
| 요청 횟수 제한 | **정함(2026-11-15)**: 확인·재설정 메일은 같은 사람·같은 용도로 1분에 한 통, 하루 다섯 통까지다. 넘으면 조용히 보내지 않고 204를 그대로 준다(계정이 있는지 드러내지 않게). 앞서 보낸 링크는 그대로 쓰인다. 로그인은 같은 이메일로 15분에 10번 틀리면 429 `TOO_MANY_ATTEMPTS`로 막는다. IP 기준 제한은 배포 때 Cloudflare 규칙으로 둔다. 작업 브랜치 `feat/backend-auth-limits` |
