# 리드미 백엔드 구조

2026-11-17 기준. 서버(`backend/`)가 지금 어떻게 나뉘어 있고 무엇을 만들었는지, 그리고 기능과 무관하게 모든 API에 걸리는 것을 모은 문서다. 프런트의 `리드미_프런트_구조_계획.md`와 짝이다.

- 지켜야 할 규칙: `backend/CLAUDE.md`
- 기능별 테이블과 API: `docs/리드미_설계_로그인.md`, `docs/리드미_설계_경험카드.md`, `docs/리드미_설계_그룹.md`, `docs/리드미_설계_공고.md`, `docs/리드미_설계_프로필.md`, `docs/리드미_설계_메일.md`
- 화면마다 쓰는 API와 설계에 없는 것: `docs/리드미_화면_API_대응.md`
- 배포 구성: `docs/리드미_배포_계획.md`

## 1. 요약

- 패키지는 기능마다 하나(`com.readme.<기능>`)이고 안은 더 나누지 않는다. 테이블마다 쓰기를 맡는 주인 패키지가 있다(3절).
- 쓰기는 JPA 엔티티와 리포지토리로, 응답을 만드는 조회는 `JdbcClient`의 SQL로 한다(4절).
- 만든 API는 이메일·비밀번호 로그인 8개, 내 계정 6개(`GET /api/me`, 2026-11-15에 더한 고치기·탈퇴 4개, 2026-11-16에 더한 구글 연결 시작), 그룹 9개, 그룹 공고 11개(2026-11-15에 공고 고치기와 홈의 그룹 소식 `GET /api/me/group-activity`를 더함), 내 공고 6개(2026-11-15에 그룹 없이 넣기 `POST /api/me/postings`, 2026-11-16에 빼기를 더함), 경험카드 8개(태그 자동완성 포함), 자료 3개(올리기·목록·지우기), 카드 추출 2개, 기본 프로필 2개, 공고 읽어 오기 1개, 메일 자동화 9개, 전형 일정 1개다(뒤의 넷은 2026-11-16). 구글 로그인(주소 2개)은 2026-11-15에 만들었고 구글 클라이언트 값을 넣어야 켜진다(6.1). dev 프로필의 임시 로그인은 2026-11-14에 걷어냈다(6.2).
- jobfit에서 공고키, 키워드 사전, 숫자 뽑기, 카드 검사를 옮겼다(10절).
- 공고 읽어 오기는 서버가 바깥 사이트의 페이지를 받는 유일한 곳이다. 받을 주소는 SSRF 검사를 거친다(`postingread`, 공고 문서 4.6).
- 테이블은 마이그레이션 V1~V12로 30개다(세션 2개 포함, 7절). 나머지 마이그레이션은 칸만 더하거나 지운다.
- 테스트는 서버와 DB를 한 번 띄워 나눠 쓰는 통합 테스트와, Spring 없이 도는 규칙 테스트로 나뉜다(8절).

- Spring의 `@EventListener`다. 기본 설정대로 내는 쪽의 스레드와 트랜잭션에서 바로 돈다. 받는 쪽이 실패하면 탈퇴 전체가 되돌려진다. `@TransactionalEventListener`(커밋 뒤)나 `@Async`로 바꾸지 않는다.
- 이벤트로 한 이유: `group`이 이미 `auth`를 불러와서, `auth`가 `group`의 서비스를 부르면 두 패키지가 서로를 부른다. `auth`가 그룹 테이블에 직접 쓰거나 `group`이 `users`를 지우는 길은 테이블 주인 규칙을 어긴다.
- 그룹 쪽 이어받기 말고 `users`를 가리키는 다른 행은 외래 키(cascade, set null)가 정리한다. 받는 쪽은 외래 키로 안 되는 일만 한다(로그인 문서 4.1의 외래 키 표).
- (2026-11-16) `posting` 안에도 이벤트가 하나 있다. `Postings.findOrCreate`(그룹에 올리기, 내 공고 넣기)가 `PostingAnalyses.Requested`를 내고 `PostingAnalyses`가 커밋 뒤(`@TransactionalEventListener`) 다른 스레드(`@Async`, Boot의 `applicationTaskExecutor`)에서 받아 공고를 분석한다. 패키지 안의 일이고 위의 탈퇴 이벤트와 달리 내는 쪽의 트랜잭션에 들지 않는다. 실패해도 올리기는 되돌려지지 않는다. `@EnableAsync`는 `ReadmeApplication`에 있다(공고 문서 4.7).
- (2026-11-16) `inboundmail` 안에도 같은 꼴의 이벤트가 있다. `MailReceiver`가 받은 메일을 저장하며 `MailClassifier.Received`를 내고, `MailClassifier`가 커밋 뒤 다른 스레드에서 분류한다(메일 설계 M8).
- 탈퇴 미리 보기(`auth/WithdrawalQueries`)는 읽기라서 카드·자료·내 공고·그룹 테이블을 직접 센다(4절). 이어받을 사람의 순서는 `LeaderHandover`와 같게 둔다.

`postingread`는 `group`의 `GroupAccess.requireMember`, `posting`의 `PostingKeys`·`DeadlineKind`, `keyword`의 `KeywordDictionary`, `extraction`의 `UploadedFiles`·`ExtractionErrorCode`를 부른다(2026-11-15, 키워드와 파일 읽기). 파일 하나를 읽는 데 메모리가 수십~수백 MB 들어 동시에 읽는 파일 수는 서버 한 대에 하나로 센다. 그래서 파일 읽기와 그 세마포어는 `extraction`에 두고 `postingread`가 부른다. `extraction`은 `postingread`를 부르지 않는다. `postingread`를 부르는 기능은 없다.

## 4. 한 기능 안의 파일

`group` 패키지를 예로 든다. 규칙은 `backend/CLAUDE.md`의 "패키지"에 있다.

| 파일 | 하는 일 | `group`의 파일 |
|---|---|---|
| `…Controller` | 주소, 입력 검사(`@Valid`), 로그인한 사람 받기. 서비스를 부르고, 트랜잭션이 끝난 뒤 `…Queries`로 응답을 읽는다 | `GroupController` |
| `…Service` | 쓰기 트랜잭션. 바꾼 행의 id만 돌려준다 | `GroupService` |
| 엔티티, `…Repository` | 쓰기. 같이 눌러도 한 번만 되어야 하는 쓰기는 조건이 붙은 native SQL | `Group`, `GroupMember`, `GroupInvite`와 리포지토리 3개 |
| `…Queries` | 응답을 만드는 SQL(`JdbcClient`). 테이블을 넘나들어도 된다 | `GroupQueries` |
| `…Requests`, `…Response` | 요청·응답 record | `GroupRequests`, `GroupResponse`, `MemberResponse` |
| `…ErrorCode` | 기능의 오류 코드 enum | `GroupErrorCode` |
| `package-info.java` | 맡는 것, 테이블, API, 다른 기능이 부르는 것, 근거 문서 | |

응답을 컨트롤러가 트랜잭션 뒤에 읽는 이유: JPA로 바꾼 값은 커밋 전까지 `JdbcClient` 조회에 보이지 않는다.

## 5. 모든 API에 걸리는 것

### 5.1 규칙

- 주소는 `/api` 아래, 본문은 JSON, 메서드는 GET, POST, PUT, DELETE만 쓴다. CORS가 이 넷만 받는다.
- 로그인 유지는 서버 세션 쿠키다(Spring Session JDBC, 쿠키는 `HttpOnly`, `SameSite=Lax`). 유지 기간은 2026-11-15에 지금 값대로 정했다(로그인 문서 8절).
  - 로그인이 끝나는 때는 서버 세션의 유휴 제한(`spring.session.timeout`, 마지막 사용 후 14일)이 정한다.
  - 쿠키 수명(`server.servlet.session.cookie.max-age`)은 이보다 긴 365일로 둔다. 쿠키는 로그인할 때 한 번만 내려오므로, 유휴 제한과 같게 두면 매일 써도 로그인하고 14일 뒤에 끊긴다. 365일은 매일 써도 다시 로그인하게 되는 상한이다(2026-11-14).
  - 이 쿠키 설정은 실제 내장 서버에서만 적용된다. 그래서 쿠키 속성은 내장 서버로 띄우는 `dev/DevProfileTests`에서 확인한다.
- 로그인하지 않은 요청은 401 `UNAUTHENTICATED`다. 로그인 없이 여는 주소는 `/actuator/health`, `/error`, `/api/auth/**`, 구글 로그인의 두 주소(`/oauth2/authorization/google`, `/login/oauth2/code/google`), 초대 미리 보기(`GET /api/group-invites/{token}`. GET만, 2026-11-15), 받은 메일을 넘기는 주소(`POST /api/inbound-mail`. 로그인과 CSRF 검사 없이 Worker의 서명으로 확인한다, 2026-11-16 사용자 결정, 메일 M1)뿐이다(`SecurityConfig`). 구글 로그인이 꺼져 있으면 두 주소는 404다. 초대 수락(`POST …/accept`)은 로그인해야 한다.
- 바꾸는 요청에는 `XSRF-TOKEN` 쿠키의 값을 `X-XSRF-TOKEN` 헤더에 넣는다. 없거나 다르면 403 `CSRF_INVALID`다.
- CORS는 `app.frontend-origin` 하나만 쿠키와 함께 받는다. 개발은 `http://localhost:5173`이다.
- 프런트와 서버는 같은 사이트 아래 둔다(`app.`, `api.`). 세션 쿠키와 CSRF 쿠키가 둘 다에서 쓰여야 해서다. 운영에서는 `app.csrf-cookie-domain`에 상위 도메인을 넣는다. 구성은 배포 계획 문서.
- 보는 사람은 `GET /api/me`로 읽는다. 다른 응답에 보는 사람과 그룹을 다시 싣지 않는다(프런트 구조 계획 4절).
- id는 숫자다. 프런트 타입이 `string`인 곳은 각 설계 문서의 "프런트와 맞출 것"에 있다.
- DB에는 영문 대문자 값(`APPLIED`, `INTERVIEW_1`)을 둔다. 응답에서는 소문자 값(`applied`)이나 화면 글자(`"1차 면접 단계"`)로 바꾼다. V1의 `provider`, `status`도 같은 방식이다.
- 한국 날짜("오늘", 마감됨)는 서버 시간대와 무관하게 `Asia/Seoul`로 구한다(`common/config/TimeConfig`의 `Clock`). 응답의 날짜는 `"YYYY-MM-DD"`, 시각은 `+09:00`을 붙인 ISO 8601이다. 시각에는 소수 초가 붙을 수 있다.
- 남에게 보이면 안 되는 값(공개 범위 밖의 지원 상태 등)은 서버가 잘라서 보낸다. 화면에서 버튼을 숨기는 것과 별개로, 동작마다 권한을 서버가 검사한다.
- 입력의 길이 제한은 테이블 칸의 길이와 같다. 주소 칸은 http·https만 받고, 역슬래시가 든 주소는 받지 않는다(브라우저는 `\`를 `/`로 읽어 다른 호스트를 연다).
- JSON 본문은 4MB까지만 읽고, 넘으면 413 `REQUEST_TOO_LARGE`다(`application.yml`의 `spring.jackson.factory.constraints.read.max-document-length`). Tomcat의 크기 제한은 폼·multipart에만 걸리고 JSON은 Jackson이 끝까지 읽어서, 큰 본문 하나로 힙이 바닥날 수 있었다. 4MB는 가장 큰 요청인 붙여 넣은 글(100만 자, 한글이면 UTF-8로 약 3MB)이 들어가는 크기다. Jackson이 읽은 바이트를 세므로 Content-Length 없는 chunked 본문에도 걸린다(2026-11-15).

### 5.2 공통 오류 코드

오류 응답은 언제나 `{ "code": "...", "message": "..." }`이다. 기능별 코드와 함께 프런트가 처리한다. 서버의 `common/error/CommonErrorCode`다.

| code | HTTP | 언제 |
|---|---|---|
| `INVALID_INPUT` | 400 | 본문을 읽을 수 없거나, 값이 검사를 통과하지 못했거나, 주소의 값 꼴이 틀렸다(`/groups/abc`). 검사에 걸린 칸 이름이 메시지 끝에 붙는다 |
| `UNAUTHENTICATED` | 401 | 로그인하지 않았다 |
| `FORBIDDEN` | 403 | 로그인은 했지만 이 동작을 할 수 없다 |
| `CSRF_INVALID` | 403 | 바꾸는 요청에 `X-XSRF-TOKEN` 헤더가 없거나 `XSRF-TOKEN` 쿠키의 값과 다르다. 화면을 새로 받아 쿠키를 다시 읽은 뒤 보내면 된다 |
| `NOT_FOUND` | 404 | 없는 주소. 없는 그룹·공고는 `GROUP_NOT_FOUND`, `POST_NOT_FOUND`를 쓴다 |
| `METHOD_NOT_ALLOWED` | 405 | 그 주소가 받지 않는 메서드 |
| `REQUEST_TOO_LARGE` | 413 | JSON 본문이 4MB를 넘었다(5.1). 깊이 500, 숫자 1000자리 같은 Jackson의 다른 읽기 한도를 넘은 본문도 이 코드다 |
| `INTERNAL_ERROR` | 500 | 서버의 예상하지 못한 오류. 내부 내용은 응답에 싣지 않는다 |

오류에 값을 함께 실어야 하면 같은 높이에 펼친다: `{ "code": "ALREADY_IN_GROUP", "message": "…", "postId": 12 }`(`ApiException.with`).

기능별 오류 코드가 있는 곳:

| 문서 | 코드 |
|---|---|
| 로그인 4절 | `EMAIL_TAKEN`, `INVALID_CREDENTIALS`, `EMAIL_NOT_VERIFIED`, `TOO_MANY_ATTEMPTS`(429), `LINK_EXPIRED`, `WRONG_PASSWORD`(400), `WRONG_EMAIL`(400), `NO_PASSWORD`(409). 규칙에 맞지 않는 비밀번호는 공통 `INVALID_INPUT` |
| 경험카드 4.3 | `CARD_NOT_FOUND`. 읽을 수 없는 문항 유형은 공통 `INVALID_INPUT` |
| 경험카드 4.4 | `SOURCE_NOT_FOUND`, `SOURCE_TOO_LARGE`, `SOURCE_UNSUPPORTED_TYPE`, `SOURCE_UNREADABLE`, `SOURCE_NO_TEXT`, `SOURCE_EMPTY`(자료 올리기) |
| 그룹 4.1 | `GROUP_NOT_FOUND`, `LEADER_CANNOT_LEAVE`, `INVITE_NOT_FOUND`, `INVITE_EXPIRED` |
| 공고 4.3 | `POST_NOT_FOUND`, `ALREADY_IN_GROUP`, `DEADLINE_ALREADY_SET`, `COMMENT_NOT_FOUND`, `POSTING_NOT_FOUND`, `ALREADY_IN_MY_POSTINGS`, `POSTING_SHARED`, 링크를 읽지 못함 `FETCH_BLOCKED`·`FETCH_FAILED`(422), 파일을 읽지 못함 `FILE_TOO_LARGE`(413)·`FILE_UNSUPPORTED_TYPE`(415)·`FILE_UNREADABLE`·`FILE_NO_TEXT`(422) |

### 6.1 지금 구조

| `auth/GoogleLoginHandler` | 구글 로그인의 끝. 계정을 정한 뒤 `LoginSession.start`를 부르고 프런트의 홈으로, 실패하면 `/login?error=google`로 보낸다. 세션에 구글 연결 표시가 있으면 로그인 대신 그 사람의 계정에 연결하고(`AccountService.linkGoogle`) 그 사람으로 로그인을 되돌린 뒤 `/settings/account?google=<결과>`로 보낸다(2026-11-16). 구글의 access token은 쓰지 않는다. | `auth/AuthMails` | 가입 확인·재설정 메일. 링크는 프런트 주소(`app.frontend-origin`)로 만들고, 보내는 사람은 `app.mail-from`이다. DB 변경이 커밋된 뒤에 보낸다 |
| `common/config/SecurityConfig` | 로그아웃(`POST /api/auth/logout`, Spring Security의 로그아웃 필터), 비밀번호 해시(`PasswordEncoder`, BCrypt), 구글 로그인(`oauth2Login`, 구글 클라이언트 값이 있을 때만) |
| `group/GroupAccess` | 그룹 안의 것을 다루는 API의 첫 검사(멤버인가). 아니면 404 `GROUP_NOT_FOUND` |

구글 로그인은 2026-11-15에 만들었다. 설정으로 켠다: 구글 클라이언트 값(`spring.security.oauth2.client.registration.google`)이 있으면 `SecurityConfig`가 Spring Security의 `oauth2Login`을 켜고, 없으면 서버는 전처럼 뜨고 두 주소는 404다. 개발은 `backend/application-local.yml`(dev 프로필만 읽는다), 운영은 환경 변수 `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`이다. 클라이언트를 만드는 순서와 등록할 돌아올 주소는 로그인 문서 6.1에 있다.

- 주소: `GET /oauth2/authorization/google`이 구글로 보내고, 구글은 `GET /login/oauth2/code/google`로 돌아온다. Spring Security의 기본 경로다.
- Spring의 구글 필터가 사람을 확인하면 `GoogleLoginHandler`가 계정을 정하고 이메일 로그인과 같은 `LoginSession.start`를 부른다. 세션에는 구글의 토큰이 아니라 `LoginUser`가 남는다. 그래서 컨트롤러는 로그인 방식을 모른다.
- 운영에서 돌아올 주소가 `https://api.도메인`으로 만들어지는 것은 `server.forward-headers-strategy: framework`(`application-prod.yml`) 덕분이다.
- 로그인한 채로 구글 연결(2026-11-16): 새 주소는 `/api` 아래의 `POST /api/me/google-link` 하나다. 로그인과 CSRF 검사를 받고, 세션에 연결할 사용자 id를 적는다. 구글로 가고 돌아오는 주소는 위의 둘 그대로이고 `permitAll`도 그대로다. 왜 안전한지는 로그인 문서 4.1에 있다.

- 비밀번호를 재설정하면 그 사람의 세션을 모두 지운다. 세션의 주인 이름(`spring_session.principal_name`)이 사용자 id라서(`LoginUser.getName`) Spring Session으로 찾는다.
- 로그인한 채로 비밀번호를 바꾸면 요청한 세션만 두고 그 사람의 다른 세션을 지운다. 탈퇴하면 그 사람의 세션을 모두 지우고, 요청한 세션도 끝내 응답에서 세션 쿠키를 지운다(2026-11-15). 셋 다 DB 변경이 커밋된 뒤에 지운다. Spring Session은 세션 행을 따로 트랜잭션을 열어 지우므로, 되돌려진 변경 때문에 로그인이 풀리지 않게 하려는 것이다.
- CSRF 쿠키(`XSRF-TOKEN`)는 요청에 없으면 어느 응답에든 새로 실린다(읽기 요청, 401 포함). 로그인과 로그아웃은 새 토큰을 준다.

### 6.2 예시 사용자로 로그인하기 (dev 프로필)

dev 프로필은 빈 DB에 예시 사용자와 예시 그룹·공고를 넣는다(`dev/DevSeedData`, `resources/dev/seed.sql`). dev 프로필이고 prod가 아닐 때만 등록된다.

- 예시 사용자(이메일이 `@example.com`)는 모두 개발용 비밀번호 `readme1234`로 실제 로그인을 한다. 예: `POST /api/auth/login { "email": "daon@example.com", "password": "readme1234" }`.
- 비밀번호는 서버가 뜰 때마다 비밀번호가 없는 예시 사용자에게 넣는다. 비밀번호가 생기기 전에 예시 데이터를 넣은 로컬 DB도 지우지 않고 쓸 수 있다.
- 2026-11-13부터 2026-11-14까지는 실제 로그인보다 그룹을 먼저 만들려고 임시 로그인(`POST /api/auth/dev-login`, 이메일만 받음)을 두었다. 실제 로그인을 만들며 걷어냈다. 세션 확인 테스트는 `auth/LoginTests`로 옮겼다.
- 예시 데이터는 실제 로그인 뒤에도 남기기로 했다(2026-11-14).

### 7.1 Supabase에 올릴 때의 조건

| 항목 | 내용 |
|---|---|
| 연결 방식 | Spring Boot처럼 계속 떠 있는 서버는 직접 연결(포트 5432)을 쓴다. 직접 연결은 IPv6이고, IPv4만 되는 망에서는 IPv4 추가 기능을 사거나 공유 풀러의 세션 모드(포트 5432)를 쓴다 |
| 쓰지 않을 것 | 공유 풀러의 트랜잭션 모드(포트 6543). prepared statement를 지원하지 않는다. 서버리스용이다 |
| Data API | 리드미는 Spring 서버만 DB에 붙는다. Supabase 문서는 클라이언트 라이브러리·REST·GraphQL을 쓰지 않으면 Data API를 끄라고 한다. 끄면 권한 설정과 관계없이 자동 생성 REST 주소가 응답하지 않는다 |
| public 스키마 | 예전에는 `public`에 만든 테이블이 Data API에 자동으로 열렸다. 2026-10-30부터 기존 프로젝트에도 "새 테이블은 명시적으로 권한을 줘야 열린다"가 적용된다. 전용 스키마 `readme`를 쓰면 이 설정과 무관하다 |
| 무료 플랜 | DB 500MB, 1주일 동안 쓰지 않으면 프로젝트 일시 정지, 자동 백업 없음, 활성 프로젝트 2개까지 |
| Pro 플랜 | 월 25달러부터, 디스크 8GB, 7일치 일일 백업, 일시 정지 없음 |

지금부터 지켜 두면 옮기기 쉬운 것:

- 스키마 변경은 Flyway로만 한다. 옮길 때는 빈 DB에 마이그레이션을 실행하고 데이터를 덤프·복원한다.
- Supabase 전용 기능(Auth, Storage, RLS 정책)에 기대지 않는다. 그러면 다른 Postgres 호스팅으로도 갈 수 있다.
- 서버를 올릴 곳이 IPv6으로 나갈 수 있는지 확인한다. 안 되면 세션 모드 풀러 주소를 쓴다.

사람들과 실제로 쓰기 시작하면 무료 플랜의 일시 정지와 백업 없음이 걸린다.

- `GoogleLoginTests`는 구글을 부르지 않는다. 구글로 보내는 것과 돌아온 뒤의 처리(실제 보안 필터와 세션)는 그대로 두고, 구글 쪽(코드를 토큰으로 바꾸기, ID 토큰 검사, 사용자 정보)만 테스트 안의 가짜(`FakeGoogle`)가 답한다.
- 내 PC의 `backend/application-local.yml`은 dev 프로필만 읽는다. test 프로필만 켜는 테스트에는 들어가지 않으므로 거기에는 구글 클라이언트가 없고, 구글 주소가 404인 것을 `common/config/SecurityConfigTests`가 본다. test와 dev를 함께 켜는 `dev/DevProfileTests`는 이 파일을 읽는다. 내 PC에 구글 값이 있으면 그 테스트에서는 구글 로그인이 켜진다(그 테스트는 구글 주소를 보지 않는다).

`Fixtures`에 경험카드용이 있다: `cardSource`(올린 자료), `extractionJob`(끝난 추출 작업), `extracted`(카드를 자료에서 뽑은 것으로), `touchCard`(고친 때를 NOW 앞으로).

`extraction/CardSourceUploadLimitTests`는 Tomcat의 multipart 크기 제한(MockMvc는 거치지 않는다)을 보려고 실제 내장 서버가 필요하다. 파일을 받는 두 주소(자료 올리기, 공고 읽어 오기)를 함께 본다. 서버를 하나 더 띄우지 않으려고 `dev/DevProfileTests`와 설정(`@SpringBootTest(webEnvironment = RANDOM_PORT)`, 프로필 `test`, `dev`)을 똑같이 두어 그 서버를 함께 쓴다. 한쪽 설정을 바꾸면 다른 쪽도 같이 바꾼다.

링크를 읽는 테스트는 바깥 사이트에 가지 않고 내 PC에 띄운 사이트를 읽는다(`postingread/LocalSite`, JDK의 `HttpServer`, `127.0.0.1`의 빈 포트). 읽어 오기는 루프백 주소를 막으므로 test 프로필만 `app.posting-read.allow-loopback-for-tests`를 켠다(`application-test.yml`). 켜도 사설망과 메타데이터 주소는 막힌다. 운영과 개발 설정에는 넣지 않는다. 같은 파일에서 호스트 간격을 0으로, 응답 시간 한도를 2초로 줄였다.
