# 리드미 백엔드 구조

2026-11-13 기준(`dev` `4446a42`). 서버(`backend/`)가 지금 어떻게 나뉘어 있고 무엇을 만들었는지, 그리고 기능과 무관하게 모든 API에 걸리는 것을 모은 문서다. 프런트의 `리드미_프런트_구조_계획.md`와 짝이다.

## 1. 요약

- 패키지는 기능마다 하나(`com.readme.<기능>`)이고 안은 더 나누지 않는다. 테이블마다 쓰기를 맡는 주인 패키지가 있다(3절).
- 쓰기는 JPA 엔티티와 리포지토리로, 응답을 만드는 조회는 `JdbcClient`의 SQL로 한다(4절).
- 만든 API는 이메일·비밀번호 로그인 8개, `GET /api/me`, 그룹 6개, 그룹 공고 9개, 내 공고 1개, 공고 읽어 오기 1개다. 구글 로그인과 경험카드는 아직 없다(9절). dev 프로필의 임시 로그인은 2026-11-14에 걷어냈다(6.2).
- 공고 읽어 오기는 서버가 바깥 사이트의 페이지를 받는 유일한 곳이다. 받을 주소는 SSRF 검사를 거친다(`postingread`, 공고 문서 4.5).
- 테이블은 마이그레이션 V1~V3로 21개다(7절).
- 테스트는 서버와 DB를 한 번 띄워 나눠 쓰는 통합 테스트와, Spring 없이 도는 규칙 테스트로 나뉜다(8절).

## 4. 한 기능 안의 파일

`group` 패키지를 예로 든다. 규칙은 `backend/CLAUDE.md`의 "패키지"에 있다.

| 파일 | 하는 일 | `group`의 파일 |
|---|---|---|
| `…Controller` | 주소, 입력 검사(`@Valid`), 로그인한 사람 받기. 서비스를 부르고, 트랜잭션이 끝난 뒤 `…Queries`로 응답을 읽는다 | `GroupController` |
| `…Service` | 쓰기 트랜잭션. 바꾼 행의 id만 돌려준다 | `GroupService` |
| 엔티티, `…Repository` | 쓰기. 같이 눌러도 한 번만 되어야 하는 쓰기는 조건이 붙은 native SQL | `Group`, `GroupMember`, `GroupInvite`와 리포지토리 3개 |
| `…Queries` | 응답을 만드는 SQL(`JdbcClient`). 테이블을 넘나들어도 된다 | `GroupQueries` |
| `…Requests`, `…Response` | 요청·응답 record | `GroupRequests`, `GroupResponse`, `MemberResponse` |
| `…ErrorCode` | 기능의 오류 코드 enum | `GroupErrorCode` |
| `package-info.java` | 맡는 것, 테이블, API, 다른 기능이 부르는 것, 근거 문서 | |

응답을 컨트롤러가 트랜잭션 뒤에 읽는 이유: JPA로 바꾼 값은 커밋 전까지 `JdbcClient` 조회에 보이지 않는다.

## 5. 모든 API에 걸리는 것

### 5.1 규칙

- 주소는 `/api` 아래, 본문은 JSON, 메서드는 GET, POST, PUT, DELETE만 쓴다. CORS가 이 넷만 받는다.
- 로그인 유지는 서버 세션 쿠키다(Spring Session JDBC, 쿠키는 `HttpOnly`, `SameSite=Lax`). 유지 기간은 `application.yml`에 14일로 넣어 두었지만 아직 정하지 않은 값이다(로그인 문서 8절).
  - 로그인이 끝나는 때는 서버 세션의 유휴 제한(`spring.session.timeout`, 마지막 사용 후 14일)이 정한다.
  - 쿠키 수명(`server.servlet.session.cookie.max-age`)은 이보다 긴 365일로 둔다. 쿠키는 로그인할 때 한 번만 내려오므로, 유휴 제한과 같게 두면 매일 써도 로그인하고 14일 뒤에 끊긴다. 365일은 매일 써도 다시 로그인하게 되는 상한이다(2026-11-14).
  - 이 쿠키 설정은 실제 내장 서버에서만 적용된다. 그래서 쿠키 속성은 내장 서버로 띄우는 `dev/DevProfileTests`에서 확인한다.
- 로그인하지 않은 요청은 401 `UNAUTHENTICATED`다. 로그인 없이 여는 주소는 `/actuator/health`, `/error`, `/api/auth/**`뿐이다(`SecurityConfig`).
- 바꾸는 요청에는 `XSRF-TOKEN` 쿠키의 값을 `X-XSRF-TOKEN` 헤더에 넣는다. 없거나 다르면 403 `CSRF_INVALID`다.
- CORS는 `app.frontend-origin` 하나만 쿠키와 함께 받는다. 개발은 `http://localhost:5173`이다.
- 프런트와 서버는 같은 사이트 아래 둔다(`app.`, `api.`). 세션 쿠키와 CSRF 쿠키가 둘 다에서 쓰여야 해서다. 운영에서는 `app.csrf-cookie-domain`에 상위 도메인을 넣는다. 구성은 배포 계획 문서.
- 보는 사람은 `GET /api/me`로 읽는다. 다른 응답에 보는 사람과 그룹을 다시 싣지 않는다(프런트 구조 계획 4절).
- id는 숫자다. 프런트 타입이 `string`인 곳은 각 설계 문서의 "프런트와 맞출 것"에 있다.
- DB에는 영문 대문자 값(`APPLIED`, `INTERVIEW_1`)을 둔다. 응답에서는 소문자 값(`applied`)이나 화면 글자(`"1차 면접 단계"`)로 바꾼다. V1의 `provider`, `status`도 같은 방식이다.
- 한국 날짜("오늘", 마감됨)는 서버 시간대와 무관하게 `Asia/Seoul`로 구한다(`common/config/TimeConfig`의 `Clock`). 응답의 날짜는 `"YYYY-MM-DD"`, 시각은 `+09:00`을 붙인 ISO 8601이다. 시각에는 소수 초가 붙을 수 있다.
- 남에게 보이면 안 되는 값(공개 범위 밖의 지원 상태 등)은 서버가 잘라서 보낸다. 화면에서 버튼을 숨기는 것과 별개로, 동작마다 권한을 서버가 검사한다.
- 입력의 길이 제한은 테이블 칸의 길이와 같다. 주소 칸은 http·https만 받고, 역슬래시가 든 주소는 받지 않는다(브라우저는 `\`를 `/`로 읽어 다른 호스트를 연다).

### 5.2 공통 오류 코드

오류 응답은 언제나 `{ "code": "...", "message": "..." }`이다. 기능별 코드와 함께 프런트가 처리한다. 서버의 `common/error/CommonErrorCode`다.

| code | HTTP | 언제 |
|---|---|---|
| `INVALID_INPUT` | 400 | 본문을 읽을 수 없거나, 값이 검사를 통과하지 못했거나, 주소의 값 꼴이 틀렸다(`/groups/abc`). 검사에 걸린 칸 이름이 메시지 끝에 붙는다 |
| `UNAUTHENTICATED` | 401 | 로그인하지 않았다 |
| `FORBIDDEN` | 403 | 로그인은 했지만 이 동작을 할 수 없다 |
| `CSRF_INVALID` | 403 | 바꾸는 요청에 `X-XSRF-TOKEN` 헤더가 없거나 `XSRF-TOKEN` 쿠키의 값과 다르다. 화면을 새로 받아 쿠키를 다시 읽은 뒤 보내면 된다 |
| `NOT_FOUND` | 404 | 없는 주소. 없는 그룹·공고는 `GROUP_NOT_FOUND`, `POST_NOT_FOUND`를 쓴다 |
| `METHOD_NOT_ALLOWED` | 405 | 그 주소가 받지 않는 메서드 |
| `INTERNAL_ERROR` | 500 | 서버의 예상하지 못한 오류. 내부 내용은 응답에 싣지 않는다 |

오류에 값을 함께 실어야 하면 같은 높이에 펼친다: `{ "code": "ALREADY_IN_GROUP", "message": "…", "postId": 12 }`(`ApiException.with`).

기능별 오류 코드가 있는 곳:

| 문서 | 코드 |
|---|---|
| 로그인 4절 | `EMAIL_TAKEN`, `INVALID_CREDENTIALS`, `EMAIL_NOT_VERIFIED`, `LINK_EXPIRED`. 규칙에 맞지 않는 비밀번호는 공통 `INVALID_INPUT` |
| 경험카드 | 아직 없다 |
| 그룹 4.1 | `GROUP_NOT_FOUND`, `LEADER_CANNOT_LEAVE`, `INVITE_NOT_FOUND`, `INVITE_EXPIRED` |
| 공고 4.3 | `POST_NOT_FOUND`, `ALREADY_IN_GROUP`, `DEADLINE_ALREADY_SET`, `COMMENT_NOT_FOUND`, `POSTING_NOT_FOUND`, 링크를 읽지 못함 `FETCH_BLOCKED`·`FETCH_FAILED`(422) |

## 6. 로그인과 세션

### 6.1 지금 구조

| 파일 | 하는 일 |
|---|---|
| `auth/LoginSession` | 로그인 방식과 무관하게 사람을 확인한 뒤 부른다. 세션 id를 바꾸고, CSRF 토큰을 새로 만들고, 로그인 정보를 세션에 저장한다 |
| `auth/LoginUser` | 세션에 저장되는 로그인한 사람(`users.id`) |
| `auth/CurrentUser` | 컨트롤러 인자에 붙여 `LoginUser`를 받는다 |
| `auth/AccountQueries`, `MeController` | 계정 읽기, `GET /api/me` |
| `auth/AuthController`, `AccountService` | 가입, 이메일 인증, 로그인, 비밀번호 재설정(로그인 문서 4절). 로그인은 비밀번호를 확인한 뒤 `LoginSession.start`를 부른다 |
| `auth/AuthMails` | 가입 확인·재설정 메일. 링크는 프런트 주소(`app.frontend-origin`)로 만들고, 보내는 사람은 `app.mail-from`이다. DB 변경이 커밋된 뒤에 보낸다 |
| `common/config/SecurityConfig` | 로그아웃(`POST /api/auth/logout`, Spring Security의 로그아웃 필터)과 비밀번호 해시(`PasswordEncoder`, BCrypt) |
| `group/GroupAccess` | 그룹 안의 것을 다루는 API의 첫 검사(멤버인가). 아니면 404 `GROUP_NOT_FOUND` |

구글 로그인은 아직 없다. Google Cloud의 OAuth 클라이언트가 생기면 붙인다. 사람을 확인한 뒤 `LoginSession.start`를 부르면 된다.

- 비밀번호를 재설정하면 그 사람의 세션을 모두 지운다. 세션의 주인 이름(`spring_session.principal_name`)이 사용자 id라서(`LoginUser.getName`) Spring Session으로 찾는다.
- CSRF 쿠키(`XSRF-TOKEN`)는 요청에 없으면 어느 응답에든 새로 실린다(읽기 요청, 401 포함). 로그인과 로그아웃은 새 토큰을 준다.

### 6.2 예시 사용자로 로그인하기 (dev 프로필)

dev 프로필은 빈 DB에 예시 사용자와 예시 그룹·공고를 넣는다(`dev/DevSeedData`, `resources/dev/seed.sql`). dev 프로필이고 prod가 아닐 때만 등록된다.

- 예시 사용자(이메일이 `@example.com`)는 모두 개발용 비밀번호 `readme1234`로 실제 로그인을 한다. 예: `POST /api/auth/login { "email": "daon@example.com", "password": "readme1234" }`.
- 비밀번호는 서버가 뜰 때마다 비밀번호가 없는 예시 사용자에게 넣는다. 비밀번호가 생기기 전에 예시 데이터를 넣은 로컬 DB도 지우지 않고 쓸 수 있다.
- 2026-11-13부터 2026-11-14까지는 실제 로그인보다 그룹을 먼저 만들려고 임시 로그인(`POST /api/auth/dev-login`, 이메일만 받음)을 두었다. 실제 로그인을 만들며 걷어냈다. 세션 확인 테스트는 `auth/LoginTests`로 옮겼다.
- 예시 데이터는 실제 로그인 뒤에도 남기기로 했다(2026-11-14).

## 7. DB

- 스키마는 전용 스키마 `readme`다(옛 로그인 가정 5). JDBC 주소의 `currentSchema=readme`, Flyway의 `default-schema`, Hibernate의 `default_schema`가 모두 이 스키마를 본다.
- 테이블은 Flyway만 만든다. JPA는 `ddl-auto: validate`다.
- 개발 DB는 `compose.yaml`의 PostgreSQL 16(`localhost:5433`)이다. dev 프로필은 빈 DB에 예시 데이터를 한 번 넣는다(6.2).
- 연결 풀은 5다. Supabase 무료 구간에 맞춘 값이다.

| 마이그레이션 | 테이블 | 생성 SQL이 있는 문서 |
|---|---|---|
| `V1__init.sql` | 10개: 계정 3개, 경험카드 6개, `llm_usage` | 로그인 3.1, 경험카드 3.1 |
| `V2__spring_session.sql` | 세션 2개 | spring-session-jdbc에 들어 있는 `schema-postgresql.sql` |
| `V3__groups.sql` | 9개: 그룹 3개, 그룹 공고·내 공고 6개 | 그룹 3.1, 공고 3.1 |

설계 문서의 생성 SQL은 마이그레이션 파일과 글자가 같다(2026-11-13 비교). 마이그레이션 파일이 원본이다.

### 7.1 Supabase에 올릴 때의 조건

| 항목 | 내용 |
|---|---|
| 연결 방식 | Spring Boot처럼 계속 떠 있는 서버는 직접 연결(포트 5432)을 쓴다. 직접 연결은 IPv6이고, IPv4만 되는 망에서는 IPv4 추가 기능을 사거나 공유 풀러의 세션 모드(포트 5432)를 쓴다 |
| 쓰지 않을 것 | 공유 풀러의 트랜잭션 모드(포트 6543). prepared statement를 지원하지 않는다. 서버리스용이다 |
| Data API | 리드미는 Spring 서버만 DB에 붙는다. Supabase 문서는 클라이언트 라이브러리·REST·GraphQL을 쓰지 않으면 Data API를 끄라고 한다. 끄면 권한 설정과 관계없이 자동 생성 REST 주소가 응답하지 않는다 |
| public 스키마 | 예전에는 `public`에 만든 테이블이 Data API에 자동으로 열렸다. 2026-10-30부터 기존 프로젝트에도 "새 테이블은 명시적으로 권한을 줘야 열린다"가 적용된다. 전용 스키마 `readme`를 쓰면 이 설정과 무관하다 |
| 무료 플랜 | DB 500MB, 1주일 동안 쓰지 않으면 프로젝트 일시 정지, 자동 백업 없음, 활성 프로젝트 2개까지 |
| Pro 플랜 | 월 25달러부터, 디스크 8GB, 7일치 일일 백업, 일시 정지 없음 |

지금부터 지켜 두면 옮기기 쉬운 것:

- 스키마 변경은 Flyway로만 한다. 옮길 때는 빈 DB에 마이그레이션을 실행하고 데이터를 덤프·복원한다.
- Supabase 전용 기능(Auth, Storage, RLS 정책)에 기대지 않는다. 그러면 다른 Postgres 호스팅으로도 갈 수 있다.
- 서버를 올릴 곳이 IPv6으로 나갈 수 있는지 확인한다. 안 되면 세션 모드 풀러 주소를 쓴다.

사람들과 실제로 쓰기 시작하면 무료 플랜의 일시 정지와 백업 없음이 걸린다.

## 8. 테스트

| 파일 | 하는 일 |
|---|---|
| `IntegrationTest` | 붙이면 서버 전체와 Testcontainers PostgreSQL을 띄운다. 이 표시를 붙인 테스트끼리 한 번 띄운 것을 나눠 쓴다. 프로필은 `test` |
| `FixedClockConfiguration` | 시계를 2026-11-13 00:30(서울)에 멈춘다(`NOW`, `TODAY`). UTC로는 11-12다 |
| `Fixtures` | 테스트마다 자기 데이터를 만든다. 실제 로그인을 할 사람은 `passwordUser` |

| `TestMailbox` | 메일을 보내지 않고 모은다. 받는 주소로 골라 링크의 토큰을 꺼낸다 |
| `src/test/resources/application-test.yml` | test 프로필. dev의 설정(내 PC의 DB, 메일 수신기, 예시 데이터)은 없다 |

테스트 클래스(2026-11-14): `auth` 4, `common` 4, `dev` 2, `group` 3, `grouppost` 6, `posting` 3. 2026-11-15에 `postingread` 11(통합 테스트는 `PostingReadTests` 하나, 나머지는 Spring 없이 도는 테스트)을 더했다. 규칙은 `backend/CLAUDE.md`의 "테스트"에 있다.

링크를 읽는 테스트는 바깥 사이트에 가지 않고 내 PC에 띄운 사이트를 읽는다(`postingread/LocalSite`, JDK의 `HttpServer`, `127.0.0.1`의 빈 포트). 읽어 오기는 루프백 주소를 막으므로 test 프로필만 `app.posting-read.allow-loopback-for-tests`를 켠다(`application-test.yml`). 켜도 사설망과 메타데이터 주소는 막힌다. 운영과 개발 설정에는 넣지 않는다. 같은 파일에서 호스트 간격을 0으로, 응답 시간 한도를 2초로 줄였다.
