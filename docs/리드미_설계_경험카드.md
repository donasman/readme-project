| 테이블 | 내용 |
|---|---|
| `card_sources` | 올린 자료에서 읽어 낸 본문 |
| `card_extraction_jobs` | 카드 추출 작업의 상태와 진행도 |
| `experience_cards` | 경험카드 본체 |
| `card_tags` | 카드의 태그(키워드 사전의 대표 표기) |

`llm_usage`는 `llm` 패키지의 테이블이다. 지금 LLM을 쓰는 곳이 카드 추출뿐이라 이 문서에 둔다.

### 3.1 생성 SQL

`V1__init.sql`의 뒷부분이다. 앞부분(스키마와 계정 테이블)은 로그인 문서 3.1에 있다. 아래는 마이그레이션 파일과 글자가 같다. 고칠 일이 생기면 마이그레이션 파일이 원본이다.

```sql
set search_path to readme;

-- ── 경험카드 ─────────────────────────────────────────────────────────
create table card_sources (
  id           bigint generated always as identity primary key,
  user_id      bigint      not null references users(id) on delete cascade,
  kind         varchar(10) not null check (kind in ('FILE', 'TEXT')),
  file_name    varchar(255),
  content_type varchar(100),
  byte_size    bigint,
  sha256       char(64)    not null,             -- 같은 자료를 다시 올렸는지 판별
  body         text        not null,             -- 읽어 낸 본문. 숫자 원문 대조에 쓴다
  char_count   integer     not null,
  created_at   timestamptz not null default now(),
  unique (user_id, sha256)
);

create table card_extraction_jobs (
  id            bigint generated always as identity primary key,
  user_id       bigint      not null references users(id) on delete cascade,
  source_id     bigint      not null references card_sources(id) on delete cascade,
  status        varchar(10) not null check (status in ('QUEUED', 'RUNNING', 'DONE', 'FAILED')),
  total_parts   integer     not null,            -- 본문을 5,000자씩 나눈 조각 수 = LLM 호출 수
  done_parts    integer     not null default 0,
  error_message text,
  created_at    timestamptz not null default now(),
  started_at    timestamptz,
  finished_at   timestamptz
);
create index card_extraction_jobs_user_idx on card_extraction_jobs (user_id, created_at desc);

create table experience_cards (
  id               bigint generated always as identity primary key,
  user_id          bigint       not null references users(id) on delete cascade,
  title            varchar(200) not null,
  period           varchar(50),                  -- '2025-03 ~ 2025-06' 글자 그대로
  org              varchar(200),
  role             varchar(200),
  summary          varchar(200),                 -- 60자를 넘으면 경고만 낸다
  situation        text,
  task             text,
  action           text,
  result           text,
  verified         boolean      not null default false,
  verified_at      timestamptz,
  visibility       varchar(10)  not null default 'PRIVATE' check (visibility in ('PRIVATE')),
  source_id        bigint references card_sources(id) on delete set null,
  job_id           bigint references card_extraction_jobs(id) on delete set null,
  extraction_notes jsonb,                        -- 추출 때 생긴 안내 목록. 카드를 확인하면 비운다
  created_at       timestamptz  not null default now(),
  updated_at       timestamptz  not null default now()
);
create index experience_cards_user_idx on experience_cards (user_id, updated_at desc);

create table card_tags (
  card_id bigint       not null references experience_cards(id) on delete cascade,
  tag     varchar(100) not null,                 -- 키워드 사전의 대표 표기
  primary key (card_id, tag)
);
create index card_tags_tag_idx on card_tags (tag);

create table card_usable_for (
  card_id       bigint      not null references experience_cards(id) on delete cascade,
  question_type varchar(10) not null
    check (question_type in ('지원동기', '직무역량', '협업', '문제해결', '성장', '기타')),
  primary key (card_id, question_type)
);

create table card_facts (
  card_id bigint       not null references experience_cards(id) on delete cascade,
  seq     integer      not null,                 -- 화면에 보이는 순서
  body    varchar(500) not null,
  primary key (card_id, seq)
);

-- ── LLM 사용 기록 ────────────────────────────────────────────────────
create table llm_usage (
  id            bigint generated always as identity primary key,
  user_id       bigint references users(id) on delete set null,
  feature       varchar(30) not null,            -- 'EXP_EXTRACT' 등
  model         varchar(50) not null,
  input_tokens  integer     not null,
  output_tokens integer     not null,
  created_at    timestamptz not null default now()
);
create index llm_usage_user_idx on llm_usage (user_id, created_at);
```

```sql
  add column cost_micros           bigint  not null default 0;   -- 백만분의 1달러. 위로 올린다
```

### 3.2 설계 이유

- **카드 칸은 jobfit 형식 그대로다.** title, period, org, role, tags, summary, star 4칸, facts, usable_for, verified. jobfit의 영문 `id`(exp-…)는 DB의 `id`로 대신한다.
- **`period`는 글자 그대로 둔다.** jobfit이 "2025-03 ~ 2025-06", "2026 ~ 현재"처럼 여러 꼴을 받는다. 기간순 정렬이 필요해지면 날짜 칸을 더한다.
- **문항 유형 값은 한글 그대로다.** jobfit 프롬프트와 테스트가 이 이름을 쓴다.
- **자료 본문을 보관하는 이유.** jobfit은 추출된 카드의 숫자를 자료 원문과 대조해, 원문에 없는 숫자가 든 fact는 빼고 star의 숫자는 `[확인 필요: 숫자]`로 바꾼다. 카드를 확인할 때도 원문을 다시 본다. 사용자가 자료를 지우면 카드는 남고 `source_id`만 빈다.
- **`llm_usage`.** 지금 월 100달러 크레딧을 쓰므로 기능별·사용자별 토큰 수를 처음부터 쌓아 둔다.

### 3.3 확인한 것

임시 PostgreSQL 16에 V1을 실행하고 아래를 SQL로 돌려 봤다. V1은 계정 테이블과 함께 확인했다.

| 확인 | 결과 |
|---|---|
| 자료 → 추출 작업 → 카드·태그·유형·fact 저장 | 통과 |
| 카드 목록(태그 + 문항 유형 + 확인 필요 필터), 태그별 카드 수 | 통과 |
| 문항 유형이 아닌 값, 같은 자료 두 번 | 모두 막힘 |
| 자료 삭제 시 카드는 남고 `source_id`·`job_id`만 빈다 | 통과 |

확인하지 않은 것: JPA 매핑. 서버에 카드 코드가 아직 없다.

2026-11-15: 카드 테이블 4개(`experience_cards`, `card_tags`, `card_usable_for`, `card_facts`)의 JPA 매핑을 통합 테스트로 확인했다(`ddl-auto: validate`, 만들기·고치기·지우기·확인). 자료·추출 테이블 2개는 2026-11-15~16에 자료 올리기와 카드 뽑기를 만들며 매핑했다(`extraction/CardSource`, `CardExtractionJob`).

### 4.2 자료와 추출 (5개)

| 메서드·주소 | 하는 일 | 비고 |
|---|---|---|
| `POST /api/card-sources` | 파일을 올리거나 글을 붙여넣는다. 서버가 본문을 읽어 저장 | 응답: 글자 수, 조각 수(= LLM 호출 수), 이미 올린 자료인지. 새 자료면 201, 이미 올린 자료면 200. 2026-11-15에 만들었다 |
| `GET /api/card-sources` | 올린 자료 목록 | 새 것이 앞. 자료마다 가장 최근 추출 작업을 싣는다. 2026-11-15에 만들었다. 2026-11-16에 자료마다 카드 수(`cardCount`)를 더했다 |
| `DELETE /api/card-sources/{id}` | 자료 본문 삭제 | 카드는 남는다(`source_id`만 빈다). 그 자료의 추출 작업은 함께 지워진다. 204. 남의 자료는 404 `SOURCE_NOT_FOUND`. 2026-11-15에 만들었다 |
| `POST /api/card-sources/{id}/extract` | 추출 작업 시작 | 202와 작업. 2026-11-16에 만들었다(4.6) |
| `GET /api/card-extractions/{jobId}` | 작업 상태: 진행 조각 수, 만든 카드 수, 건너뛴 카드 | 프런트가 몇 초마다 조회. 2026-11-16에 만들었다(4.6) |

올리기와 추출을 나눈 이유: 추출 전에 "조각 3개, LLM 호출 3회"를 보여 주고 시작할 수 있다.

올리기 요청은 같은 주소가 `Content-Type`으로 둘을 나눠 받는다.

- 파일: `multipart/form-data`의 `file` 칸 하나.
- 붙여넣은 글: `application/json`의 `{ "text": "…" }`.

올리기 응답(`source`는 목록의 한 항목과 같은 꼴이다):

```json
{
  "source": {
    "id": 3,
    "name": "이력서.pdf",
    "kind": "file",
    "chars": 12480,
    "parts": 3,
    "cardCount": null,
    "createdAt": "2026-11-15",
    "latestJob": null
  },
  "duplicate": false
}
```

- `name`: 파일 이름. 붙여넣은 글이면 `null`이다.
- `kind`: `"file"`, `"text"`.
- `chars`: 본문 글자 수(코드 포인트). `parts`: 본문을 5,000자씩 나눈 조각 수(jobfit `_split`과 같은 규칙). 둘 다 주민번호·전화번호를 가린 본문으로 센다(4.4).
- `cardCount`: 이 자료에서 뽑아 지금 남아 있는 카드 수. 아직 뽑지 않은 자료(추출 작업도 카드도 없다)면 `null`이다(4.4, 2026-11-16 정함).
- `createdAt`: 올린 날(한국 날짜).
- `duplicate`: 이미 올린 자료(다듬고 가린 본문이 같다)면 `true`이고, `source`는 그때 저장한 자료다.
- `latestJob`: 그 자료의 가장 최근 추출 작업. 없으면 `null`이다. 있으면 `{ "id": 7, "status": "running", "doneParts": 2, "totalParts": 3 }`이다. `status`는 `queued`, `running`, `done`, `failed`다(화면·API 대응 문서 3절 23번, 2026-11-15 정함).

`GET /api/card-sources`는 `source`와 같은 꼴의 배열이다.

### 4.3 만들면서 정한 것

2026-11-15에 4.1의 8개를 만들며 정한 것(화면·API 대응 문서 3절 22번, 25번). 가정 C1~C5는 초안대로다.

- **`sourceName`**(22번): 카드 응답에 싣는다. 카드를 뽑은 자료의 `file_name`이다. 자료가 없거나(직접 만든 카드, 자료를 지운 카드) 붙여넣은 글(`kind = TEXT`, 파일 이름이 없다)이면 null이다.
- **태그 자동완성 `GET /api/keywords?q=`**(25번): 프런트의 꼴 그대로 `[{ "label": "Kubernetes", "note": "k8s의 대표 표기" }]`다. `label`은 대표 표기, `note`는 걸린 다른 표기를 적은 글이고 대표 표기에 걸렸으면 null이다. 친 글자와 똑같은 표기, 그 글자로 시작하는 표기, 그 글자가 든 표기의 순이고(대소문자 무관), 같으면 사전 순서다. 대표 표기 하나는 한 번만 나오고 많아야 10개다. 빈 글자면 빈 목록이다.
- **태그**: 대표 표기로 바꿔 저장한다(`스프링부트`, `java` → `Spring Boot`, `Java`). 사전에 없는 태그는 친 그대로(앞뒤 공백만 지운다) 저장하고 검사가 경고한다. 같은 태그는 한 번만 둔다.
- **남의 카드**: 없는 카드와 같은 404 `CARD_NOT_FOUND`다. 둘을 구분하지 않는다.
- **검사 결과 `issues`**: 카드 응답마다(목록, 상세, 만들기, 고치기, 확인) 저장된 값으로 매긴다. 규칙은 jobfit `check_cards`(7절)를 옮긴 `card/CardRules`다. jobfit과 다른 점은 셋이다. 칸 이름과 글을 화면의 말로 쓴다(`"field": "요약"`, "요약이 72자입니다(60자 이내)"). id·예시 카드·verified 검사는 리드미에 해당하지 않아 뺐다(확인 여부는 화면이 따로 보여 준다). 사전에 없는 태그를 경고한다.
- **카드 확인 `POST /api/cards/{id}/verify`**: `verified = true`, `verified_at`은 지금이다. STAR에만 있는 숫자마다 그 숫자가 든 STAR 문장을 근거 숫자 끝에 더한다(120자가 넘으면 숫자 앞뒤만). jobfit `ground_star`에서 사람이 맞다고 한 길(`vouched`)과 같다. `extraction_notes`는 비운다(null). 다시 확인해도 된다. 더할 숫자가 없으면 근거 숫자는 그대로고 `verified_at`만 바뀐다.
- **목록 거르기**: `tag`, `type`, `verified`, `jobId`, `q`를 함께 쓸 수 있다. `tag`는 다른 표기도 대표 표기로 바꿔 찾고, `type`은 다른 이름(기술역량, 팀워크)도 받는다. `q`는 제목, 기간, 어디서, 맡은 일, 요약, STAR, 태그, 근거 숫자에 그 글자가 들었는지 본다. 대소문자를 가리지 않고 `%`·`_`도 글자 그대로다.
- **입력의 길이**: 칸의 길이와 같다(제목 200, 기간 50, 어디서·맡은 일·요약 200, 태그 하나 100, 근거 숫자 하나 500). 칸에 길이가 없는 것은 STAR 한 칸 2,000자, 태그 30개, 근거 숫자 50개까지 받는다(2026-11-15 정함). 카드 검사(숫자 뽑기)가 글 길이의 제곱으로 오래 걸려서다. 막지 않았을 때 4만 자짜리 STAR 한 칸("-a-a-a…")의 검사가 16초 넘게 걸렸고, 목록 요청 다섯 개면 DB 연결 다섯 개를 모두 붙잡았다. 그래서 검사는 DB 쿼리가 끝난 뒤에 한다. 문항 유형은 6종으로 읽은 값만 받는다. 읽을 수 없는 값이 하나라도 있으면 400이다.

만들면서 채운 빈칸:

- 목록(`GET /api/cards`)과 상세는 같은 꼴이다. 카드 확인 화면이 `?verified=false`로 받은 카드를 한 장씩 보여 주므로 목록에도 STAR, 근거 숫자, 검사 결과가 있어야 한다. 카드 수가 적어 한 번에 다 읽는다.
- 목록은 최근에 고친 카드가 앞이다(`updated_at` 역순, 같으면 id 역순). 카드 확인도 고친 것으로 본다.
- 응답의 태그는 이름순이다(대소문자 무관, 영문이 한글보다 앞). `card_tags`에 순서 칸이 없어서다. 문항 유형은 6종의 순서(지원동기, 직무역량, …), 근거 숫자는 넣은 순서다.
- 제목만 꼭 넣는다(빈 제목은 400). 빈 요약·태그·문항 유형은 저장하고 검사가 오류로 알린다. jobfit도 저장된 카드를 검사한다.
- 앞뒤 공백을 지우고 빈 글자는 null로 둔다. STAR의 빈 칸도 null로 두고 응답에서는 빈 글자다. 응답의 `summary`도 없으면 빈 글자다. 빈 태그·근거 숫자는 400이다.
- 고치기(PUT)는 모든 칸을 보낸 값으로 바꾼다. 확인 여부, 자료, 추출 작업, 추출 안내는 그대로다. 근거 숫자는 보낸 순서대로 `seq` 1부터 다시 매긴다.
- 직접 만든 카드는 확인 전(`verified = false`)이다(C5의 추출된 카드와 같다).
- 지우기는 204다. 태그, 문항 유형, 근거 숫자도 지워진다.
- `GET /api/cards/tags`는 `[{ "name": "Spring Boot", "count": 2 }]`다. 많이 쓰인 태그가 앞, 같으면 이름순이다.
- `visibility`는 DB 값 `"PRIVATE"` 그대로 보낸다. 프런트 타입이 이 값이다.
- 카드 확인이 근거 숫자에 무엇을 넣었는지 알리는 글(jobfit이 확인 뒤 보여 주는 줄)은 응답에 싣지 않는다. 더한 문장은 근거 숫자에 보인다.
- 카드 확인은 아직 자료 원문을 보지 않는다. jobfit은 원문에 그 숫자가 있으면 STAR 문장 대신 원문 문장을 넣는다. 자료·추출(4.2)을 만들 때 원문 쪽을 옮겨 맞춘다(구조 문서 10절).

카드 검사(`issues`)의 항목:

| level | field | 언제 |
|---|---|---|
| 오류 | 제목, 태그, 요약, 쓸 문항 유형 | 비었다 |
| 경고 | 요약 | 60자를 넘는다. 이모지도 한 글자로 센다 |
| 경고 | 태그 | 대표 표기가 아니다(API로 저장한 카드는 대표 표기라 나오지 않는다), 사전에 없다 |
| 오류 | 쓸 문항 유형 | 6종이 아니다(API로는 저장되지 않는다) |
| 경고 | 쓸 문항 유형 | 다른 이름이다(API로는 6종으로 바꿔 저장한다) |
| 경고 | 근거 숫자 | 없다 |
| 경고 | STAR | 빈 칸이 있다, 근거 숫자에 없는 숫자가 있다 |
| 경고 | 기간 | 읽을 수 없다(`2025-03 ~ 2025-06`, `2025.03`, `2026 ~ 현재` 같은 꼴이 아니다) |

오류 코드(`card/CardErrorCode`):

| code | HTTP | 언제 |
|---|---|---|
| `CARD_NOT_FOUND` | 404 | 카드 상세·고치기·지우기·확인: 카드가 없거나 남의 카드다. 둘을 구분하지 않는다 |

길이나 개수를 넘은 값, 빈 제목, 빈 태그·근거 숫자, 읽을 수 없는 문항 유형(본문의 `usableFor`, 목록의 `type`), 꼴이 틀린 거르기 값(`verified=maybe`, `jobId=abc`)은 공통 400 `INVALID_INPUT`이다(구조 문서 5.2). 로그인하지 않았으면 `GET /api/keywords`도 401이다.

### 4.4 만들면서 정한 것: 자료 올리기

2026-11-15에 정한 것(화면·API 대응 문서 3절 23번, 24번):

- **받는 형식과 크기**(24번): PDF(글자 층만), DOCX, HWPX, HWP, PPTX, TXT, MD이고 20MB까지다. 시안의 여섯에 HWP를 더했다. 스캔본과 사진은 2026-11-16부터 Claude로 옮겨 적는다(4.7).
- **진행 중인 작업 찾기**(23번): 자료 목록에 자료마다 가장 최근 추출 작업(`latestJob`)을 싣는다. 화면을 나갔다 와도 그 작업을 이어서 묻는다.
- **같은 자료**: `unique (user_id, sha256)`라서 같은 사람이 같은 자료를 다시 올리면 새로 만들지 않고 저장된 자료를 `duplicate: true`로 돌려준다. 조건이 붙은 native insert(`on conflict do nothing`)로 넣고 바뀐 행 수를 본다.

만들면서 채운 빈칸:

- **`sha256`은 다듬은 본문의 해시다**(2026-11-16부터 주민번호·전화번호를 가린 뒤의 본문이다. 아래 "가리기"). 파일 바이트가 아니다. 붙여넣은 글은 바이트가 없어서 두 종류를 한 규칙으로 본다. 같은 이력서를 다시 내보낸 파일은 바이트가 달라도 본문이 같고, 본문이 같으면 같은 카드가 나오므로 추출(LLM 비용)을 다시 하지 않게 막는 데 맞다. 이미 올린 파일의 글을 붙여넣어도 같은 자료다. 대신 파일을 다 읽은 뒤에야 같은 자료인지 안다.
- **형식은 내용으로 정한다.** 파일 앞부분(매직 바이트: `%PDF-`, zip, OLE)과 zip 안의 구성(`word/document.xml`, `ppt/slides/slideN.xml`, `Contents/sectionN.xml`)을 보고, HWP는 FileHeader 스트림의 서명으로 본다. 확장자는 앞부분으로 알 수 없는 TXT와 MD에만 쓴다. 그래서 `이력서.pdf`라는 이름의 DOCX도 DOCX로 읽는다. `content_type`에는 브라우저가 보낸 값이 아니라 서버가 알아낸 형식을 넣는다.
- **라이브러리**: PDF는 Apache PDFBox 3.0.8, HWP는 hwplib 1.1.11(Apache-2.0)이다. hwplib은 쓰는 POI를 안에 품고 있어 다른 의존이 없다. DOCX, PPTX, HWPX는 zip에 XML이라 JDK의 `java.util.zip`과 StAX로 읽는다(Apache POI를 쓰지 않는다).
- **글을 꺼내는 규칙은 jobfit `textio.py`와 같다.** 글자 요소(`w:t`, `a:t`, `hp:t`)를 문단(`w:p`, `a:p`, `hp:p`)마다 이어 줄로 내고, 슬라이드와 구역 사이는 빈 줄이다. PDF는 쪽마다 읽어 빈 줄로 잇고, 쪽당 40자보다 적으면 스캔본이다. jobfit과 다른 점:
  - HWP를 읽는다(jobfit은 읽지 않는다).
  - 열람 암호 없이 열리는 PDF(인쇄·복사 제한만 건 것)는 읽는다(jobfit은 암호가 걸린 PDF를 모두 거부한다).
  - HWPX 구역은 번호 순서다(jobfit은 글자 순서라 `section10`이 `section2` 앞에 온다).
  - 빈 문단 `<w:p></w:p>`에서 jobfit은 빈 줄을 내고 서버는 내지 않는다. `<w:p/>`는 둘 다 내지 않는다.
- **PDF는 한 번에 읽는다.** 쪽 끝에 `\f`를 두고 문서를 한 번 읽은 뒤 쪽으로 나눈다(쪽마다 읽으면 부를 때마다 문서 전체를 돈다). 쪽 수도 쪽 트리의 `/Count`가 아니라 실제로 읽은 쪽을 센다.
- **HWP는 표 안의 글도 읽는다**(hwplib의 `InsertControlTextBetweenParagraphText`). 이력서는 대개 표다. 암호가 걸린 문서와 배포용 문서는 422 `SOURCE_UNREADABLE`이다. hwplib 1.1.11의 글만 읽는 길(`forExtractText`)은 문단 번호 처리에서 오류가 나서 문서 전체를 읽는 길을 쓴다.
- **TXT·MD의 글자 인코딩**: BOM이 있으면 그것(UTF-8, UTF-16), 없으면 UTF-8, 그것도 아니면 CP949(윈도우 메모장의 옛 기본값)로 읽는다. NUL이 든 파일은 글 파일이 아니다(415).
- **다듬기**: 파일과 붙여넣은 글이 같은 규칙을 거친다. 줄바꿈을 `\n`으로 맞추고, 제어 문자(탭과 줄바꿈은 남긴다), NUL(PostgreSQL의 `text`가 받지 않는다), BOM, 짝 없는 서로게이트를 지운다. 한글 자모를 NFC로 합치고(macOS에서 만든 파일) 앞뒤 공백을 지운다. 다듬은 글이 비면 422 `SOURCE_EMPTY`다.
- **주민번호·전화번호 가리기**: **정함(2026-11-16)**. 둘 다 받지 않는 값이다(프로필 방향 문서 2절). 그런데 이력서 원문에 자주 있어서, 그대로 두면 본문(`card_sources.body`)에 저장되고 카드 추출 때 LLM으로 넘어간다(같은 문서 3절 5번). 그래서 다듬은 본문을 해시하고 저장하기 직전에 가린다(`extraction/PersonalNumbers`). 파일과 붙여넣은 글이 같다.
  - 주민번호 꼴은 `[주민번호]`, 전화번호 꼴은 `[전화번호]`로 바꾼다. 무엇이 있던 자리인지 LLM과 사람이 알아보게 한글 이름을 대괄호로 쌌다. 숫자가 없어 카드 검사의 숫자 뽑기에 걸리지 않는다.
  - 주민번호: 생년월일 6자리(달 01~12, 날 01~31), 대시, 뒷자리 7자리(첫 자리 1~8. 외국인등록번호의 5~8도 같은 꼴이다). 대시 앞뒤의 공백, Word·한글이 바꿔 넣는 대시(`–`, `—` 등), 전각 하이픈도 대시로 본다.
  - 붙여 쓴 13자리 주민번호도 가린다. 서류 양식이나 표에서 옮기면 대시 없이 나오기도 한다. 아무 13자리 숫자가 날짜와 성별 자리를 우연히 맞출 확률은 3%쯤이다. 그렇게 걸리는 숫자(주문 번호, 밀리초 시각)는 경험카드에 쓸 숫자가 아니다.
  - 이미 가린 꼴(`950101-1******`)은 그대로 둔다. 생년월일과 성별만 남았고, 둘 다 프로필이 받는 값이다.
  - 전화번호: 휴대폰(010, 011, 016~019), 서울(02), 지역(031~064), 인터넷 전화(070), 평생번호(050X)로 시작하고 가운데 3~4자리, 끝 4자리다. 사이는 `-`, `.`, 공백이거나 붙여 쓴다. 국번을 괄호로 싼 꼴(`(02) 1234-5678`)과 `+82` 꼴(`+82-10-…`, `+82 (0)10-…`, `+821012345678`)도 가린다.
  - 1588·1577 같은 대표번호와 080은 가리지 않는다. 회사의 번호다. 대표번호는 4자리-4자리라 범위(`1500-2000명`)와 꼴도 같다.
  - 걸리지 않게 한 것: 날짜(`2025-03-01`, `2024.02.15`), 기간(`2023.03 ~ 2024.02`), 금액(`1,234,567원`), 비율, 버전(`3.2.1`), IP 주소, 학번, 우편번호. 전화번호는 0이나 `+82`로 시작해야 하고, 앞뒤에 숫자가 더 붙으면 번호로 보지 않는다. 경계는 `PersonalNumbersTests`에 있다.
  - 못 가리는 것: 한글로 쓴 번호(공일공), 자리마다 띄어 쓴 번호, `+` 없이 쓴 `82-10-…`, 공백으로만 나눈 주민번호, 전각 숫자. 주소, 이메일, 계좌번호도 가리지 않는다. 새는 사례가 보이면 꼴을 더한다(코드의 shortcut 주석).
  - 같은 자료인지는 가린 본문의 해시로 본다. 그래서 가리기 전의 같은 글을 다시 올려도 같은 자료다. 전화번호만 다른 두 이력서도 같은 자료가 된다. 같은 카드가 나오므로 그래도 된다.
  - 글자 수(`chars`, `char_count`)와 조각 수도 가린 본문으로 센다. 표시가 번호보다 짧아 그만큼 준다(`010-1234-5678` 13자 → 6자). 그래서 100만 자 상한을 다시 볼 일이 없다.
  - 공고 읽어 오기(`UploadedFiles.documentText`)의 글은 가리지 않는다. 공고의 연락처는 회사의 것이고, 사용자가 그 글을 보고 고친다. 그래서 파일 읽기가 아니라 자료 저장(`CardSourceService.save`)에서 가린다. `card_sources`에 쓰는 곳이 여기 하나라 가리지 않은 본문이 저장될 길이 없다.
  - 저장 트랜잭션 안에서 해시와 함께 한다. 100만 자에 0.1초쯤, 1만 자 이력서는 1ms쯤이다.
  - 이 규칙 전에 저장한 자료는 그대로다. 운영 전이라 따로 고치지 않는다.
- **글자 수는 코드 포인트로 센다.** jobfit의 `len`과 같다. 조각 수도 같은 기준이다.
- **본문은 100만 자까지다**(조각 200개). 넘으면 413 `SOURCE_TOO_LARGE`이고 메시지가 다르다. 이력서·포트폴리오는 보통 10만 자를 넘지 않는다. 메모리와 DB(Supabase 무료 500MB)를 지키려는 상한이다. 붙여넣은 글도 100만 자까지이고, 다듬기 전에 200만 자를 넘으면 사본을 만들기 전에 거부한다.
- **압축 폭탄과 XXE**(사용자가 올린 파일은 믿지 않는다. 가입이 열려 있다):
  - PDF와 HWP는 서버와 다른 자바 프로세스에서 읽는다(`extraction/IsolatedReader`, 2026-11-15 검토 뒤). 작은 파일도 풀면 메모리를 다 쓸 수 있어서다. PDFBox는 스트림 하나를 통째로 메모리에 풀고(xref 스트림 포함), hwplib은 글자마다 객체를 만든다(글자당 20바이트쯤). 그 프로세스는 힙 256MB, 30초로 제한한다. 넘으면 그 프로세스만 끝나고(메모리는 `-XX:+ExitOnOutOfMemoryError`, 시간은 서버가 강제로 끝낸다) 422 `SOURCE_UNREADABLE`이다. 서버는 파일을 임시 파일로 넘기고(표준 입력) 글을 임시 파일로 받으며(표준 출력) 둘 다 바로 지운다. 그 프로세스는 기록을 남기지 않는다. 테스트와 `bootRun`에서는 그 클래스 경로로, 실행 jar(`java -jar`)에서는 jar 안의 `PropertiesLauncher`(`-Dloader.main`)로 띄운다. 실행 jar로 띄워 PDF와 HWP를 올려 확인했다(2026-11-15). 한 번 띄우는 데 1초쯤 걸린다.
  - 동시에 읽는 파일은 2개다(`UploadedFiles`의 세마포어. 2026-11-15부터 공고 읽어 오기의 파일과 함께 센다, 공고 문서 4.6). 기다리는 파일은 Tomcat의 임시 파일에 있다. PDF·HWP를 읽는 프로세스가 둘까지 뜨므로 서버 메모리는 그만큼 더 든다(배포의 `readme-api.service` 주석).
  - zip(DOCX, PPTX, HWPX): 항목 10,000개, 압축을 푼 크기 합계 100MB까지다. 넘으면 413 `SOURCE_TOO_LARGE`다. 항목 이름이 UTF-8이 아닌 zip(한국어 윈도우에서 만든 CP949 이름)은 문서가 아니라 415 `SOURCE_UNSUPPORTED_TYPE`이다.
  - XML: DTD가 든 XML은 읽지 않는다(외부 엔티티, 엔티티 폭탄). DTD와 외부 엔티티를 끈 JDK StAX를 쓴다. Office·한글 문서의 XML에는 DTD가 없다. 요소를 1,000단계보다 깊이 겹친 XML도 읽지 않는다(`jdk.xml.maxElementDepth`). 거부하면 422 `SOURCE_UNREADABLE`이다.
  - 배포용 한글 문서는 스트림이 암호화되어 있어 읽지 않는다(422).
  - 읽는 동안 쌓는 글은 200만 자(UTF-16)를 넘으면 멈춘다. zip의 글은 파일마다 문자열 하나로 쌓는다(문단마다 문자열을 만들지 않는다).
  - 서버 앞의 Caddy는 25MB를 넘는 요청을 끊는다(`deploy/Caddyfile`, 413, 본문 없음). 서버가 메모리를 다 쓰면 끝나고 systemd가 다시 띄운다(`deploy/readme-api.service`의 `-XX:+ExitOnOutOfMemoryError`).
- **20MB를 넘는 파일**: 실제 서버에서는 Tomcat의 multipart 제한(`spring.servlet.multipart.max-file-size: 20MB`)이 먼저 걸린다. `resolve-lazily: true`로 컨트롤러가 인자를 만들 때 파일을 읽게 해서, 이 오류를 자료 컨트롤러가 413 `SOURCE_TOO_LARGE`로 답한다. 다른 기능이 파일을 받게 되면 그 컨트롤러도 같은 처리가 필요하다(공고 읽어 오기가 2026-11-15에 같은 처리로 `FILE_TOO_LARGE`를 준다). `max-request-size`는 multipart 머리말을 넣어 21MB다.
- **파일 이름**: 경로(옛 브라우저는 `C:\…\이력서.pdf`를 보낸다)와 제어 문자를 지우고 NFC로 합친 뒤 255자(칸의 길이)까지 둔다. 남는 것이 없으면 `null`이다.
- **원본 파일은 두지 않는다**(C2). 메모리에서 읽고 버린다. PDF·HWP는 읽는 프로세스에 넘기려고 잠깐 임시 파일에 쓰고 읽은 뒤 바로 지운다.
- **파일을 읽는 일은 트랜잭션 밖에서 한다.** 큰 파일을 읽는 동안 DB 연결(풀 5개)을 잡지 않는다.
- **기록(log)**: 파일 이름과 내용은 남기지 않는다. 읽지 못한 원인은 debug 수준에 예외의 종류만 남긴다.
- **목록의 조각 수는 본문을 읽어 센다.** 조각 수 칸이 테이블에 없어서다. 자료가 많아지거나 본문이 커지면 칸을 더한다(코드의 shortcut 주석).
- **자료마다 카드 수(`cardCount`)**: **정함(2026-11-16)**. 그 자료를 가리키는(`experience_cards.source_id`) 내 카드를 지금 센다. 칸을 따로 두지 않고 목록을 읽을 때 센다. 그래서 지운 카드는 빠지고, 뽑는 중이면 지금까지 만든 카드 수다(C5: 뽑은 카드는 바로 카드 목록에 들어간다). 직접 만든 카드는 자료가 없어 세지 않는다. 추출 작업도 카드도 없으면 `null`이다. 프런트 타입의 뜻("아직 뽑지 않았으면 null")을 따랐다. 뽑았는데 카드를 모두 지웠으면 `0`이다. 올리기 응답의 `source`도 같은 꼴이라 이미 올린 자료면 그 자료의 카드 수가 온다. 자료를 지우면 카드의 `source_id`가 비므로 그 카드는 어느 자료에도 세지 않는다. 카드 수는 `extraction`이 `card`의 테이블을 읽기만 한다(응답을 만드는 조회는 테이블을 넘나들어도 된다).

오류 코드(`extraction/ExtractionErrorCode`):

| code | HTTP | 언제 |
|---|---|---|
| `SOURCE_NOT_FOUND` | 404 | 지우기: 내 자료가 아니거나 없다. 둘을 구분하지 않는다 |
| `SOURCE_TOO_LARGE` | 413 | 파일이 20MB를 넘는다. 메시지가 상황마다 다르다: 글이 100만 자를 넘는다, 압축을 풀면 너무 크다(zip 항목 수·크기) |
| `SOURCE_UNSUPPORTED_TYPE` | 415 | 받는 형식이 아니다(XLSX, CSV, 옛 워드·엑셀, 항목 이름이 CP949인 zip, 확장자 없는 글 등). 확장자가 아니라 내용으로 판단한다 |
| `SOURCE_UNREADABLE` | 422 | 형식은 맞는데 읽지 못했다: 손상된 파일, 열람 암호가 걸린 PDF, 암호·배포용 한글 문서, DTD가 든 XML이나 너무 깊이 겹친 XML, 인코딩을 알 수 없는 글 파일, PDF·HWP를 읽는 프로세스가 메모리(256MB)나 시간(30초)을 넘었다 |
| `SOURCE_NO_TEXT` | 422 | 글자를 읽을 수 없다. 2026-11-16부터 글자 층이 없는 PDF와 사진은 Claude로 옮겨 적으므로(4.7), Claude가 받지 않는 사진 형식(TIFF, HEIC·AVIF)과 옮겨 적지 못한 파일만이다. 메시지가 그 사정을 말한다 |
| `SOURCE_EMPTY` | 422 | 읽은 글이 비었다: 빈 파일, 공백뿐인 파일이나 글 |

`text` 칸이 없는 JSON, `file` 칸이 없는 multipart는 공통 400 `INVALID_INPUT`이다(구조 문서 5.2).

### 4.5 만들면서 정한 것: LLM 호출(`llm` 패키지)

2026-11-16에 정한 것(남은 작업 2단계). `llm_usage`가 이 문서에 있어 함께 둔다:

- **라이브러리**: Anthropic 공식 Java SDK(`com.anthropic:anthropic-java` 3.8.0). Spring AI는 쓰지 않는다(정리 문서 4절 라이브러리 표). Boot 4.1.2·Java 21에서 붙여 확인했다. SDK는 Jackson 2를 쓰고 Boot가 2.21.7로 올린다. 서버의 Jackson 3과 따로 돈다.
- **호출 한 곳**: 다른 기능은 `Llm`만 부른다. `ask(userId, feature, system, text, type)`은 답을 record(`type`)로 받는다. 그 record의 JSON 스키마로 구조화 출력(`output_config.format`)을 요청한다.
- **모델과 생각 깊이**: 모델은 설정값 `app.llm.model`(`claude-opus-5-5`)이다. effort와 출력 상한(`max_tokens`, 생각과 답을 합친 것)은 기능마다 `LlmFeature`에 둔다:

  | 기능 | effort | 출력 상한 |
  |---|---|---|
  | 카드 추출 `CARD_EXTRACT` | medium | 32,000 |
  | 공고 분석 `POSTING_ANALYSIS` | medium | 16,000 |
  | 공고 칸 채우기 `POSTING_FIELDS` | low | 8,000 |
  | 메일 분류 `MAIL_CLASSIFY` | low | 8,000 |
  | 스캔본·사진 옮겨 적기 `DOCUMENT_READ` | low | 32,000 |
  | 성적증명서 과목 줄 읽기 `TRANSCRIPT_READ`(2026-11-19, 학점 계산기 문서) | low | 16,000 |

  출력 상한은 처음 값이고 각 기능을 만들 때 실제 응답을 보고 맞춘다. 생각(thinking)은 보내지 않는다. Opus 5.5는 생각이 늘 켜져 있고 끄면 400이다. temperature도 보내지 않는다.
- **스트리밍**: 늘 스트리밍으로 받고 SDK의 누적기로 최종 메시지를 만든다. 출력이 길어도 HTTP 시간 제한에 걸리지 않는다. 다시 시도는 SDK 기본값이다(408·409·429·5xx와 연결 오류를 2번).
- **거절 대비**: 서버 쪽 fallback(`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`)을 켠다. 안전 분류기가 거절하면 Anthropic이 그 분류에 맞는 모델(Opus 5나 Opus 4.8)로 같은 요청을 돌린다. 그래서 beta 쪽 호출을 쓴다. 넘겨받은 모델까지 거절하면 502 `LLM_FAILED`다.
- **API 키**: `app.llm.api-key`. 개발은 `backend/application-local.yml`, 운영은 `ANTHROPIC_API_KEY`(운영은 키가 없으면 서버가 뜨지 않는다). SDK의 `fromEnv()`는 쓰지 않는다. 키가 없으면 PC의 다른 로그인 정보(`ant` 프로필 등)까지 찾아 쓰기 때문이다. 개발에서 키가 없으면 서버는 뜨고 LLM 기능만 503 `LLM_UNAVAILABLE`이다. SDK 3.8.0은 키를 `x-api-key`가 아니라 `Authorization: Bearer` 머리로 보낸다(테스트에서 본 것).
- **사용액 기록**: 시도 한 번에 `llm_usage` 한 행이다. 서버 쪽 fallback이 돌면 거절한 모델과 넘겨받은 모델이 따로 한 행씩이다. 단가가 다르고, 응답의 맨 위 `usage`에는 마지막 시도만 있어서다(시도별 값은 `usage.iterations`).
  - 칸: 입력·출력·캐시 쓰기(5분, 1시간)·캐시 읽기 토큰, 그리고 저장할 때의 단가표(`app.llm.prices`)로 낸 금액(`cost_micros`, 백만분의 1달러, 위로 올림). 단가가 넷이라 입력·출력 토큰만으로는 금액이 맞지 않는다. 금액을 저장해 두면 단가가 바뀌어도 지난 행은 그대로이고 한도는 합 하나로 본다.
  - 생각 토큰은 출력 토큰에 들어 있다.
  - 단가표에는 Opus 5.5와 fallback이 넘겨줄 수 있는 Opus 5·Opus 4.8이 있다(2026-11-16 가격 문서). 표에 없는 모델은 표에서 가장 비싼 단가로 센다.
  - 거절이나 잘린 답도 기록한다(토큰이 청구된다). API 오류와 연결 실패는 기록하지 않는다.
  - 부른 쪽의 트랜잭션과 따로 커밋한다. 이미 청구된 호출이라 부른 쪽이 되돌려져도 남겨야 한다.
  - `feature`에는 `LlmFeature`의 이름(`CARD_EXTRACT` 등)이 들어간다. V1의 주석 `'EXP_EXTRACT'`는 예였다.
- **한 달 한도**: `Llm.requireBudget(userId)`. 이번 달(서울 기준 달력 월, `Clock`)에 쓴 금액의 합이 `app.llm.monthly-limit-usd`(2달러)에 닿았으면 429 `LLM_LIMIT_REACHED`다.
  - 기능이 사용자의 요청을 받을 때 부른다. `ask`는 한도를 보지 않는다. 그래서 이미 시작한 일(자료의 여러 조각을 차례로 읽는 추출 작업)은 도중에 한도에 닿아도 끝까지 가고, 일 하나만큼 넘을 수 있다.
  - 같은 사람이 동시에 둘을 시작하면 둘 다 통과할 수 있다(코드의 shortcut 주석).
  - 그룹이 나눠 쓰는 공고 분석은 올린 사람의 사용액에 넣는다(정리 문서 7절).
  - 어림(정리 문서 5절의 가정)으로 Opus 5.5는 카드 추출 한 조각이 0.08~0.18달러, 공고 분석 한 건이 0.05~0.15달러다. 자료를 올리고 공고 10건을 넣으면 첫 달에 2달러에 닿을 수 있다. 값은 그대로 두고, 실제 사용액을 보고 다시 본다(2026-11-16 사용자 결정).
- **계정 쪽 안전장치**: Console에서 운영용 키의 작업공간에 한 달 사용 한도를 건다. 서버 코드가 잘못돼도 거기서 멈춘다. 개발용 키는 다른 작업공간에서 만든다. 둘 다 같은 크레딧에서 나간다.
- **기록(log)**: 자료나 공고의 글은 남기지 않는다. 기능, 상태 코드, 요청 id만 남긴다.
- **트랜잭션 밖에서 부른다.** 답을 기다리는 동안 DB 연결(풀 5개)을 잡지 않는다.
- **프롬프트 캐시는 아직 쓰지 않는다.** 카드 추출(5단계)이 조각마다 같은 지시문을 보내므로 그때 붙인다. 기록은 이미 캐시 토큰을 나눠 둔다.
- **테스트**: 실제 API를 부르지 않는다(구조 문서 8절). 실제 키로 부르는 확인은 사용자가 시킬 때만 한다(돈이 든다).

오류 코드(`llm/LlmErrorCode`). LLM을 쓰는 기능의 API가 그대로 낸다. 프런트는 그 기능을 붙일 때 처리한다:

| code | HTTP | 언제 |
|---|---|---|
| `LLM_LIMIT_REACHED` | 429 | 이번 달 사용액이 한도에 닿았다. LLM을 쓰는 기능만 막는다 |
| `LLM_UNAVAILABLE` | 503 | API 키가 없거나 Claude API를 부르지 못했다(키 오류, 계정의 사용 한도·크레딧 소진, 과부하, 연결 실패). 사용액에 넣지 않는다 |
| `LLM_FAILED` | 502 | 답을 받았지만 쓸 수 없다(거절, 출력 상한에 걸림, 형식이 틀림). 사용액에 넣는다 |

### 4.6 만들면서 정한 것: 카드 뽑기

2026-11-16에 만들었다(남은 작업 5-2~5-7). 코드는 `extraction`(작업, 프롬프트, 실행기)과 `card`(카드 다듬기와 저장)에 있다.

API:

- `POST /api/card-sources/{id}/extract`: 202와 작업(아래 꼴). 내 자료가 아니면 404 `SOURCE_NOT_FOUND`, 이번 달 LLM 한도에 닿았으면 429 `LLM_LIMIT_REACHED`(4.5).
  - 그 자료의 작업이 이미 기다리거나(`queued`) 돌고(`running`) 있으면 그 작업을 돌려준다. 새로 만들지 않고 한도도 보지 않는다.
  - 가장 최근 작업이 실패(`failed`)했으면 그 작업을 마친 조각 다음부터 다시 돌린다. 이미 쓴 LLM 사용액을 다시 쓰지 않는다.
  - 그 밖에는 새 작업이다. 다 뽑은 자료를 다시 뽑으면, 이미 있는 카드와 제목이 같은 카드는 건너뛴다.
- `GET /api/card-extractions/{jobId}`: 작업. 내 작업이 아니면 404 `JOB_NOT_FOUND`.

```json
{ "id": 7, "sourceId": 3, "status": "running", "doneParts": 1, "totalParts": 3, "cardsSoFar": 2, "newCards": 0,
  "skippedSameAs": ["주문 조회 API 개선 프로젝트"], "error": null }
```

- `status`: `queued`, `running`, `done`, `failed`. `error`는 `failed`일 때 화면에 보일 이유다(LLM 오류의 메시지).
- `cardsSoFar`: 이 작업이 만든 카드 가운데 남아 있는 수. `newCards`는 끝났으면 `cardsSoFar`, 아니면 0이다.
- `skippedSameAs`: 이미 있는 카드와 같은 경험이라 건너뛴 카드의, 그 이미 있는 카드의 제목들.

돌리는 방법:

- 작업은 뒤에서 돈다(`extraction/ExtractionRunner`). 동시에 2개까지다. 컨트롤러가 작업을 만든 트랜잭션을 마친 뒤에 넘긴다.
- 조각마다 LLM에 한 번 묻는다(`CARD_EXTRACT`, effort medium, 출력 상한 32,000). LLM 호출은 트랜잭션 밖이고, 조각 하나의 저장(카드, 프로필, 마친 조각 수)은 한 트랜잭션이다. 그래서 서버가 도중에 꺼지면 마친 조각까지 남는다.
- 서버가 뜰 때 `QUEUED`·`RUNNING`으로 남은 작업을 마친 조각 다음부터 이어 돌린다(5-7, 배포 계획 6절 8번). 같은 작업이 한 서버에서 두 번 돌지 않게 서버 메모리에 도는 작업을 적어 둔다(서버 한 대 가정, 코드의 shortcut 주석).
- 한도는 시작할 때만 본다. 도중에 한도에 닿아도 끝까지 간다(4.5).
- LLM이 실패하면(키 없음, API 오류, 거절, 쓸 수 없는 답) 작업을 `FAILED`로 두고 그 메시지를 `error`에 싣는다. 이미 저장한 조각의 카드는 남는다.
- 테스트에서는 `app.extraction.synchronous: true`(`application-test.yml`)로 요청한 스레드에서 바로 돌린다.

프롬프트(5-2): `resources/prompts/exp-extract.md`를 jobfit 원본에서 고쳤다.

- 답은 YAML이 아니라 구조화 출력(JSON)이다. 카드 칸은 jobfit과 같고 `usable_for`만 `usableFor`다. jobfit의 영문 id는 없다(DB id를 쓴다).
- 프로필 칸(이름, 생년월일, 학력, 자격증, 어학, 경력)을 함께 뽑는다(프로필 방향 3절 6번). 성별은 2026-11-17에 뺐다. 연락처와 주민번호는 쓰지 말라고 한다. 날짜와 학점도 글자로 받고, 틀린 값은 서버가 버린다.
- 지시문은 늘 같고, 조각마다 바뀌는 것(이미 있는 카드, 태그 표기, 자료 조각)은 사용자 글에 넣는다. 이미 있는 카드는 "경험 — 제목"(경험 이름이 없으면 제목)으로 2,000자까지(4.8), 태그 표기는 600자까지다(jobfit의 `fit_existing`, `fit_list`). 태그 표기는 자료 조각에 나온 사전 낱말, 그다음 내 카드의 태그이고 직무 이름(백엔드 등)은 뺀다.

카드 다듬기(5-4, jobfit `normalize_cards`, `ground_star`, `card/CardRules.normalizeExtracted`·`groundStar`):

- 제목이 이미 있는 카드(또는 같은 답의 앞 카드)와 같으면 건너뛴다. 제목은 NFKC로 바꾸고 공백·기호를 지우고 소문자로 견준다(jobfit `_norm_title`).
- 태그는 대표 표기, 문항 유형은 6종으로 읽고 아닌 것은 빼고 알린다.
- 근거 숫자 가운데 자료에 없는 숫자가 든 것은 빼고 알린다. STAR에만 있는 숫자는, 자료에 있으면 그 숫자가 든 자료 문장(STAR 문장과 가장 많이 겹치는 것, 120자가 넘으면 숫자 앞뒤만)을 근거 숫자에 더하고, 없으면 STAR에서 `[확인 필요: 숫자]`로 바꾼다.
- **jobfit과 다른 점**: 숫자를 자료 전체가 아니라 그 카드가 나온 조각과 대조한다. 숫자 뽑기가 글 길이에 따라 오래 걸려서다. 다른 조각에만 있는 숫자는 `[확인 필요]`가 될 수 있다.
- 칸 길이를 넘는 글은 자른다(제목·기관·역할·요약 200, 기간 50, STAR 한 칸 2,000, 태그 30개·100자, 근거 숫자 50개·500자).
- 안내는 카드의 `extractionNotes`에 화면의 말로 남는다(예: "자료 원문에 없는 숫자가 있어 이 근거 숫자를 뺐습니다 — …"). 카드를 확인하면 빈다.
- 카드는 확인 전(`verified: false`)으로 들어가고, `source_id`, `job_id`, `source_part`(조각 번호)를 단다.
- 패키지: `extraction`이 `CardsExtracted` 이벤트를 내고 `card`(카드 테이블의 주인)의 `ExtractedCardsSaver`가 같은 트랜잭션에서 받아 저장한다. `card`는 `extraction`의 이벤트와 `SourceParts`를 부르고, `extraction`은 `card`를 부르지 않는다(구조 문서 3절).

프로필(5-5): 조각마다 답의 프로필 칸으로 `Profiles.fillBlanks`를 부른다(프로필 설계 4.2: 빈 칸만, 목록은 빈 목록만). 이미 있는 프로필 값은 건드리지 않는다. 학력·경력 같은 목록은 처음 값이 나온 조각의 줄만 들어간다(코드의 shortcut 주석).

원문 조각(5-6, 화면·API 대응 3절 21번): `V7__card_extraction.sql`이 `experience_cards.source_part`(조각 번호)와 `card_extraction_jobs.skipped_titles`를 더했다. 카드 응답의 `sourceExcerpt`는 그 조각의 글(5,000자까지)이다. 목록도 싣는다(카드 확인 화면이 목록으로 받는다). 직접 만든 카드, 자료를 지운 카드, 추출 전에 만든 카드는 `null`이다.

오류 코드 하나를 더했다:

| code | HTTP | 언제 |
|---|---|---|
| `JOB_NOT_FOUND` | 404 | 작업 상태: 내 작업이 아니거나 없다(자료를 지우면 작업도 지워진다) |

스캔본·사진(5-8)은 4.7에 있다.

### 4.7 만들면서 정한 것: 스캔본·사진 읽기

2026-11-16(남은 작업 5-8, 6-1의 파일 쪽). 정리 문서 7절 "OCR 대체"대로 Claude에 파일을 그대로 넣는다(`extraction/ScannedFiles`, `llm`의 `DOCUMENT_READ`, effort low, 출력 상한 32,000).

- 규칙으로 글자를 읽지 못한 파일(글자 층이 없는 PDF, 사진)만 보낸다. 자료 올리기와 공고 읽어 오기의 파일이 같은 길(`UploadedFiles`)이다.
- Claude는 파일의 글자를 그대로 옮겨 적는다(구조화 출력 `{ "text" }`). 옮겨 적은 글은 붙여넣은 글처럼 다듬고, 자료면 주민번호·전화번호를 가려 저장한다(4.4). 저장되는 형식(`content_type`)은 `application/pdf`나 `image/png` 등이다.
- **PDF는 20쪽까지다.** 쪽마다 그림으로도 읽어 쪽 수만큼 돈이 든다(한 쪽에 입력 1,500토큰쯤). 넘으면 Claude를 부르기 전에 413 `SOURCE_TOO_LARGE`("스캔한 PDF는 20쪽까지 읽습니다…")다. 쪽 수는 PDF를 읽는 다른 프로세스가 쪽 나무를 하나씩 세어 넘긴다(`/Count`는 믿지 않는다).
- **사진은 JPG, PNG, GIF, WebP이고 5MB까지다.** Claude가 받는 형식만이다. TIFF와 HEIC·AVIF(아이폰 사진)는 422 `SOURCE_NO_TEXT`("이 사진 형식은 읽지 못합니다. JPG나 PNG로 바꿔 올려 주세요"), 5MB를 넘는 사진은 413 `SOURCE_TOO_LARGE`다.
- 한도는 읽기 전에 보고(429 `LLM_LIMIT_REACHED`), 사용액은 올린 사람에게 넣는다. Claude를 부를 수 없으면(키 없음, API 오류) 503 `LLM_UNAVAILABLE`, 옮겨 적지 못했거나 글자가 없으면 422 `SOURCE_NO_TEXT`("글자를 읽지 못했습니다. 글자가 잘 보이는 파일로 다시 올려 주세요")다.
- 옮겨 적는 동안(수십 초) 요청이 기다린다. 동시에 읽는 파일 수(2개)는 그동안 잡지 않는다. 그 수는 서버 메모리를 지키려는 것이다.
- 공고 읽어 오기에서는 사진도 받는다(옮겨 적은 글을 붙여넣은 본문처럼 읽는다). 못 읽으면 `FILE_NO_TEXT`, `FILE_TOO_LARGE`로 바뀌고, LLM 오류(429, 503)는 그대로 온다.

### 4.8 설계: 장면 단위 카드와 어려움·배운 점 (2026-11-17)

사용자가 2026-11-17에 둘 다 하기로 했고 가정(2절의 C6~C10)도 같은 날 초안대로 정했다(남은 작업 5-11, 5-12). 서버는 같은 날 만들었다(`V12__card_episodes.sql`). 화면도 같은 날 코드를 먼저 만들었다(아래 "화면").

**만들면서 바꾼 것**: 어려움과 배운 점은 카드의 맨 위 칸이 아니라 `star` 안의 두 칸(`star.obstacle`, `star.learning`)으로 두었다. 숫자 검사와 다듬기가 이미 `star`의 칸을 차례로 돌아서, 칸만 늘리면 두 칸까지 같은 규칙이 걸린다. 빈 칸 경고만 STAR 넷을 본다.

**왜 바꾸는가**

- 자소서는 같은 프로젝트를 문항마다 다른 장면으로 쓴다. "주문 조회 API 개선" 하나에도 느린 쿼리를 줄인 장면(문제해결), 캐시 도입을 팀에 설득한 장면(협업), 첫 설계가 틀려 다시 한 장면(성장)이 있다. 지금은 프롬프트가 "경험 하나 = 카드 하나"라서 한 카드의 행동(A)에 여러 장면이 섞이고, 어느 문항에도 딱 맞지 않는다.
- 많이 쓰는 경험 정리 방식은 대부분 STAR의 변형이다(STAR-L·CARL은 배운 점, SOAR·SHARE는 장애물을 더한다). 지금 카드에 없는 재료는 "어려움"과 "배운 점" 둘이다. 이 둘이 있으면 한 카드를 STAR, SOAR, CARL 어느 꼴로든 꺼내 쓸 수 있다. 한국 자소서의 성장·실패 문항은 배운 점을 거의 늘 묻는다.
- PREP(결론, 이유, 사례, 결론)과 XYZ(이력서 한 줄)는 저장 방식이 아니라 보여 주는 방식이다. 자소서 초안(10단계)이나 "이력서 한 줄" 기능에서 쓴다. 이번에는 다루지 않는다.

**바뀌는 것 한눈에**

| 곳 | 지금 | 바뀐 뒤 |
|---|---|---|
| 카드의 단위 | 경험(프로젝트·업무·활동) 하나 | 장면 하나: 한 상황에서 한 번 행동해 한 결과가 나온 것 |
| 경험 | 없다(제목이 경험 이름) | 카드에 `experience`(경험 이름)를 둔다. 같은 이름의 카드가 한 묶음이다(C6) |
| 이야기 칸 | 상황, 과제, 행동, 결과(STAR) | STAR에 어려움(`obstacle`)과 배운 점(`learning`)을 더한다. 둘 다 선택이다 |
| 뽑기 | 경험마다 카드 한 장 | 같은 경험에서 문항 유형이 다른 장면이면 카드를 나눈다. 경험마다 3장까지(C7) |

**테이블**: `V12__card_episodes.sql`(번호는 dev에 들어가는 순서로 정한다)

```sql
set search_path to readme;

alter table experience_cards
  add column experience varchar(200),   -- 경험 이름. 같은 이름(앞뒤 공백·대소문자 무시)의 카드가 한 묶음. 없으면 혼자인 카드
  add column obstacle   text,           -- 어려움(SOAR의 O). 없으면 null
  add column learning   text;           -- 배운 점(STAR-L·CARL의 L). 없으면 null
create index experience_cards_experience_idx on experience_cards (user_id, lower(btrim(experience)));
```

- 지금 있는 카드는 `experience`를 비워 둔다(C9). 화면은 혼자인 카드로 보인다.
- 기간, 어디서, 맡은 일은 지금처럼 카드마다 둔다. 같은 경험의 카드끼리 같은 값을 갖는 것이 보통이지만, 장면마다 기간이 다를 수 있다(C6의 다른 선택지와 함께 본다).

**API**: 카드 응답과 만들기·고치기 본문에 `experience`를 더하고, `star`에 `obstacle`·`learning`을 더한다. 새 주소는 없다.

```json
{
  "id": 12,
  "experience": "주문 조회 API 개선 프로젝트",
  "title": "느린 조회 쿼리를 찾아 응답 시간 줄이기",
  "star": { "situation": "...", "task": "...", "action": "...", "result": "...",
            "obstacle": "운영 DB라 인덱스를 바꾸며 서비스를 멈출 수 없었다",
            "learning": "느린 곳을 짐작하지 않고 실행 계획부터 본다" },
  "...": "그 밖의 칸은 4.1 그대로"
}
```

- `experience`, `star.obstacle`, `star.learning`은 없으면 응답에서 빈 글자다(STAR 칸과 같다). 본문에서 빈 글자와 null은 넣지 않은 것이다.
- 목록 거르기 `experience`는 앞뒤 공백과 대소문자를 가리지 않고 같은 이름이다. 이미 있는 카드 목록(프롬프트)은 `cardHeadings`가 "경험 — 제목"으로 만든다.
- 길이: `experience` 200자, `obstacle`·`learning` 각 2,000자(STAR 한 칸과 같다).
- 목록 거르기에 `experience`(그 경험의 카드만)를 더한다. `q` 검색은 세 칸도 본다.
- 경험 이름 고르기(자동완성)는 화면이 이미 받은 카드 목록에서 만든다. 카드 수가 적어 서버 주소를 더하지 않는다.

**카드 검사(`issues`)**

- 어려움과 배운 점에 근거 숫자에 없는 숫자가 있으면 STAR와 같은 경고를 낸다(C8). 카드 확인(`verify`)이 STAR에만 있는 숫자를 근거 숫자로 옮기는 규칙도 두 칸에 똑같이 쓴다.
- 두 칸이 비었다고 경고하지 않는다. 자료에 없으면 사람이 나중에 채운다.
- 같은 경험에 카드가 많아도 경고하지 않는다.

**뽑기(프롬프트 `exp-extract.md`와 다듬기)**

- 카드 규칙을 바꾼다: "장면 하나 = 카드 하나. 같은 프로젝트·업무에서 답할 수 있는 문항 유형(문제해결, 협업, 성장 …)이 다른 장면이 있으면 카드를 나눈다. 경험마다 3장까지. 같은 장면을 다른 말로 두 번 쓰지 않는다. `experience`는 그 장면이 속한 프로젝트·업무의 이름이고, 같은 경험의 카드는 같은 이름을 쓴다."
- `obstacle`, `learning`: 자료에 적혀 있을 때만 쓴다. 없으면 "". 배운 점을 지어내지 않는다는 것을 프롬프트에 적는다(자료에 없는 소감은 쓰지 않는다).
- 사용자 글의 "이미 있는 카드"에 경험 이름도 싣는다("경험 — 제목"). 같은 장면을 다시 뽑지 않고, 같은 경험의 새 장면은 같은 경험 이름을 쓰게 하려는 것이다.
- 건너뛰기는 지금처럼 제목으로 본다. 장면마다 제목이 달라서 경험 이름은 보지 않는다.
- 숫자 대조(4.6)는 어려움과 배운 점에도 한다.
- 비용: 카드 수만큼 출력이 늘어난다. 2026-11-17의 실제 호출(카드 2장)이 $0.027이었다. 경험마다 2~3장이면 출력이 그만큼 늘어 자료 한 조각에 몇 센트 안이다.

**쓰는 곳**

- 맞는 카드(공고 설계 4.8): 카드마다 센다. 같은 경험의 카드가 여럿 맞으면 여럿 보인다(C10).
- 카드 뽑기 결과의 "카드 N장을 만들었습니다"는 장수 그대로다.
- 자소서 초안(10단계)은 문항 유형에 맞는 장면 카드를 고르고, 문항에 따라 STAR, SOAR(어려움), CARL(배운 점), PREP(두괄식)으로 풀어 쓴다.

**화면(화면·API 대응 3.5의 27·28번)**

2026-11-17에 시안보다 코드를 먼저 만들었다(사용자 결정: 코드를 먼저 쓰고 시안을 코드에 맞춰 고친다). 아래 넷이 처음 정한 것이고, 그 아래가 만든 모양이다.

- 카드 목록: 같은 경험의 카드를 한 묶음으로 보인다(경험 이름 아래에 장면 카드들). 경험이 없는 카드는 혼자 보인다.
- 카드 상세·고치기: 경험 이름(이미 쓴 경험 이름을 고를 수 있다), STAR 사이와 뒤에 어려움·배운 점 칸. 순서는 상황, 과제, 어려움, 행동, 결과, 배운 점.
- 카드 확인: 새 칸 둘과 경험 이름을 보인다. 같은 경험에서 나온 카드가 연달아 오면 "같은 경험의 다른 장면"임을 알린다.
- 직접 만들기: 경험 이름을 고르거나 새로 쓴다. "이 경험의 다른 장면 더하기"로 같은 경험의 새 카드를 연다.

만든 모양(2026-11-17. 같은 날 캔버스 "리드미 시안 3종"의 6차 페이지와 시안 A 카드 목록에도 옮겼다):

- 목록: 경험이 있는 카드는 경험마다 회색 바탕 덩어리에 모은다. 머리 줄에 "경험", 경험 이름(h2), "장면 N장", "장면 더하기"(작은 테두리 버튼)가 있고 그 아래 카드 격자다. 같은 경험은 처음 나온 자리에 모으고, 경험이 없는 카드는 이어진 것끼리 지금처럼 격자로 둔다. 묶기는 `card-rules.ts`의 `groupByExperience`이고 서버와 같이 앞뒤 공백·대소문자를 가리지 않는다.
- 상세: 제목 위에 경험 이름(작은 굵은 회색 글). "STAR" 패널은 "이야기"로 이름을 바꾸고 여섯 칸을 순서대로 보인다. 어려움·배운 점은 비었으면 보이지 않는다. 옆 칸 맨 위에 "경험"과 "이 경험에 장면 더하기"(화살표 링크)를 둔다.
- 고치기·직접 만들기: "기본" 패널 맨 위에 "경험 이름"(선택). 이미 쓴 이름은 브라우저의 고르기 목록(`datalist`)으로 고른다. 이름은 화면이 카드 목록(`GET /api/cards`)을 함께 읽어 만든다. "이야기" 패널에 여섯 칸이 있고, 어려움·배운 점은 "선택" 표시와 무엇을 적는지 안내가 붙는다. "장면 더하기"는 `/cards/new?experience=…`로 열어 경험 이름을 채워 둔다.
- 카드 확인: 같은 경험의 카드를 이어서 본다. 제목 위 줄에 경험 이름과 기간, 같은 경험의 카드가 둘 이상이면 "같은 경험에서 뽑은 장면 N장 가운데 K번째입니다"를 보인다. `[확인 필요]`는 결과뿐 아니라 여섯 칸에서 모두 찾고, "이 문장 지우기"도 여섯 칸에서 지운다(서버가 어느 칸에나 붙이기 때문이다). 상자는 이야기 칸들 아래에 하나 둔다.

**jobfit과 다른 점**: jobfit의 카드는 경험 하나에 STAR 하나다. 어려움·배운 점과 경험 묶음은 리드미에서 더한 것이라 jobfit의 검사·초안 규칙(7절)에 없다. 옮긴 검사(`check_cards`)는 그대로 두고, 숫자 검사만 두 칸으로 넓힌다.

2026-11-15에 자료 올리기를 만들며 프런트와 비교한 것:

1. (2026-11-15, 자료 올리기) `uploadSource`: 파일은 `multipart/form-data`의 `file` 칸으로, 글은 JSON `{ "text": … }`로 보낸다. 응답은 `{ source, duplicate }`이고, 조각 수는 따로 오지 않고 `source.parts`에 있다(프런트의 `chunks`). 새 자료면 201, 이미 올린 자료면 200과 `duplicate: true`다. 이미 올린 자료라고 화면에 알릴지는 프런트가 정한다.
2. `CardSource`: `chars`와 `createdAt`(한국 날짜 `"YYYY-MM-DD"`)은 프런트와 같다. `name`은 붙여넣은 글이면 `null`이다. 가짜 서버처럼 "붙여넣은 글"로 보여 주려면 프런트가 바꿔 쓴다. 서버가 더한 것: `kind`(`"file"`, `"text"`), `parts`, `latestJob`. `cardCount`는 2026-11-16에 더했다(4.4). 프런트 타입처럼 `number | null`이고 아직 뽑지 않은 자료면 `null`이다. 프런트의 `toSource`는 `s.cardCount`를 쓴다.
3. (2026-11-16 카드 뽑기를 만들며 고침) 작업 응답(4.6)은 `{ id, sourceId, status, doneParts, totalParts, cardsSoFar, newCards, skippedSameAs, error }`다. 프런트의 `ExtractionJob`과 다른 곳: 조각을 `doneParts`·`totalParts`로 부른다(프런트는 `doneChunks`·`totalChunks`), 상태가 소문자 넷이고 `failed`와 `error`가 있다(프런트는 `"RUNNING" | "DONE"`), id가 숫자다. 프런트는 서버의 작업을 `toJob`으로 바꿔 쓴다: `doneParts`·`totalParts`는 `doneChunks`·`totalChunks`, `queued`·`running`은 `"RUNNING"`, `done`은 `"DONE"`, `failed`는 `"FAILED"`다. `latestJob`은 `{ id, status, doneParts, totalParts }`다. 프런트의 `ExtractionJob`은 `doneChunks`, `totalChunks`, 대문자 `"RUNNING" | "DONE"`이다. 서버는 조각을 `parts`로 부르고, 상태는 소문자 넷(`queued`, `running`, `done`, `failed`)이다. 화면에 다시 들어오면 `latestJob`이 `queued`·`running`인 자료의 작업을 이어서 묻는다(화면·API 대응 문서 3절 23번).
4. 받는 형식에 HWP가 더해졌다. 프런트의 `ACCEPT`와 안내 글에 `.hwp`를 더했다. 20MB를 넘는 파일은 서버가 413 `SOURCE_TOO_LARGE`로 막는다. 프런트도 보내기 전에 막으면 큰 파일을 올리는 시간을 아낀다(`card-sources-page.tsx`의 shortcut 주석).
5. 오류 코드 6개(4.4)를 화면이 처리한다. 메시지는 화면에 그대로 보여도 된다.
6. 글자 수는 서버가 코드 포인트로 센다. 프런트의 `text.length`(UTF-16)와 이모지에서 다를 수 있으니 서버의 `chars`를 쓴다.
7. (2026-11-15 검토 뒤) 20MB를 넘는 파일은 프런트가 보내기 전에 막는다. 그리고 413은 `code`와 관계없이 모두 "너무 크다"로 처리한다. 서버 앞의 Caddy가 25MB를 넘는 요청을 본문 없는 413으로 끊기 때문이다(`code`가 없다).
8. (2026-11-17, 4.8) 카드에 `experience`(경험 이름, 없으면 빈 글자)가 더해지고 `star`에 `obstacle`·`learning`이 더해졌다. 만들기·고치기 본문도 같다. 목록은 `?experience=`로 한 경험의 카드만 거른다. 프런트의 `CardDetail`, `CardInput`, `Star`에 실었다. 화면은 2026-11-17에 코드를 먼저 만들었다(4.8 "화면"). 목록은 서버의 `?experience=`를 쓰지 않고 받은 카드를 화면에서 묶는다.
